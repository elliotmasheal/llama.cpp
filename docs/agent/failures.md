# 失败处理与升级

## 1. 排错不是退出

- 首次失败就记录：现象/复现命令 -> 根因假设 -> 区分性实验及预期 -> 实际证据 -> 排除项/下一判据。跨轮保留的结论进 `DECISIONS.md`，数字进 `RESULTS.md`。
- 先找第一处偏差，再改代码；CPU 参考也须独立核对。相同变量同方向微调不是新假设；两次无新增证据就换定位手段（反例、边界、逐阶段差分、参考审查），不机械重跑。
- 假设被否定是进展；没有吞吐读数不代表没有证据。无区分性的重试才是无效尝试，没有"试满次数即可退出"的配额。
- 构建/DLL/测试失败、定位不明、一次修复未过门：在授权内自行排错。归因硬件前排除结构性问题；禁止靠缩正式 prompt、改单次最优或放宽阈值过门。

## 2. 必须先确认的六类动作

1. 改目标/阈值/口径/`design`，或删改已有实测数字。
2. 换模型 / 量化 / 后端。
3. 新增 design 5.1 未登记模块，或第二套调度器 / 缓存 / 预算器。
4. 联网下载或向外部服务上传项目内容；本地资料先用完。
5. 预计写盘 > 20 GiB（含 `bench/raw/`）。
6. 单条新命令首次执行预估 > 2 小时。

第 6 类白名单：G-REG 整组、repack 与逐字节校验、全量 `-j8` 构建、`test-backend-ops` 单项；不豁免资源锁及其它边界。已有明确授权只覆盖其指定范围，不重复请示，也不外推。

## 3. 继续、等待、结束

- 授权内的实现方式、补测试、诊断顺序由 agent 决定，不问"要不要继续"。
- 资源冲突写 `blockers`，先做无冲突研究/测试准备；不抢占、不凭超时夺锁。安全工作全部耗尽才以阻塞结束，不循环轮询或虚报完成。
- 六类动作暂停受影响分支；在 `state.json` 的 `escalations` 登记 `id/question/needs_by/options`，向用户给证据、建议与影响。等待时可做独立且已授权的工作。
- 门禁失败不自行放行；design 已规定停问的决策门必须升级，但不阻止无关的已授权研究。
- 仅目标已验收、用户叫停、权限/环境使所有可推进工作受阻时结束。工具限制不能写成完成；保留精确错误、未满足条目、下一命令与恢复条件。

关闭 escalation 时填 `resolved`、`state=closed` 与 `DECISIONS.md` 判决引用。校验器只检查部分字段；散文与待决条目一致性由 agent 核实，不宣称有自动双向检查。
