# 失败处理与升级

## 1. 重试额度

- **同一任务第 5 次尝试前，必须先写"失败假设 + 排查计划"进 `DECISIONS.md` 未结项，再动手。**
- 额度不等于允许重复试错：每次尝试必须写明"它证伪什么、产出什么证据"。
- 同一族假设（同一个变量的同方向微调）不许连试两次；连续两次没拿到新读数即视为无效尝试。
- 归因到硬件之前先排除内核结构性问题（`RESULTS` 51-55 的教训：六次微优化建立在错误读数上）。

## 2. 失败留三样

复现命令、已排除项、下一步判据。

## 3. 必须停下来问用户的六类

1. 改目标或阈值；改 `design`；删改已有实测数字；改口径。
2. 换模型 / 量化 / 后端。
3. 新增 `design` 第 5.1 节未登记的模块，或第二套调度器 / 缓存 / 预算器。
4. 需要联网下载。
5. 预计写盘 > 20 GiB（含 `bench/raw/`）。
6. 单条新命令**首次执行**预估 > 2 小时。

**白名单**（不算第 6 类，直接跑）：G-REG 整组重跑、repack 与逐字节校验、全量 `-j8` 构建、`test-backend-ops` 单项。

## 4. 抬头与升级

- 待用户决策一律进 `state.json` 的 `escalations`，**不允许**写在散文里等用户看到。
- 每条 escalation 必填 `id`、`question`、`needs_by`、`options`（每项一句话 + 影响）。
- 关闭时必须填 `resolved`，并在 `DECISIONS.md` 留判决 slug。
- `state_check.py --lint` 双向检查：文档里出现"请你定 / 等用户 / 待用户"字样而没有对应 open 条目即报错；条目已关闭却仍是 open 也报错。

## 5. 不许做的事

- 不许用"跳过某个臂""只跑一次""把两档平均""换更小的 prompt"之类手段让门禁变绿。
- 资源冲突不许自行抢占：写进 `state.json` 的 `blockers`，由 bench 队首优先。
- 不许把"已知但无害"当绕过（`DECISIONS` 63.4 的教训：分段全绿不等于串联全绿，串联本身是一个测试）。
