# Qwen3.6-35B-A3B Q4_K_XL 专用 MoE 运行时设计文档

- 版本：v0.1（M0 完成，设计草案）
- 日期：2026-10-24
- 目标模型：`F:\LLM\llm\Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf`（21.28 GiB，架构 `qwen35moe`）
- 目标硬件：RX 6700S 8 GiB（Vulkan）+ Ryzen 7 6800HS + 40 GB 内存，笔记本「平衡」电源方案，插电

## 1. 目标与非目标

### 1.1 目标

| 指标 | 目标 | 口径 |
|---|---|---|
| Prefill（PP） | ≥ 1000 tok/s | 10K prompt，ctx 256K，batch 512 |
| Decode（TG） | ≥ 130 tok/s | 单流，greedy，10K prompt 之后的 128 token（2026-10-24 决定由 200 下调到 130） |

TG 目标不调整。达成条件依赖第 6 节的推测解码与命中率假设，M1 需要验证。

### 1.2 非目标

- 不改变权重的量化格式（Q4_K / Q5_K / Q6_K / Q8_0 保持原样）。
- 不改变模型输出（greedy 下与参考实现 bit-level 或 KLD=0 对齐；允许在推测解码中因浮点归约顺序产生的微小差异，需量化上报）。
- 不支持其他模型、其他量化、其他后端（CUDA/Metal 不考虑）。
- 不做多用户服务化调度；单进程、单会话为主，多会话仅作为后续扩展。

### 1.3 硬约束（来自 M0 实测，不随设计变化）

- 每个 token 的稠密权重（output 头 + attention/DeltaNet + 共享专家）必须读一遍：约 **2.17 GB**。
- 显存带宽地板 **≈217 GB/s**（dense GEMV 实测，2026-10-20）。
- 单流 TG 的稠密部分上限：2.17 GB / 217 GB/s ≈ 10 ms → **≤100 tok/s**。这不是运行时能绕过的，必须靠"一次读取摊到多个 token 上"。
- H2D 实测 **14.3 GB/s**（硬墙，2026-10-21）；CPU 读带宽 4 线程约 **40 GB/s**。

## 2. M0 实测结论

### 2.1 张量账（M0-1，本轮从 GGUF 直接统计）

| 类别 | 大小 | 每个 token 读取 |
|---|---|---|
| routed_experts（Q4_K 11520 块、Q5_K 7040 块、Q6_K 630 块） | 18.74 GiB | 只读 top-8 |
| dense_other（attention / DeltaNet / 路由器 / 归一化） | 1.39 GiB | 全量 |
| output 头（Q8_0） | 0.50 GiB | 全量 |
| shared_expert（Q8_0） | 0.13 GiB | 全量 |
| token_embd（Q8_0） | 0.50 GiB | 否（只查一行） |
| nextn（MTP 块，Q8_0） | 8 MiB | 草稿时读取 |

- 层数：40 个主层 + 1 个 MTP 层（`nextn_predict_layers=1`）。
- 专家数 256，top-8，专家 FFN 维 512，hidden 2048。
- 每个专家约 **1.84 MiB**（按 41×256 个专家摊平）。
- 稠密每 token 读取：2.02 GiB ≈ **2.17 GB**。
- 专家每 token 读取：8 × 40 × 1.84 MiB ≈ **0.62 GB**。

### 2.2 路由 trace（M0-2，10K prompt + 128 token greedy）

数据：`bench/raw/m0-qwen36/trace-10k-g128.bin`，模拟脚本：`bench/raw/m0-qwen36/m0-sim.py`，输出：`m0-sim-10k.txt`。

**局部性（解码，只用 30 个完整记录的 DeltaNet 层）**

| 指标 | 数值 |
|---|---|
| 与上一 token 同专家的比例 reuse(t-1) | 56.8% |
| 连续 w 个解码 token 的唯一专家数/层：w=1 / 2 / 4 / 8 | 8.0 / 11.5 / 16.4 / 23.3 |
| 同口径随机路由期望：w=2 / 4 / 8 | 15.8 / 30.5 / 57.4 |

**命中率（全局 LRU，预算以专家数计，换算 MiB 按 1.84 MiB/专家）**

| 缓存占比（39 层 9984 专家） | 容量 | 解码命中（prefill 预热 LRU） |
|---|---|---|
| 10% | 1.78 GiB | 96.8% |
| 20% | 3.57 GiB | 97.4% |
| 25% | 4.46 GiB | 97.9% |
| 30% | 5.35 GiB | 98.2% |

对照：静态 top-N（按 prefill 频次固定）在 25% 只有 46.1%，远低于动态 LRU。**结论：命中来自时间局部性，静态驻留不可取。**

**冷启动对照**：prefill 本身用 LRU（不预热）在 10% 时只有 62.1%，20% 时 79.5%。

### 2.3 M0 的不足（必须写清楚）

1. **解码阶段 trace 有缺口**：40 层中，full-attention 层（3、7、11、…、35）以及层 39 在解码阶段没有 `ffn_moe_*` 节点被回调。根因未查清（已排除图复用 `LLAMA_GRAPH_REUSE_DISABLE`、Vulkan topk 融合；CPU 后端下 `ffn_moe_topk` 在这些层是 VIEW）。本轮统计只用了 30 个完整层，全部是 DeltaNet 层。**M1 必须补全这 10 层的解码路由。**
2. **层 39 只有 21 个 token**：最后一层的输出在 prefill 中被裁剪（只保留需要的行）。本轮排除该层。
3. **prompt 重复性（M1 已部分复测）**：`prompt10k.txt` 为 README 类文本，645 行中仅 407 行唯一。M1 改用 13 份不同技术文档拼接的 `prompt-multidoc10k.txt`（prefill 9402 token）复测，结果与原 prompt 几乎一致：
   - 解码命中率（25% 缓存）：97.8%（原 prompt 97.9%）；
   - w=8 唯一专家/层：23.4（原 23.3）；reuse(t-1)：57.0%（原 56.8%）。
   但这两份都是技术文本，唯一词比例都在 0.4 左右，**仍不是真正的"非重复"文本**（例如对话、代码、多语言），所以结论只适用于这一类 prompt。
4. **带宽数字未在本轮重测**：沿用 2026-10-20/21 同机实测（dense GEMV 217 GB/s、H2D 14.3 GB/s、CPU 40 GB/s）。电源为「平衡」+ 插电（`bench/env/power.txt`，`Win32_Battery.BatteryStatus=2`，未严格核实）。
5. **MTP 接受率已测（完整词表）**：E 为 2.84-3.82，但受限词表下的 E 未测，它决定 TG 130 能否达成。

### 2.5 M1 进展：MTP 多深度测量（完整词表，10K prompt，greedy，256 token）

| `--spec-draft-n-max` | 草稿数 | 接受数 | 单草稿接受率 | 推算周期数 | 每周期产出 token E |
|---|---|---|---|---|---|
| 默认（约 3，128 token 时） | 130 | 83 | 63.8% | 45 | 2.84 |
| 4 | 310 | 177 | 57.1% | 79 | 3.24 |
| 8 | 519 | 189 | 36.4% | 67 | 3.82 |

- 周期数 = 生成 token 数 − 接受数（每个周期产出 接受数 + 1 个 token，含 bonus）。这是推算值，不是直接计数。
- 草稿数/周期：k=4 时约 3.9；k=8 时约 7.7，与推算一致。
- 这些 E 是**完整词表**草稿的结果，也是当前的基线。

**TG 投影（按第 6 节周期模型，未实测）：**

- k=4：周期约 17.7 ms，E=3.24，约 183 tok/s（此处未计入完整词表草稿的输出头代价，见第 2.6 节，修正后约 125）。
- k=8：周期约 21.1 ms，E=3.82，约 181 tok/s（同上，修正后约 102）。

以上是按周期模型做的理论估计，没有把草稿输出头的代价算进去。把完整词表草稿的输出头代价（每步约 2.3 ms）算进去后，见第 2.6 节的修正投影。

**M1 第 3 项（新门槛：TG ≥ 130）：** 当 E ≥ 130 × 周期时间 时通过。k=4 需要 E ≥ 2.3，k=8 需要 E ≥ 2.74。完整词表下，k=3～4 的理论投影满足条件（见第 2.6 节），k=8 不满足。因此第 3 项**有条件通过：草稿深度取 3～4，并且需要实测周期时间确认**。

### 2.6 完整词表草稿的修正投影（计入草稿输出头代价）

草稿每一步都要读一次完整输出头（Q8_0，约 0.5 GB，按 217 GB/s 约 2.3 ms）。周期时间 = 验证 pass + 草稿步数 × 2.3 ms + 未命中 H2D（约 1-1.5 ms）。

草稿步数取第 2.5 节推算的"草稿数/周期"（默认约 2.9，n-max 4 约 3.9，n-max 8 约 7.7）。验证 pass 时间取第 6.2 节（k=3 约 15 ms，k=4 约 15.9 ms，k=8 约 18.3 ms）。

| 配置 | 草稿/周期 | E（已测） | 周期时间（估） | TG（估） | ≥130？ |
|---|---|---|---|---|---|
| 默认深度，完整词表 | 2.9 | 2.84 | 约 22.4 ms | 约 127 | 否 |
| n-max 4，完整词表 | 3.9 | 3.24 | 约 25.9 ms | 约 125 | 否 |
| n-max 8，完整词表 | 7.7 | 3.82 | 约 37.5 ms | 约 102 | 否 |
| 默认深度，受限词表（假设 E 不变） | 2.9 | 2.84 | 约 16.1 ms | 约 176 | 是 |

- **结论：完整词表基线理论上只有约 125，低于 130。** 之前"136～142"的数字是我计算草稿步数时的错误，应以这张表为准。
- 受限词表把草稿代价降到约 0.15 ms/步。要达到 130，E 只需不低于 2.1（默认深度）或 2.3（n-max 4）；已测的完整词表 E 分别是 2.84 和 3.24，因此**受限词表有约 25–30% 的接受率余量**。这正是它的价值：完整词表不达标，受限词表有空间。
- 这些周期时间只是模型估计，误差可能在 ±10%。M2/M3 前必须用真实 Vulkan 路径测量。
- 受限词表的 E 还没测。**第 3 项门槛是否通过，取决于受限词表下的 E 是否不低于上面给出的下限。**

## 3. 概要设计

### 3.1 核心思路

既然稠密权重每 token 必读一遍（约 10 ms 下限），单流 TG 的唯一出路是**一次前向处理多个 token**，把稠密读取和专家读取摊销到 k 个 token 上。M0 的局部性数据表明：连续 8 个 token 只需 23.3 个唯一专家/层（随机是 57.4），这让多 token 验证的专家读取也能摊销。

因此运行时的主路径是：

**原生 MTP 草稿 + 整模型 k=8 批量验证 + 显存专家 LRU 缓存 + 单次提交的每 pass 命令缓冲。**

### 3.2 组件

```
            +-----------------------------+
 prompt --> |  Prefill 引擎（层优先分块）   |--> KV / DeltaNet 状态
            +-----------------------------+
                          |
            +-----------------------------+
            |  Decode 引擎（推测循环）       |
            |   - MTP 草稿（受限词表）        |
            |   - 验证 pass（k 个 token）    |
            |   - 接受/回滚                 |
            +-----------------------------+
                 |                |
     +-----------------+  +------------------------+
     | 稠密权重（VRAM 常驻） |  | 专家存储（RAM 全量，重组布局） |
     |  2.02 GiB         |  |  18.74 GiB            |
     +-----------------+  +------------------------+
                 |                |
     +---------------------------------------+
     | 显存专家缓存（SLRU / LRU，约 3.5-4.5 GiB）|
     +---------------------------------------+
                 |
     +---------------------------------------+
     | Vulkan 内核集（GEMV / GEMM / 路由 / 注意力）|
     +---------------------------------------+
```

### 3.3 与现有 fork 的关系

- 本设计**不复用**通用 `llama_context` 图路径作为 decode 主路径（它每 token 约 4000 个节点，每层有多次 dispatch，且 MoE 节点在解码时有缺口，见 2.3）。
- 复用：GGUF 解析（`gguf-py` 或等价的 C++ 读取）、Vulkan 设备初始化、tokenizer、Q4_K/Q5_K/Q6_K/Q8_0 的反量化与块格式定义（`ggml-common.h`）。
- 复用但需要改造：`ggml-vulkan` 中的 `mul_mat_vec`、`mul_mat_id` 内核（改为批量 k 版本）。
- 不复用：`llama-moe-cache` 的调度与预取（M0 显示静态驻留不如动态 LRU；且它的预取依赖旧的图）。

## 4. 关键技术

### 4.1 原生 MTP 推测解码

- 模型自带 1 个 MTP 层（`blk.40`），共享 output 头与 token_embd。
- 草稿循环：用 MTP 层预测后续 k-1 个 token。每步的 MTP 块只有 8 MiB，成本可忽略。
- **关键问题**：每步草稿要读一次 output 头（Q8_0，0.50 GiB）。7 步就是 3.5 GB，抵消全部收益。
- **基线：完整词表草稿**。草稿步和验证 pass 都用完整词表，零模型改动，接受的 token 与纯 greedy 完全相同。代价是每草稿步读一次输出头（约 0.5 GB，约 2.3 ms）。按第 2.6 节的投影，理论 TG 约 125，低于 130。
- **受限词表草稿**（例如按训练频次选出的 16K 候选）是达到 130 的主要手段。草稿步的输出头读取降到约 33 MB/步，草稿代价近乎为零。只要受限词表的接受率下降不超过约 25–30%，就能达到 130。下降幅度未测，必须先测。
- 正确性由验证 pass 保证：验证始终使用**完整词表**，无论草稿是否受限，接受的 token 都与纯 greedy 一致。受限词表只影响接受率和速度，不影响输出。

### 4.2 批量验证 pass（k=8）

- 一次前向处理 k 个 token（位置连续），稠密权重只读一次。
- 每层的专家路由是 k 个 token 的并集，唯一专家数见 2.2（w=8 时 23.3/层）。
- DeltaNet 层需要支持 k 个 token 的串行状态更新（递推本身是串行的，但权重读取可以共享）；full-attention 层需要 k 个 query 对同一段 KV 的注意力（KV 只读一次）。
- 固定形状：k ∈ {1, 2, 4, 8} 四种形状，各自预录命令缓冲，避免每 token 重建图。

### 4.3 显存专家缓存

- 容量：约 3.5 GiB（约 1950 个专家，占 19.5%）。命中率 20% 时为 97.4%（M0 实测），足够。
- 替换策略：按层的 SLRU（probation / protected 两段），不用静态驻留。
- 缓存槽：每个槽 1.84 MiB，按专家整块存放，与重组后的 RAM 布局一一对应。
- 未命中：通过 H2D（14.3 GB/s）搬到专用槽位；在 k=8 窗口内，未命中约 19.6 个专家/窗口，约 38 MB，H2D 约 2.6 ms。这部分与计算重叠（M0 记录的双队列隐藏率约 99%）。

### 4.4 文件重组（允许）

- 按 `[层][专家]` 连续存放 gate/up/down 三块，每个专家 1.84 MiB 对齐到 2 MiB 边界（或 64 KiB 对齐，取决于 H2D 块大小测量结果）。
- 按 10K 统计的使用频次（LRU 用不到，但用于初始化预热和分析）写入 sidecar 索引。
- 重组前后权重字节一致（逐块校验），不修改任何量化值。
- 仅重排，不转换格式。

### 4.5 Prefill（PP）

- 层优先分块：chunk = 512 token；每层的专家只读一次，用双缓冲从 RAM 上传。
- 计算量约 6 GFLOP/token，1000 tok/s 需要约 6 TFLOPS 有效算力，超过 RDNA2 FP32 实际能力，**必须用 int8 点积**（`V_DOT4_I32_I8`）的 Q4_K × Q8_1 GEMM。
- 每层上传约 470 MB，在 14.3 GB/s 下约 33 ms；每层计算约 100 ms（2048 token），传输被计算覆盖。
- 注意力：DeltaNet 层为线性复杂度；full-attention 层的 10K 注意力计算占比低。

### 4.6 每 pass 的执行模型

- 每个 pass 一个命令缓冲，层间只用 barrier，不回到 CPU。
- 采样在 GPU 上做 greedy（argmax 或 top-1 候选），只回传 k 个 token id。
- 接受判定在 CPU 上做（k 个 int32，比较即可）。
- 同步次数：每 pass 1 次（等待 k 个 id），而非每层一次。

### 4.7 CPU 角色

- 当前设计 CPU 不参与 decode 的专家计算（专家缓存 + H2D 已覆盖 2% 未命中）。
- CPU 只负责：分词、接受判定、调度、MTP 草稿的候选词表选择。
- 如果 M1 测得未命中率明显高于 2%，再启用 CPU 计算未命中专家（40 GB/s 下的备用路径）。

## 5. 核心实现

### 5.1 模块划分

| 模块 | 职责 | 输入 | 输出 |
|---|---|---|---|
| `gguf_index` | 读取 GGUF，建立张量表与字节偏移 | GGUF 路径 | 张量描述符 |
| `repack` | 生成重组文件（专家连续、对齐） | 原 GGUF | `*.qwen36rt.bin` + 索引 |
| `vk_dev` | Vulkan 设备、队列、内存分配（显存预算） | 设备参数 | 设备句柄、分配器 |
| `weights` | 稠密权重常驻显存；专家存储映射 | 重组文件 | 稠密缓冲、专家页表 |
| `expert_cache` | 显存专家槽、SLRU、H2D 调度 | 路由 id 列表 | 命中/未命中、槽号 |
| `kernels` | 批量 GEMV/GEMM、路由 top-8、注意力、DeltaNet | 张量 | 张量 |
| `pass` | 构建并提交一个 pass 的命令缓冲（按 k 预录） | k、位置、KV 句柄 | token ids |
| `spec` | MTP 草稿、受限词表、接受/回滚 | 上下文、草稿 logits | 接受 token 序列 |
| `prefill` | 层优先分块的 prefill | prompt | KV 与 DeltaNet 状态 |
| `telemetry` | 命中率、H2D 字节、每 pass 耗时、接受率 | 每 pass 事件 | CSV/JSON |

### 5.2 数据结构（草案）

```c++
struct ExpertKey { uint16_t layer; uint16_t expert; };   // 40/41 层 × 256
struct ExpertSlot { int32_t slot; uint32_t gen; };        // 显存槽号与代数
struct ExpertPageTable {                                  // 静态表，启动时生成
    uint64_t host_offset[41][256];                        // 重组文件内偏移
    ExpertSlot cache[41][256];                            // 当前驻留槽（-1 表示未驻留）
};
struct PassPlan {
    uint32_t k;                                           // 1/2/4/8
    int32_t  pos0;                                        // 起始位置
    uint32_t route_ids[41][8][8];                         // 每层每 token 的 top-8（GPU 写，CPU 读取）
};
```

### 5.3 pass 流程（伪代码）

```
pass_step(k, tokens):
  upload tokens and pos
  for layer in 0..39:
    attn_or_deltanet(layer, k)           # 稠密读取，一次
    router(layer, k) -> route_ids        # top-8，GPU 上
    cache_lookup(layer, route_ids)       # GPU 上查表，输出 hit/miss mask
    if miss_count > 0: enqueue_h2d(...)  # 与计算重叠
    moe_compute(layer, k, slots)         # 命中专家直接算，未命中等 H2D 完成
  output_head(k)                         # 完整词表，argmax
  submit(); wait(); read(k ids, route stats)
```

### 5.4 接受与回滚

```
draft = mtp_draft(ctx, k-1)            # 受限词表
verified = pass(k, [last] + draft)     # 完整词表
accept = longest prefix where draft[i] == verified[i]
ctx.append(accept) + verified[len(accept)]   # 第一个不匹配处用验证结果
rollback KV/DeltaNet state to accept length  # DeltaNet 需要保存 k 个中间状态
```

- DeltaNet 回滚：在 pass 内保存每个 token 之后的递推状态（k 份，状态很小）；接受后只保留需要的那一份。
- full-attention 层的 KV：按位置写入，回滚只需移动长度指针。

### 5.5 显存预算（8176 MiB 设备）

| 项目 | MiB | 备注 |
|---|---|---|
| 桌面占用 | 500-1400 | 运行时无法控制，取中值约 1000 |
| 稠密权重 | 2068 | 2.02 GiB |
| 专家缓存 | 3584 | 3.5 GiB，约 1950 槽 |
| KV（full-attention，256K） | 待测 | 取决于 full-attention 层数，需从 GGUF 确认 |
| 计算缓冲（k=8，ubatch=512） | 约 1100 | 参考 M0 的 Vulkan compute buffer 1016 MiB |
| 草稿与其他 | 约 100 | 受限词表 logits、MTP 块 |
| 合计（不含 KV） | 约 7850 | 超出 8176 - 1000 = 7176，**需要缩小缓存或计算缓冲** |

**修正方案**：专家缓存降到 2.5-3.0 GiB（约 1400-1600 槽，命中率约 95-96%，待 M1 验证）；计算缓冲按 k=8 实测压缩。这一项必须在 M1 实测后定稿。

## 6. 性能模型

### 6.1 单 pass 字节账（k 个 token）

- 稠密：2.17 GB（每 pass 一次）。
- 专家（VRAM 读取）：U_k × 40 × 1.93 MB，U_k 取 M0 实测值。
- 未命中（H2D）：U_k × 40 × miss_rate × 1.93 MB，miss_rate 取 2%。
- 草稿（k-1 步）：(k-1) × (33 MB 受限头 + 8 MiB MTP 块)。

### 6.2 计算表（显存 217 GB/s，H2D 14.3 GB/s）

| k | U_k | 专家读取 | pass 读取（VRAM） | pass 时间 | 未命中 H2D | 草稿 | 周期时间（不重叠 / 完全重叠） |
|---|---|---|---|---|---|---|---|
| 1 | 8.0 | 0.62 GB | 2.79 GB | 12.9 ms | 0.5 ms | 0 | 13.4 / 12.9 ms |
| 2 | 11.5 | 0.89 GB | 3.06 GB | 14.1 ms | 0.7 ms | 0.3 ms | 15.1 / 14.4 ms |
| 4 | 16.4 | 1.27 GB | 3.44 GB | 15.9 ms | 1.0 ms | 0.8 ms | 17.7 / 16.9 ms |
| 8 | 23.3 | 1.80 GB | 3.97 GB | 18.3 ms | 1.5 ms | 1.3 ms | 21.1 / 19.6 ms |

（未命中 H2D 按 2% 计算：k=8 时每 pass 约 38 MB，14.3 GB/s 下约 2.6 ms。上表用的是 1.5 ms，是按专家槽分批合并后的估计，需要 M1 验证。）

### 6.3 TG 与接受数 E（每 pass 接受的 token 数，含 bonus）

TG = E / 周期时间。取 k=8、周期 20-21 ms：

| E（每 pass 接受数） | TG（tok/s） |
|---|---|
| 3.0 | 143-150 |
| 4.0 | 190-200 |
| 4.5 | 214-225 |
| 5.0 | 238-250 |

（注：本表只算了验证 pass 和周期时间，没有计入草稿步的输出头代价，因此偏乐观。完整词表下的修正值见第 2.6 节。）

**达到 130 tok/s 所需的 E：** k=8 周期 21 ms 时 E ≥ 2.7；周期取第 2.6 节的修正值时，见第 2.6 节的下限。

### 6.4 PP 计算

- 每 token 6 GFLOP，1000 tok/s 要 6 TFLOPS 有效算力。
- RDNA2 FP32 峰值约 7.9 TFLOPS，实际能到 30-50%。纯 FP32/FP16 路径做不到。
- int8 点积（`V_DOT4_I32_I8`）路径的理论吞吐约为 FP32 的 2-4 倍。M2 必须用它。

### 6.5 能否达到 130 的结论（当前估计）

- 稠密地板 100 tok/s（单 token）是硬上限，只能靠推测摊销突破。
- 完整词表推测的理论 TG 约 125（第 2.6 节），略低于 130；受限词表有约 25–30% 的 E 余量，可达到 130。
- 这依赖三个未验证的前提：**(a) 局部性在更多文本类型上仍然成立；(b) 受限词表的 E 不低于第 2.6 节给出的下限；(c) 每 pass 的 Vulkan 提交与同步开销 < 1 ms。**
- 任何一条不成立，TG 会降到 110–125。

## 8. 测试与验收

### 8.1 正确性

- **参考对齐**：同一 prompt、同一 seed、greedy，输出 token 序列与 `llama-cli`（同模型）逐 token 一致。
- **logits 对齐**：完整词表 logits 与参考实现的 KL 散度 ≤ 1e-4（只在 k=1 路径上检查，推测路径上只检查接受的 token）。
- **重组校验**：重组文件的每个专家块与原 GGUF 的字节 SHA-256 一致。
- **接受回滚**：构造 k 个 token 中第 i 个不匹配的用例，检查 KV 与 DeltaNet 状态与串行解码一致。

### 8.2 性能

- 统一工况：10K prompt（`prompt10k.txt`，并增加一份非重复文本），ctx 256K，greedy，生成 128 token。
- 每个数字必须带口径：日期、提交号、电源态、显存预算、缓存大小、k、草稿词表大小。
- 报告：PP、TG、E（平均接受数）、接受率 p（分位置）、命中率、H2D 字节/token、显存峰值（每进程独占，`GPU Process Memory`）、内存峰值。

### 8.3 回归门禁

- 每个里程碑必须跑通第 8.1 节的正确性测试。
- 改动内核后跑 Vulkan 的 `test-backend-ops` 相应用例（`MUL_MAT`、`MUL_MAT_ID`、`FLASH_ATTN_EXT`），与 CPU 结果一致。

### 11.3 术语

- **稠密（dense）**：每个 token 都会全量读取的权重（attention/DeltaNet/输出头/共享专家）。
- **U_k**：连续 k 个 token 在一层中的唯一专家数。
- **E**：一个 pass 中平均接受的 token 数（含 bonus）。
- **p**：草稿每个位置的接受率（几何模型）。
- **MTP**：模型自带的多 token 预测层（`nextn_predict_layers`）。
