## 1. 目标与非目标

### 1.1 目标

| 指标 | 目标 | 口径 |
|---|---|---|
| Prefill（PP） | ≥ 1000 tok/s | 10K prompt，ctx 256K，batch 512 |
| Decode（TG） | ≥ 130 tok/s | 单流，greedy，10K prompt 之后的 128 token（2026-10-24 决定由 200 下调到 130） |

TG 目标不调整。达成条件依赖第 6 节的推测解码与命中率假设，M1 需要验证。

### 1.2 非目标

- 不改变权重的量化格式（Q4_K / Q5_K / Q6_K / Q8_0 保持原样）。
- 不改变模型输出（greedy 下与参考实现 bit-level 或 KLD=0 对齐；允许在推测解码中因浮点归约顺序产生的微小差异，需量化上报）。
- 不支持其他模型、其他量化、其他后端（CUDA/Metal 不考虑）。
- 不做多用户服务化调度；单进程、单会话为主，多会话仅作为后续扩展。

### 1.3 硬约束（来自 M0/M1 实测，不随设计变化）

- 每个 token 的稠密权重（output 头 + attention/DeltaNet + 共享专家）必须读一遍：约 **2.17 GB**。
- 显存读带宽上限 **156 GB/s**（M1-5 大缓冲区实测 154.9-156.5，`RESULTS.md` 第 8 节）。v0.1 的 217 GB/s
  来自 14 MiB 工作集命中 Infinity Cache，已作废。
- 单流 TG 的稠密部分上限：2.17 GB / 156 GB/s ≈ 13.9 ms → **≤72 tok/s**。这不是运行时能绕过的，
  必须靠"一次读取摊到多个 token 上"。
- H2D 单向 **14.17 GB/s**（M1-5，`RESULTS.md` 第 8 节）；CPU 4 线程读 **39.2-40.8 GB/s**（同处）。
- 解码 miss 率 18-23%（25-30% 显存专家缓存下，`RESULTS.md` 第 7 节）；H2D 与 CPU 两条路径
  **共用主机内存带宽**，并发时的聚合率未测（M1-7）。

## 2. M0 实测结论

### 2.1 张量账（M0-1，本轮从 GGUF 直接统计）

| 类别 | 大小 | 每个 token 读取 |
|---|---|---|
| routed_experts（Q4_K 11520 块、Q5_K 7040 块、Q6_K 630 块） | 18.74 GiB | 只读 top-8 |
| dense_other（attention / DeltaNet / 路由器 / 归一化） | 1.39 GiB | 全量 |
| output 头（Q8_0） | 0.50 GiB | 全量 |
| shared_expert（Q8_0） | 0.13 GiB | 全量 |
| token_embd（Q8_0） | 0.50 GiB | 否（只查一行） |
| nextn（MTP 块，Q8_0） | 8 MiB | 草稿时读取 |

- 层数：40 个主层 + 1 个 MTP 层（`nextn_predict_layers=1`）。
- 专家数 256，top-8，专家 FFN 维 512，hidden 2048。
- 每个专家约 **1.84 MiB**（按 41×256 个专家摊平）。
- 稠密每 token 读取：2.02 GiB ≈ **2.17 GB**。
- 专家每 token 读取：8 × 40 × 1.84 MiB ≈ **0.62 GB**。

### 2.2 路由 trace（M1-1 修复后，40 层 x 128 token）

数据：`bench/raw/m0-qwen36/trace-10k-g128.bin`（r=2 逐字节一致），分析：`bench/tools/m0-analyze.py`，
输出 `m1-analyze-vram156.txt`。口径见 `RESULTS.md` 第 7 节。**v0.1 的 56.8% / 23.3 / 97.9% 全部作废**：
那次 trace 的 cb_eval 回调返回 `false`，调度器据此跳过当前 split 的余下节点，前向是残缺的。

**局部性（解码，40 层）**

| 指标 | 数值 |
|---|---|
| 与上一 token 同专家的比例 reuse(t-1) | 41.8% |
| 连续 w 个解码 token 的唯一专家数/层：w=1 / 2 / 4 / 5 / 8 / 9 | 8.0 / 12.7 / 19.9 / 23.5 / 31.6 / 33.9 |
| 同口径随机路由期望：w=4 / 8 | 30.6 / 57.4 |

**命中率（全局 LRU，prefill 预热，40 层共 10240 槽；与 k 无关）**

| 缓存占比 | 容量 | 解码命中 |
|---|---|---|
| 20% | 3.76 GiB | 77.3% |
| 25% | 4.70 GiB | 81.6% |
| 30% | 5.64 GiB | 85.4% |

对照：静态 top-N（按 prefill 频次固定）在 25% 只有 60.7%，低于动态 LRU。**结论不变：命中来自时间局部性，
静态驻留不可取。**

**冷启动对照**：prefill 本身用 LRU（不预热）在 10% 时 59.2%，20% 时 75.4%。

### 2.3 M0/M1 的不足（必须写清楚）

1. ~~解码阶段 trace 有缺口~~ **已闭环（M1-1）**：根因是 cb_eval post-compute 回调返回 `false` 会让
   调度器跳过后余节点（`ggml-backend.cpp:2118`）。现在 40 层 x 128 token 齐全，layer 39 的解码段
   是"末尾 128 条"，其 prefill 段只保留 21 行（最后一层输出被裁剪）。
2. **解码 token 有局部循环**：128 个解码 token 的唯一值 89（README）/ 92（多文档），会略微抬高命中率。
3. **只有技术类文本**：两份 prompt 的唯一词比例都在 0.4 左右；对话、代码、多语言未测（M1-2b）。
4. **MTP 接受率只测了完整词表**：E 为 2.84-3.82；受限词表下的 E 未测（M1-3b）。
5. **两条 miss 路径的并发聚合率未测**：H2D 与 CPU 读共用主机内存（M1-7）。第 6 节的"各半"投影
   建立在这个未知量上。

### 2.6 周期模型（M1-5 带宽复测后重算）

v0.1 的所有投影按 217 GB/s 与 2% miss 计算，两项都被 M1 推翻，本节取代它们。
一个 pass 里有三条并行的工作流：

| 工作流 | 介质 | 每 pass 的量 | 速率 |
|---|---|---|---|
| GPU 读命中专家 + 稠密 | 显存 | 2.17 GB + 命中专家 | 156 GB/s |
| miss 走 H2D | PCIe | miss 字节 | **8.9-11.2 GB/s（争用时）**，单跑 14.17 |
| miss 走 CPU | 主机内存 + 4 线程 | miss 个数 | **0.123-0.137 ms/专家** |
| 草稿 | 显存（受限词表） | (k-1) × 33 MB | 156 GB/s |

周期 = max(三条腿) + 草稿。miss 的分配是运行时决策，目标是让三条腿耗时相等（`QRT_MISS_SPLIT=auto`）；
固定比例在 H2D 掉速时会失衡。两条腿争用的实测量见 `RESULTS.md` 第 9 节：H2D 掉约 27%，
聚合为单跑之和的 74-83%，因此不能把单跑速率相加。

| 缓存 | k | E | GPU 读 ms | miss 数/pass | 最优分配 | miss ms | 周期 ms | TG |
|---|---:|---:|---:|---:|---|---:|---:|---:|
| 25% | 4 | 2.84 | 20.4 | 235.2 | 97 / 138 | 18.9 | 21.0 | **135** |
| 25% | 5 | 3.24 | 21.3 | 294.6 | 122 / 173 | 23.7 | 24.3 | **133** |
| 30% | 4 | 2.84 | 21.0 | 187.5 | 77 / 110 | 15.1 | 21.5 | **132** |
| 30% | 5 | 3.24 | 22.1 | 234.7 | 97 / 138 | 18.9 | 22.7 | **143** |

- 数据来源：`RESULTS.md` 第 8、9 节。E 与 k 成对：E=2.84 对应约 2.9 草稿/周期（验证宽度约 4）。
- **只走 H2D 一律不达标（82-113）**，这是 v0.1 第 4.7 节的模型，已废弃。
- 分担后 132-143，余量只有 1-10%。且 **GPU 读自身（20-22 ms）已是并列瓶颈**，miss 怎么分都压不到它以下。
- 全部为投影（三条腿的速率是实测量，分配与重叠是算术）。M1-4b 用真实 Vulkan 路径复核。

## 3. 概要设计

### 3.1 核心思路

既然稠密权重每 token 必读一遍（13.9 ms 下限，→72 tok/s），单流 TG 的唯一出路是
**一次前向处理多个 token**，把稠密读取和专家读取摊销到 k 个 token 上。M1 的局部性数据表明：
连续 8 个 token 只需 31.6 个唯一专家/层（随机是 57.4），这让多 token 验证的专家读取也能摊销。

因此运行时的主路径是：

**原生 MTP 草稿 + 整模型 k=4~5 批量验证 + 显存专家 LRU 缓存 + miss 由 H2D 与 CPU 分担
+ 单次提交的每 pass 命令缓冲。**

k 取 4-5 而不是 8，原因是 GPU 读本身已是并列瓶颈（第 2.6 节）：更大的 k 只增加唯一专家数
（U_8=31.6 对 U_5=23.5），换来的 E 增益（3.82 对 3.24）抵不过读数增长。

### 3.2 组件

```
            +-----------------------------+
 prompt --> |  Prefill 引擎（层优先分块）   |--> KV / DeltaNet 状态
            +-----------------------------+
                          |
            +-----------------------------+
            |  Decode 引擎（推测循环）       |
            |   - MTP 草稿（默认完整词表）    |
            |   - 验证 pass（k = 4-5）       |
            |   - 接受/回滚                 |
            +-----------------------------+
                 |          |          |
     +-----------------+  |  +------------------------+
     | 稠密权重（VRAM 常驻） |  | 专家存储（RAM 全量，重组布局） |
     |  2.02 GiB         |  |  18.74 GiB            |
     +-----------------+  |  +------------------------+
                 |          |          |
     +-----------------------+  +-----------------------+
     | 显存专家缓存 4.7-5.6 GiB |  | miss: H2D 或 CPU 计算  |
     | SLRU，25-30% 覆盖        |  | 按耗时均衡分配         |
     +-----------------------+  +-----------------------+
                 |
     +---------------------------------------+
     | Vulkan 内核集（GEMV / GEMM / 路由 / 注意力）|
     +---------------------------------------+
```

### 3.3 与现有 fork 的关系

- 本设计**不复用**通用 `llama_context` 图路径作为 decode 主路径（它每 token 约 4000 个节点，每层有多次 dispatch）。
  注意：v0.1 曾以"MoE 节点在解码时有缺口"作为理由，该缺口已查明是 bench 工具的 cb_eval 用法问题
  （M1-1），**不是 fork 的缺陷**，理由据此修正。
- 复用：GGUF 解析（`gguf-py` 或等价的 C++ 读取）、Vulkan 设备初始化、tokenizer、Q4_K/Q5_K/Q6_K/Q8_0 的反量化与块格式定义（`ggml-common.h`）。
- 复用但需要改造：`ggml-vulkan` 中的 `mul_mat_vec`、`mul_mat_id` 内核（改为批量 k 版本）。
- 不复用：`llama-moe-cache` 的调度与预取（M0 显示静态驻留不如动态 LRU；且它的预取依赖旧的图）。

## 4. 关键技术

### 4.1 原生 MTP 推测解码

- 模型自带 1 个 MTP 层（`blk.40`），共享 output 头与 token_embd。
- 草稿循环：用 MTP 层预测后续 k-1 个 token。每步的 MTP 块只有 8 MiB，成本可忽略。
- **关键问题**：每步草稿要读一次 output 头（Q8_0，0.50 GiB）。按 156 GB/s 是 3.2 ms/步，
  3 步就是约 10 ms，与整个验证 pass（20 ms）同量级。
- **基线：完整词表草稿**。草稿步和验证 pass 都用完整词表，零模型改动，接受的 token 与纯 greedy 完全相同。
  代价是每草稿步 3.2 ms。按第 2.6 节，k=5 时周期 22.1 + 4×3.2 ≈ 35 ms -> E=3.24 -> 约 93。
- **受限词表草稿**（例如按训练频次选出的 16K 候选）是达到 130 的必要手段，不是可选优化：
  草稿步的输出头读取降到约 33 MB/步（约 0.2 ms），第 2.6 节的 133-148 全部建立在这一点上。
  代价是接受率未知下降，M1-3b 必须测：E 不低于 2.1（k=4）或 2.3（k=5）即通过。
- 正确性由验证 pass 保证：验证始终使用**完整词表**，无论草稿是否受限，接受的 token 都与纯 greedy 一致。
  受限词表只影响接受率和速度，不影响输出。

### 4.2 批量验证 pass（k = 4-5）

- 一次前向处理 k 个 token（位置连续），稠密权重只读一次。
- 每层的专家路由是 k 个 token 的并集：U_4=19.9、U_5=23.5、U_8=31.6（第 2.2 节实测）。
- DeltaNet 层需要支持 k 个 token 的串行状态更新（递推本身是串行的，但权重读取可以共享）；
  full-attention 层需要 k 个 query 对同一段 KV 的注意力（KV 只读一次）。
- 固定形状：k ∈ {1, 2, 4, 5} 四种形状，各自预录命令缓冲，避免每 token 重建图。
  k=8 一并实现但默认关闭（第 2.6 节显示它在 GPU 读上更贵）。

### 4.3 显存专家缓存

- 容量：4.70-5.64 GiB（25-30% 覆盖，约 2500-3000 槽）。命中率 81.6-85.4%（M1 实测）。
  v0.1 的"3.5 GiB 命中 97.4%"来自作废的 trace，已改。
- 替换策略：按层的 SLRU（probation / protected 两段），不用静态驻留。
- 缓存槽：每个槽 1.84 MiB，按专家整块存放，与重组后的 RAM 布局一一对应。
- 未命中：**两条路径分担**（第 4.7 节）。k=5 / 25% 缓存时 miss 294.6 个/pass（0.56 GB）；
  H2D 全速 38.8 ms、CPU 全速 31.8 ms，各分担一半后每条约 16-19 ms，与 GPU 读的 21.3 ms 同量级。
  分配由 `QRT_MISS_SPLIT` 控制，目标是三条腿耗时相等，不是固定 50/50。

### 4.4 文件重组（允许）

- 按 `[层][专家]` 连续存放 gate/up/down 三块，每个专家 1.84 MiB 对齐到 2 MiB 边界（或 64 KiB 对齐，取决于 H2D 块大小测量结果）。
- 按 10K 统计的使用频次（LRU 用不到，但用于初始化预热和分析）写入 sidecar 索引。
- 重组前后权重字节一致（逐块校验），不修改任何量化值。
- 仅重排，不转换格式。

### 4.5 Prefill（PP）

- 层优先分块：chunk = 512 token；每层的专家只读一次，用双缓冲从 RAM 上传。
- 计算量约 6 GFLOP/token，1000 tok/s 需要约 6 TFLOPS 有效算力，超过 RDNA2 FP32 实际能力，**必须用 int8 点积**（`V_DOT4_I32_I8`）的 Q4_K × Q8_1 GEMM。
- 每层上传约 470 MB，在 14.17 GB/s 下约 33 ms；每层计算约 100 ms（2048 token），传输被计算覆盖。
- 注意力：DeltaNet 层为线性复杂度；full-attention 层的 10K 注意力计算占比低。

### 4.6 每 pass 的执行模型

- 每个 pass 一个命令缓冲，层间只用 barrier，不回到 CPU。
- 采样在 GPU 上做 greedy（argmax 或 top-1 候选），只回传 k 个 token id。
- 接受判定在 CPU 上做（k 个 int32，比较即可）。
- 同步次数：每 pass 1 次等待 GPU + 1 次等待 CPU 腿（两条腿在 pass 末尾汇合），而不是每层一次。

### 4.7 CPU 角色

用户 2026-10-24 决定：**decode 的 miss 专家由 H2D 与 CPU 分担**。这条取代 v0.1 的"CPU 不参与 decode"。

- CPU 计算未命中专家：直接读 RAM 中的原权重，不经过 PCIe，也不写显存。
- 与 GPU 并行：GPU 同时算命中专家与稠密部分，两条腿在层边界汇合（每层一次 light fence）。
- 代价模型：**0.123-0.137 ms/专家（4 线程，M1-7 实测）**；按 40 GB/s 与 1.93 MiB/专家理论上限约
  0.048 ms，现读数差 2.6-2.9 倍，是 M3 内可挖的余量，但当前投影已按 0.137 计算。
- **已测（M1-7）**：H2D 与 CPU 读并发时，H2D 掉到 8.9-11.2 GB/s（单跑 14.17，约 -27%），
  聚合 33.5-41.0 GB/s（单跑之和的 74-83%）。因此分配不能用固定比例，必须自适应；
  据此重算的周期见第 2.6 节，TG 132-143。
- CPU 还负责：分词、接受判定、调度、MTP 草稿的候选词表选择。

## 5. 核心实现

### 5.1 模块划分

| 模块 | 职责 | 输入 | 输出 |
|---|---|---|---|
| `gguf_index` | 读取 GGUF，建立张量表与字节偏移 | GGUF 路径 | 张量描述符 |
| `repack` | 生成重组文件（专家连续、对齐） | 原 GGUF | `*.qwen36rt.bin` + 索引 |
| `vk_dev` | Vulkan 设备、队列、内存分配（显存预算） | 设备参数 | 设备句柄、分配器 |
| `weights` | 稠密权重常驻显存；专家存储映射 | 重组文件 | 稠密缓冲、专家页表 |
| `expert_cache` | 显存专家槽、SLRU、命中/未命中判定 | 路由 id 列表 | 命中/未命中、槽号 |
| `miss_split` | 把 miss 分给 H2D 与 CPU，使三条腿耗时相等 | miss 列表、两腿当前速率 | 两段 miss 列表 |
| `cpu_moe` | 在 CPU 上与 GPU 并行计算分到的 miss 专家 | miss 列表、激活值 | 部分输出 |
| `kernels` | 批量 GEMV/GEMM、路由 top-8、注意力、DeltaNet | 张量 | 张量 |
| `pass` | 构建并提交一个 pass 的命令缓冲（按 k 预录） | k、位置、KV 句柄 | token ids |
| `spec` | MTP 草稿、受限词表、接受/回滚 | 上下文、草稿 logits | 接受 token 序列 |
| `prefill` | 层优先分块的 prefill | prompt | KV 与 DeltaNet 状态 |
| `telemetry` | 命中率、H2D 字节、每 pass 耗时、接受率 | 每 pass 事件 | CSV/JSON |

### 5.2 数据结构（草案）

```c++
struct ExpertKey { uint16_t layer; uint16_t expert; };   // 40/41 层 × 256
struct ExpertSlot { int32_t slot; uint32_t gen; };        // 显存槽号与代数
struct ExpertPageTable {                                  // 静态表，启动时生成
    uint64_t host_offset[41][256];                        // 重组文件内偏移
    ExpertSlot cache[41][256];                            // 当前驻留槽（-1 表示未驻留）
};
struct PassPlan {
    uint32_t k;                                           // 1/2/4/8
    int32_t  pos0;                                        // 起始位置
    uint32_t route_ids[41][8][8];                         // 每层每 token 的 top-8（GPU 写，CPU 读取）
};
```

### 5.3 pass 流程（伪代码）

```
pass_step(k, tokens):
  upload tokens and pos
  for layer in 0..39:
    attn_or_deltanet(layer, k)            # 稠密读取，一次
    router(layer, k) -> route_ids         # top-8，GPU 上
    cache_lookup(layer, route_ids)        # GPU 上查表，输出 hit/miss mask
    split = plan_split(miss_ids)          # 按三条腿耗时相等切分（QRT_MISS_SPLIT）
    enqueue_h2d(split.h2d_part)           # 异步，与计算重叠
    launch_cpu_moe(split.cpu_part)        # CPU 线程直接读 RAM 算，不占 PCIe
    moe_compute(layer, k, hits, h2d_slots)  # 命中 + 等到位的 H2D 部分
  output_head(k)                          # 完整词表，argmax
  submit(); wait_cpu_leg(); read(k ids, route stats)
```

### 5.4 接受与回滚

```
draft = mtp_draft(ctx, k-1)            # 受限词表
verified = pass(k, [last] + draft)     # 完整词表
accept = longest prefix where draft[i] == verified[i]
ctx.append(accept) + verified[len(accept)]   # 第一个不匹配处用验证结果
rollback KV/DeltaNet state to accept length  # DeltaNet 需要保存 k 个中间状态
```

- DeltaNet 回滚：在 pass 内保存每个 token 之后的递推状态（k 份，状态很小）；接受后只保留需要的那一份。
- full-attention 层的 KV：按位置写入，回滚只需移动长度指针。

### 5.5 显存预算（8176 MiB 设备）

| 项目 | MiB | 备注 |
|---|---|---|
| 桌面占用 | 500-1400 | 运行时无法控制，取中值约 1000 |
| 稠密权重 | 2068 | 2.02 GiB |
| 专家缓存 | 4813-5776 | 25-30% 覆盖，4.70-5.64 GiB（第 2.2 节命中率的前提） |
| KV（full-attention，256K） | 待测 | 取决于 full-attention 层数（M1-6） |
| 计算缓冲（k=5） | 约 700-1100 | 参考 M0 的 Vulkan compute buffer（k=8 时 1016 MiB） |
| 草稿与其他 | 约 100 | 受限词表 logits、MTP 块 |
| 合计（不含 KV） | 约 8700-10000 | **明显超出** 8176 - 1000 = 7176 |

**结论：25-30% 专家缓存与 8 GiB 显存不能同时成立。** 三个可动的方向，都需要实测才能定：

1. 缓存降到 20%（3.76 GiB，命中 77.3%）：miss 涨到 290.8 个/pass，周期估 24-27 ms，TG 约 105-120。
2. 压低计算缓冲：k=5 且精简中间张量，目标 600 MiB 以内；仍需 KV 数字（M1-6）。
3. 提高单条 miss 腿的效率，让更小的缓存也能撑住（N9 的每专家代价从 0.108 降到 0.06 即为 1.8 倍）。

这一项必须在 M1-GATE 前用 M1-6 的 KV 数字与 M1-4b 的计算缓冲实测定稿。

## 6. 性能模型

### 6.1 单 pass 字节账（k 个 token）

- 稠密：2.17 GB（每 pass 一次，来自显存）。
- 专家（VRAM 读取）：命中数 × 1.93 MB，命中数 = U_k × 40 − miss。
- 未命中：miss × 1.93 MB，由 H2D 与 CPU 分担（U_k 与 miss 见第 2.2 节实测）。
- 草稿（k-1 步）：受限词表时约 33 MB/步，完整词表时 0.5 GB/步。

### 6.2 三条腿的耗时（表见第 2.6 节）

| 腿 | 公式 | 速率来源 |
|---|---|---|
| GPU | (2.17 GB + 命中 × 1.93 MB) / 156 GB/s | M1-5 大缓冲区实测 |
| H2D | miss × 1.93 MB / 9.9 GB/s | M1-7 争用下沿（单跑 14.17） |
| CPU | miss × 0.137 ms | M1-7 4 线程上沿 |

周期 = max(三条腿) + 草稿 + 每 pass 提交与同步开销（要求 < 1 ms，M1-4b 测）。
v0.1 的 6.2 表（217 GB/s、2% miss、只走 H2D）已作废。

### 6.3 TG 与接受数 E（每 pass 接受的 token 数，含 bonus）

TG = E / 周期。按第 2.6 节的周期：

| 配置 | 周期 | E（已测） | TG |
|---|---:|---:|---:|
| k=4，25% 缓存 | 21.0 ms | 2.84 | 135 |
| k=5，25% 缓存 | 24.3 ms | 3.24 | 133 |
| k=4，30% 缓存 | 21.5 ms | 2.84 | 132 |
| k=5，30% 缓存 | 22.7 ms | 3.24 | 143 |

**达到 130 所需的 E**：k=5 / 25% 缓存需 E ≥ 3.16；已测 3.24，余量只有 2.5%。
k=4 / 25% 需 E ≥ 2.73；已测 2.84，余量 4%。**四个组合的余量都在 2-10% 之间，没有一个宽松。**

### 6.4 PP 计算

- 每 token 6 GFLOP，1000 tok/s 要 6 TFLOPS 有效算力。
- RDNA2 FP32 峰值约 7.9 TFLOPS，实际能到 30-50%。纯 FP32/FP16 路径做不到。
- int8 点积（`V_DOT4_I32_I8`）路径的理论吞吐约为 FP32 的 2-4 倍。M2 必须用它。

### 6.5 能否达到 130 的结论（当前估计）

- 稠密地板 72 tok/s（单 token，156 GB/s）是硬上限，只能靠推测摊销突破。
- 三条腿模型（两条 miss 腿的速率已实测）投影 132-143，**余量只有 1-10%**，依赖四个前提：
  **(a) 受限词表的 E 达到 3.16（k=5）或 2.73（k=4）；(b) miss 分配自适应且重叠良好；
  (c) 每 pass 提交与同步开销 < 1 ms（M1-4b）；(d) 25-30% 专家缓存能塞进 8 GiB（第 5.5 节，当前不成立）。**
- 其中 (d) 最硬：显存预算合计约 8700-10000 MiB，超出可用 7176 MiB。若缓存只能给到 20%，
  投影降到 105-120，达不到 130。
- 因此 **TG 130 的可达性目前是"有条件"，不是"已确认"**：需要 M1-3b（受限词表 E）、M1-4b（周期）、
  M1-6（KV 预算）三项，再回用户处评审。

### 11.3 术语

- **稠密（dense）**：每个 token 都会全量读取的权重（attention/DeltaNet/输出头/共享专家）。
- **U_k**：连续 k 个 token 在一层中的唯一专家数。
- **E**：一个 pass 中平均接受的 token 数（含 bonus）。
- **p**：草稿每个位置的接受率（几何模型）。
- **MTP**：模型自带的多 token 预测层（`nextn_predict_layers`）。
