## 1. 目标与非目标

### 1.1 目标

| 指标 | 目标 | 口径 |
|---|---|---|
| Prefill（PP） | ≥ 1000 tok/s | 10K prompt，ctx 256K，batch 512 |
| Decode（TG） | ≥ 130 tok/s | 单流，greedy，10K prompt 之后的 128 token（2026-10-24 决定由 200 下调到 130） |

TG 目标不调整。达成条件依赖第 6 节的推测解码与命中率假设，M1 需要验证。

目标值由硬件 roofline 推算（R0/R1a/R1b/R1c，`bench/RESULTS.md` 第 12-14 节）：

- **TG**：显存读上限 156.5 GB/s（规格 224 不可达），可行点 21.9% 缓存、**k=4**；实测受限 16K
  E=2.850（RESULTS 19），CPU 专家核 0.118 时 E_min 2.90、0.090 时 2.72，即 CPU 约 **0.10 ms/专家**
  时到 130。**k=5 的 E=3.055 只作速度上限**：它在 greedy margin 0.1192 处翻转，按 U-7 不是
  验收配置（RESULTS 21/23）。130 是硬地板，CPU 核优化是前提。
  以上是技术/对话文本；**U-5（用户 2026-10-24）把 code 也纳入 130**。code 在 21.9% 缓存下
  命中 66.0%，要 130 需 CPU 专家核 **<=0.059 ms**（约 107 GFLOPS，目标 0.055）+ H2D 10.8；
  当前 0.118 -> 82、0.090 -> 97。M3-1a 必须交付 0.059（当前专用核 0.079-0.082，RESULTS 20/22）。
- **PP**：专家形状 Q4_K GEMM 实测 **3.66 TFLOPS**，PP 约 **610**；1000 需要 **6.0**（1.64x），
  是 M2-4 的硬交付项，不是硬件墙（ALU 上限 8.67、dense 大 K 5.95）。**PP >= 1000 由用户
  2026-10-24 定为硬目标，不下调。**
- 每轮同时报实测 roofline 与差距分解，不用"当前实现就这样"当结论。
每轮报告两个数，差距按腿分解成优化项，不用"当前实现就这样"当结论。

### 1.2 非目标

- 不改变权重的量化格式（Q4_K / Q5_K / Q6_K / Q8_0 保持原样）。
- 不改变模型输出（greedy 下与参考实现 bit-level 或 KLD=0 对齐；允许在推测解码中因浮点归约顺序产生的微小差异，需量化上报）。
- 不支持其他模型、其他量化、其他后端（CUDA/Metal 不考虑）。
- 不做多用户服务化调度；单进程、单会话为主，多会话仅作为后续扩展。

### 1.3 硬件上限与当前软件（必须分开）

**规格 / 链路极限（不可越）**

- GDDR6 **224 GB/s**（128-bit x 14 Gbps）；PCIe 4.0 x8 **15.75 GB/s**；DDR5-4800 双通道 **76.8 GB/s**；
  RDNA2 FP32 **7.9 TFLOPS**；设备显存 8176 MiB。
- 稠密权重每 token 必读 2.17 GB。单 token 前向上限 = 2.17 GB / 带宽：224 下 103 tok/s，156.5 下 72。
  突破仍只能靠一次前向摊多个 token。
- 不改变量化格式；不改变输出（k=1 KLD <= 1e-4，推测路径接受 token 与参考 greedy 一致）。
- **算术上限按指令类别算，不能只写 FP32 一个数**（用户 2026-10-25 授权补入）：FP32 FMA 7.9 TFLOPS；
  `V_DOT4_I32_I8` 每条指令 4 次乘加，等价算术上限约为 FP32 的 2-4 倍。实测稠密 q8_0 稠密 GEMM
  已到 **12.89 TFLOPS**（N=8192/K=2048/M=10240）、**14.81**（k=4096），见 RESULTS 第 55 节。
  因此"0.85 x roofline"必须按该腿实际使用的指令类别取值：稠密投影与专家 GEMM 用 int8 点积，
  其余（注意力、归一化、DeltaNet 递推）用 FP32。
- **int8 腿的 roofline 取 2 倍，不取 4 倍**（用户 2026-10-25 定，DECISIONS 68）：
  RDNA2 的 `V_DOT4_I32_I8` 吞吐是 FP32 的 **2 倍**（4 倍是 RDNA3 的规格），故
  int8 roofline = 7.9 x 2 = **15.8 TOPS**，0.85 x 它 = **13.4 TOPS**；FP32 腿仍 7.9（0.85 x = 6.7）。
  实测与 2 倍口径一致：稠密 14.81 是 15.8 的 93.7%、12.89 是 81.6%（RESULTS 55），
  Q4_K 专家 7.09 是 44.9%（RESULTS 44，解包开销）。按 4 倍（31.6）算则实测只到 47% / 22%，
  与"内核已接近可优化上限"的判断矛盾。**跨类别不可比。**

**当前软件读数（优化目标，不是约束）**

- 显存读 156.5 GB/s = 规格的 **70%**（M1-5，大缓冲区）。
- CPU 4 线程读 39-41 GB/s = 规格的 **52%**；8 线程反而更慢，说明瓶颈在探针。
- H2D 单跑 14.17（链路的 90%，已近极限）；与 CPU 读并发掉到 8.9-11.2（M1-7）。
- CPU 每专家 0.115-0.118 ms（R1b，4 线程，55-61 GFLOPS、16.6 GB/s）；需求是 <= 0.090，0.048 只是带宽口径。
- 解码 miss 率 18-23%（20-30% 缓存，M1-7）。
- R1 负责逐条逼近：显存 190、并发 H2D 12.5、CPU 0.070、int8 GEMM 7 TFLOPS。

### 2.1 张量账（M0-1，本轮从 GGUF 直接统计）

| 类别 | 大小 | 每个 token 读取 |

- 层数：40 个主层 + 1 个 MTP 层（`nextn_predict_layers=1`）。
- 专家数 256，top-8，专家 FFN 维 512，hidden 2048。
- 每个专家约 **1.84 MiB**（按 41×256 个专家摊平，摊平值 1 917 128 B）。
  **实际尺寸按层不同**：38 层 1 812 MiB / 层 34、38 是 1.945 MiB / 层 39 是 2.195 MiB（RESULTS 第 35 节），
  槽与上传缓冲一律按**该层实际字节**取，不按摊平值。
- 三种尺寸的成因是**量化类型按层混用**（RESULTS 第 39、40 节）：多数层 gate/up 是 Q4_K、down 是 Q5_K；
  层 34/38 的 down 是 Q6_K；层 39 的 gate/up 是 Q5_K、down 是 Q6_K。
  因此 int8 GEMM 需要 **Q4_K / Q5_K / Q6_K 三个变体**，三个都已在运行时落地并按矩阵字节数自动判定类型。
- 稠密每 token 读取：2.02 GiB ≈ **2.17 GB**。
- 专家每 token 读取：8 × 40 × 1.84 MiB ≈ **0.62 GB**（按摊平值，实际 0.62-0.68 GB）。

### 2.6 周期模型（M1-5 带宽复测后重算）

v0.1 的所有投影按 217 GB/s 与 2% miss 计算，两项都被 M1 推翻，本节取代它们。
一个 pass 里有三条并行的工作流：

| 工作流 | 介质 | 每 pass 的量 | 速率 |
|---|---|---|---|
| GPU 读命中专家 + 稠密 | 显存 | 2.17 GB + 命中专家 | 156 GB/s |
| miss 走 H2D | PCIe | miss 字节 | **8.9-11.2 GB/s（争用时）**，单跑 14.17 |
| miss 走 CPU | 主机内存 + 4 线程 | miss 个数 | **0.115-0.118 ms/专家（R1b）** |
| 草稿 | 显存（受限词表） | (k-1) × 33 MB | 156 GB/s |

聚合为单跑之和的 74-83%，因此不能把单跑速率相加。

## 3. 概要设计

### 3.1 核心思路

既然稠密权重每 token 必读一遍（13.9 ms 下限，→72 tok/s），单流 TG 的唯一出路是
**一次前向处理多个 token**，把稠密读取和专家读取摊销到 k 个 token 上。M1 的局部性数据表明：
连续 8 个 token 只需 31.6 个唯一专家/层（随机是 57.4），这让多 token 验证的专家读取也能摊销。

因此运行时的主路径是：

**原生 MTP 草稿 + 整模型 k=4 批量验证（k=5 仅探索）+ 显存专家 LRU 缓存 + miss 由 H2D 与 CPU 分担
+ 单次提交的每 pass 命令缓冲。**

k 默认 4 而不是 5 或 8：k=5 会把近分叉翻过去（U-7 / R9），k=8 只增加唯一专家数
（U_8=31.6 对 U_5=23.5），换来的 E 增益（3.82 对 3.05）抵不过读数增长。

### 3.2 组件

```
            +-----------------------------+
 prompt --> |  Prefill 引擎（层优先分块）   |--> KV / DeltaNet 状态
            +-----------------------------+
                          |
            +-----------------------------+
            |  Decode 引擎（推测循环）       |
            |   - MTP 草稿（默认完整词表）    |
            |   - 验证 pass（k = 4-5）       |
            |   - 接受/回滚                 |
            +-----------------------------+
                 |          |          |
     +-----------------+  |  +------------------------+
     | 稠密权重（VRAM 常驻） |  | 专家存储（RAM 全量，重组布局） |
     |  2.02 GiB         |  |  18.74 GiB            |
     +-----------------+  |  +------------------------+
                 |          |          |
     +-----------------------+  +-----------------------+
     | 显存专家缓存 4.1 GiB   |  | miss: H2D 或 CPU 计算  |
     | SLRU，21.9% 覆盖         |  | 按耗时均衡分配         |
     +-----------------------+  +-----------------------+
                 |
     +---------------------------------------+
     | Vulkan 内核集（GEMV / GEMM / 路由 / 注意力）|
     +---------------------------------------+
```

### 3.3 与现有 fork 的关系

- 本设计**不复用**通用 `llama_context` 图路径作为 decode 主路径（它每 token 约 4000 个节点，每层有多次 dispatch）。
  注意：v0.1 曾以"MoE 节点在解码时有缺口"作为理由，该缺口已查明是 bench 工具的 cb_eval 用法问题
  （M1-1），**不是 fork 的缺陷**，理由据此修正。
- 复用：GGUF 解析（`gguf-py` 或等价的 C++ 读取）、Vulkan 设备初始化、tokenizer、Q4_K/Q5_K/Q6_K/Q8_0 的反量化与块格式定义（`ggml-common.h`）。
- 复用但需要改造：`ggml-vulkan` 中的 `mul_mat_vec`、`mul_mat_id` 内核（改为批量 k 版本）。
- 不复用：`llama-moe-cache` 的调度与预取（M0 显示静态驻留不如动态 LRU；且它的预取依赖旧的图）。

## 4. 关键技术

### 4.1 原生 MTP 推测解码

- 模型自带 1 个 MTP 层（`blk.40`），共享 output 头与 token_embd。
- 草稿循环：用 MTP 层预测后续 k-1 个 token。每步的 MTP 块只有 8 MiB，成本可忽略。
- **关键问题**：每步草稿要读一次 output 头（Q8_0，0.50 GiB）。按 156 GB/s 是 3.2 ms/步，
  3 步就是约 10 ms，与整个验证 pass（20 ms）同量级。
- **基线：完整词表草稿**。草稿步和验证 pass 都用完整词表，零模型改动，接受的 token 与纯 greedy 完全相同。
  代价是每草稿步 3.2 ms。按第 2.6 节，k=4 时周期 21.0 + 3×3.2 ≈ 30.6 ms -> E=2.84 -> 约 93。
- **受限词表草稿**（例如按训练频次选出的 16K 候选）是达到 130 的必要手段，不是可选优化：
  草稿步的输出头读取降到约 33 MB/步（约 0.2 ms），第 2.6 节的 132-143 全部建立在这一点上。
  代价是接受率下降，M1-3b 已测：16K 在 k=4 是 **2.850**、k=5 是 3.055（RESULTS 19）。
  **验收用 k=4**（门槛 2.90 / 2.72，见 6.3）；k=5 只作速度探索。
- 正确性由验证 pass 保证：验证始终使用**完整词表**，无论草稿是否受限，接受的 token 都与纯 greedy 一致。
  受限词表只影响接受率和速度，不影响输出。

### 4.2 批量验证 pass（k = 4-5）

- 一次前向处理 k 个 token（位置连续），稠密权重只读一次。
- 每层的专家路由是 k 个 token 的并集：U_4=19.9、U_5=23.5、U_8=31.6（第 2.2 节实测）。
- DeltaNet 层需要支持 k 个 token 的串行状态更新（递推本身是串行的，但权重读取可以共享）；
  full-attention 层需要 k 个 query 对同一段 KV 的注意力（KV 只读一次）。
- 固定形状：k ∈ {1, 2, 4, 5} 四种形状，各自预录命令缓冲，避免每 token 重建图。**默认 k=4**；
  k=5 与 k=8 一并实现但只作速度探索（k=5 的保真见 R9，k=8 在 GPU 读上更贵）。

### 4.3 显存专家缓存

- 容量：**约 4.06 GiB（21.7% 覆盖）**。v0.5 后 q8_0 K + q4_0 V + 16K 窗口占 143 MiB，剩 4154 MiB（5.5 节）；
  25% 放不下，不再追求。20 / 25 / 30% 档命中率 77.3 / 81.6 / 85.4%（M1 实测），21.7% 约 79%。
  v0.1 的"3.5 GiB 命中 97.4%"来自作废的 trace，已改。
- 替换策略：按层的 SLRU（probation / protected 两段），不用静态驻留。
- 缓存槽：**按层分尺寸**，槽字节 = 该层专家的实际字节（1.812 / 1.945 / 2.195 MiB 三种），按专家整块存放，
  与重组后的 RAM 布局一一对应；4154 MiB 按层切分（RESULTS 第 35 节，U-8）。槽不跨层互换，
  SLRU 按层维护。按最大专家开槽是 1912 槽，按层分槽比它多约 15%。
- **prefill 复用缓存区**（U-9）：层优先分块要两块层缓冲（约 952 MiB），prefill 期间从专家缓存区里借，
  不新增预算桶；decode 启动时再按 5.5 把 4154 MiB 缓存建起来。两个阶段不共存。
- 未命中：**两条路径分担**（第 4.7 节）。miss 数按 `40 x 8 x k x (1 - hit)` 从 RESULTS 第 7 节推，
  k=5 / 21.7% 约 322 个/pass（0.57 GB）；k=4 约 258 个。**平均多重度 = 8k/U_k**（k=4 为 1.61），
  CPU 腿按多重度算（RESULTS 22），不是每个 miss 专家都跑满 k 个 token。
  分配由 `QRT_MISS_SPLIT` 控制，目标是三条腿耗时相等，不是固定 50/50。

### 4.4 文件重组（允许）

- 按 `[层][专家]` 连续存放 gate/up/down 三块，**每个专家按其实际字节 64 KiB 对齐**（变长，不按 1.84 MiB
  常数，也不按 2 MiB 边界）；索引给出每块的 offset/bytes/hash（RESULTS 第 33、35 节）。
- 按 10K 统计的使用频次（LRU 用不到，但用于初始化预热和分析）写入 sidecar 索引。
- 重组前后权重字节一致（逐块校验），不修改任何量化值。
- 仅重排，不转换格式。

### 4.5 Prefill（PP）

- **chunk 在层内循环**：一层只上传一次，把 prompt 里所有 chunk 的 token 都在这层算完再进下一层
  （层优先跨 chunk）。专家搬运因此是**每 prompt 一次**，不是每 chunk 一次；chunk 只影响计算侧的
  占用率。10K prompt 实测：专家腿 2976-2980 ms（3436 tok/s）、端到端 7.09-7.10 TFLOPS、
  搬运 18.5 GiB/prompt（RESULTS 第 44 节）。chunk 优先（每 chunk 重读一遍）只有约 1190 tok/s。
- 层优先分块：chunk 由 R0 曲线定，**默认 2048**；每层的专家只读一次，用双缓冲从 RAM 上传
  （运行时实测：8 槽在飞时 H2D 11.5-12.1 GB/s、等待被完全藏住，`RESULTS.md` 第 35、37 节）。
  每层专家约 464-476 MiB（按层 1.812-2.195 MiB/专家，`RESULTS.md` 第 35 节），14.17 GB/s 下 33-35 ms
  （每 prompt 一次，见上一条）；
  PP 1000 要求 chunk >= 1420（6 TFLOPS）或 >= 1190（8 TFLOPS），chunk=512 只能到 361（`RESULTS.md` 第 11 节）。
- **存储读取是 prefill 的另一条硬腿**：1846 MiB/层的上传被藏住后，从重组文件读进 staging 只有
  2.6 GB/s（`RESULTS.md` 第 37 节），此时 PP 1000 需要 >= 9 GB/s 的读取。读通路（mmap 而非逐专家
  `fread`）与上传同等重要，验收时两条腿都要报数。
- 计算量约 6 GFLOP/token，1000 tok/s 需要约 6 TFLOPS 有效算力，超过 RDNA2 FP32 实际能力，**必须用 int8 点积**（`V_DOT4_I32_I8`）的 Q4_K × Q8_1 GEMM。
- 2048 token 时每层计算约 51 ms（6 TFLOPS 有效），大于上传 35.5 ms，传输被覆盖。
  **6 TFLOPS 有效算力是 PP 1000 的硬前提**；int8 点积已测到 6.08-6.20 TFLOPS（`RESULTS.md` 第 28 节）。
- 注意力与稠密：按张量形状核算（`RESULTS.md` 第 45 节），10K prompt 的三条腿是
  **稠密投影 30.9 TFLOP（50%）**、注意力本体 9.45 TFLOP（15%）、路由专家 21.1 TFLOP（34%）。
  "full-attention 层的注意力计算占比低"只对注意力本体成立；**稠密投影是最大的一条腿**，
  且稠密权重是 q8_0，需要单独的 Q8_0 x Q8_1 GEMM（M2-6b）。
  DeltaNet 的递推 FLOPs 很小（1.6 MFLOP/token）但是串行的，属于时延问题。

### 4.6 每 pass 的执行模型

- 每个 pass 一个命令缓冲，层间只用 barrier，不回到 CPU。
- 采样在 GPU 上做 greedy（argmax 或 top-1 候选），只回传 k 个 token id。
- 接受判定在 CPU 上做（k 个 int32，比较即可）。
- 同步次数：每 pass 1 次等待 GPU + 1 次等待 CPU 腿（两条腿在 pass 末尾汇合），而不是每层一次。

### 4.7 CPU 角色

用户 2026-10-24 决定：**decode 的 miss 专家由 H2D 与 CPU 分担**。这条取代 v0.1 的"CPU 不参与 decode"。

- CPU 计算未命中专家：直接读 RAM 中的原权重，不经过 PCIe，也不写显存。
- 与 GPU 并行：GPU 同时算命中专家与稠密部分，两条腿在层边界汇合（每层一次 light fence）。
- 代价模型：**0.115-0.118 ms/专家（4 线程，R1b 实测，55-61 GFLOPS、16.6 GB/s）**；按 40 GB/s 与 1.93 MiB/专家理论上限约
  0.048 ms，现读数差 2.6-2.9 倍，是 M3 内可挖的余量，但当前投影已按 0.137 计算。
  **v0.4 修正**：该值是**单 token** 口径。k=4 时一个 miss 专家平均服务 1.61 个 token，
  M3-1a 的专用核实测 t=1/2/4/5 为 0.079/0.106/0.160/0.199 ms（8 线程），期望约 0.10 ms；
  最坏 t=4 是均值的 1.6 倍（RESULTS 20/22）。运行时必须按多重度计算。
- **已测（M1-7）**：H2D 与 CPU 读并发时，H2D 掉到 8.9-11.2 GB/s（单跑 14.17，约 -27%），
  聚合 33.5-41.0 GB/s（单跑之和的 74-83%）。因此分配不能用固定比例，必须自适应；
  据此重算的周期见第 2.6 节，TG 132-143。
- CPU 还负责：分词、接受判定、调度、MTP 草稿的候选词表选择。

### 5.2 数据结构（草案）

```c++
struct ExpertKey { uint16_t layer; uint16_t expert; };   // 40/41 层 × 256
struct ExpertSlot { int32_t slot; uint32_t gen; };        // 显存槽号与代数；槽字节按层查 slot_bytes[layer]
struct ExpertPageTable {                                  // 静态表，启动时生成
    uint64_t host_offset[41][256];                        // 重组文件内偏移
    uint64_t bytes[41][256];                              // 每专家实际字节（按层不同，RESULTS 35）
    ExpertSlot cache[41][256];                            // 当前驻留槽（-1 表示未驻留）
};
struct PassPlan {
    uint32_t k;                                           // 1/2/4/5/8
    int32_t  pos0;                                        // 起始位置
    uint32_t route_ids[41][8][8];                         // 每层每 token 的 top-8（GPU 写，CPU 读取）
};
```

### 5.3 pass 流程（伪代码）

```
pass_step(k, tokens):
  upload tokens and pos
  for layer in 0..39:
    attn_or_deltanet(layer, k)            # 稠密读取，一次
    router(layer, k) -> route_ids         # top-8，GPU 上
    cache_lookup(layer, route_ids)        # GPU 上查表，输出 hit/miss mask
    split = plan_split(miss_ids)          # 按三条腿耗时相等切分（QRT_MISS_SPLIT）
    enqueue_h2d(split.h2d_part)           # 异步，与计算重叠
    launch_cpu_moe(split.cpu_part)        # CPU 线程直接读 RAM 算，不占 PCIe
    moe_compute(layer, k, hits, h2d_slots)  # 命中 + 等到位的 H2D 部分
  output_head(k)                          # 完整词表，argmax
  submit(); wait_cpu_leg(); read(k ids, route stats)
```

### 5.4 接受与回滚

```
draft = mtp_draft(ctx, k-1)            # 受限词表
verified = pass(k, [last] + draft)     # 完整词表
accept = longest prefix where draft[i] == verified[i]
ctx.append(accept) + verified[len(accept)]   # 第一个不匹配处用验证结果
rollback KV/DeltaNet state to accept length  # DeltaNet 需要保存 k 个中间状态
```

- DeltaNet 回滚：在 pass 内保存每个 token 之后的递推状态（k 份，状态很小）；接受后只保留需要的那一份。
- full-attention 层的 KV：按位置写入，回滚只需移动长度指针。

### 5.5 显存预算（8176 MiB 设备，v0.5）

| 项目 | MiB | 备注 |
|---|---|---|
| 桌面占用 | 500-1400 | 取中值 1000 |
| 稠密权重 | 2079 | M1-6 的 GGUF 账 |
| 专家缓存 | 4154 | **21.7% 覆盖**（q8_0 K + q4_0 V + 16K 窗口后的余量） |
| KV（q8_0 K + q4_0 V，16K 常驻窗口） | 143 | 256K 页面放主机，共 2288 MiB；K 544 + V 288 = 832 B/token/层 |
| 计算缓冲（k=5） | 700-1100 | M1-4b 实测 |
| 草稿与其他 | 100 | 受限词表 logits、MTP 块 |
| 合计 | 7176 | 计算缓冲 700 时正好；1100 时缓存降到 3754（19.6%） |

**结论：v0.5 之后预算仍能合上，但只剩一条窄带。** 可行点是 q8_0 K + q4_0 V + 16K 窗口 + 21.7% 缓存；
计算缓冲每多 100 MiB，缓存覆盖掉约 0.5 pp。25-30% 缓存与 8 GiB 仍然互斥，已放弃。
M1 的命中率与 TG 读数是在 21.9% 档（4198 MiB）测的；v0.5 的 21.7%（4154 MiB）差 44 MiB、约 23 个槽，
在模型噪声内，不重测。三个仍需实测的量：

1. 计算缓冲（M1-4b）：目标 <= 700 MiB；超出就把缓存降到 20% 以下并重算 TG。
2. KV 精度的数值（M2-6a / G-QUAL）：默认档 q8_0 K + q4_0 V 必须 KLD <= 1e-4；不过降 q8_0/q8_0
   （16K 窗口 187 MiB，缓存 21.4%），再不过回退 f16/f16（352 MiB，20.6%，且 256K 常驻不可行）。
3. 桌面占用：500-1400 波动，跑数前用显存读数确认，不按中值承诺。

## 6. 性能模型

### 6.1 单 pass 字节账（k 个 token）

- 稠密：2.17 GB（每 pass 一次，来自显存）。
- 专家（VRAM 读取）：命中数 × 1.93 MB，命中数 = U_k × 40 − miss。
- 未命中：miss × 1.93 MB，由 H2D 与 CPU 分担（U_k 与 miss 见第 2.2 节实测）。
- 草稿（k-1 步）：受限词表时约 33 MB/步，完整词表时 0.5 GB/步。

### 6.2 三条腿的耗时（表见第 2.6 节）

| 腿 | 公式 | 速率来源 |
|---|---|---|
| GPU | (2.17 GB + 命中 × 1.93 MB) / 156 GB/s | M1-5 大缓冲区实测 |
| H2D | miss × 1.93 MB / 9.9 GB/s | M1-7 争用下沿（单跑 14.17） |
| CPU | miss × 0.137 ms | M1-7 4 线程上沿 |

周期 = max(三条腿) + 草稿 + 每 pass 提交与同步开销（要求 < 1 ms，M1-4b 测）。
v0.1 的 6.2 表（217 GB/s、2% miss、只走 H2D）已作废。

### 6.3 TG 与接受数 E（每 pass 接受的 token 数，含 bonus）

TG = E / 周期。按第 2.6 节的周期：

| 配置 | 周期 | E（已测） | TG |
|---|---:|---:|---:|
| k=4，25% 缓存 | 21.0 ms | 2.84 | 135 |
| k=5，25% 缓存 | 24.3 ms | 3.24 | 133 |
| k=4，30% 缓存 | 21.5 ms | 2.84 | 132 |
| k=5，30% 缓存 | 22.7 ms | 3.24 | 143 |

**实测（16K 受限词表，RESULTS 19）**：k=4 E=2.850、k=5 E=3.055。**验收配置是 k=4**：
21.9% 缓存下 k=4 需 E >= **2.90**（CPU 0.118）或 **2.72**（CPU 0.090）；E=2.850 对应 CPU 约 0.10。
对 0.118 差 1.7%，对 0.090 余 4.8%。k=5 的 3.055 只作速度上限，不作验收（R9 / U-7）。
**余量取决于 CPU 专家核，不是缓存。**

### 6.4 PP 计算

- 每 token 6 GFLOP，1000 tok/s 要 6 TFLOPS 有效算力。
- RDNA2 FP32 峰值约 7.9 TFLOPS，实际能到 30-50%。纯 FP32/FP16 路径做不到。
- int8 点积（`V_DOT4_I32_I8`）路径的理论吞吐约为 FP32 的 2-4 倍。M2 必须用它。
- R1c 实测：专家形状 Q4_K x Q8_1 GEMM **3.66 TFLOPS**（2048x512x2048，check 通过），dense 大 K 5.95，
  ALU 上限 8.67。**6.0 需要 1.64x 的内核优化**（activation load / fold / occupancy），由 M2-4 交付。
- **M2 实测重写（2026-10-25，用户授权改 design）**：原来"dense 上限 3.5 TFLOPS、PP 1000 只能动量化"
  的结论作废（RESULTS 第 46-50 节给出的读数来自**散列读**权重的内核）。权重在加载期改成块主序后，
  同一形状 12.89 TFLOPS（RESULTS 第 52-55 节）。按实测重算 10K prompt 的 PP 预算：

  | 腿 | 实测/推算 | 出处 |
  |---|---:|---|
  | 路由专家（层优先跨 chunk） | 2.98 s | RESULTS 44 |
  | 稠密投影（30.9 TFLOP / 12.89 TFLOPS） | **2.4 s** | RESULTS 55 |
  | DeltaNet 递推（30 层，串行递推版） | 1.47 s | RESULTS 52 |
  | full-attn（10 层） | 待 M2-6d | - |

  合计约 7 s 量级（不含 full-attn）-> **PP 1000 不再需要改数值方案**；DeltaNet 与 full-attn
  是接下来的瓶颈，见 RESULTS 第 45、52 节。

- **纯算力上限（0.85 x 各腿 roofline，不含读取与调度，DECISIONS 68）**：
  稠密 30.9 / 13.4 = 2.30 s、专家 21.1 / 13.4 = 1.57 s、注意力 9.45 / 6.7 = 1.41 s，
  合计 **5.29 s -> 1936 tok/s**。所以硬地板 1000 只要求 int8 腿跑到 roofline 的 **45%**，
  不要求逼近上限；反过来说，专家腿 7.09（44.9%）与注意力 3.18（40.3%）都还有一倍空间，
  而稠密 12.89（81.6%）已经不是主要矛盾。

### 6.5 能否达到 130 的结论（当前估计）

- 稠密地板 72 tok/s（单 token，156 GB/s）是硬上限，只能靠推测摊销突破。
- 三条腿模型（两条 miss 腿的速率已实测）投影 132-143，**余量只有 1-10%**，依赖四个前提：
  **(a) 受限词表的 E 达到 k=4 的 2.90（CPU 0.118）或 2.72（CPU 0.090）——已测 2.850，即
  CPU 约 0.10 时过线（RESULTS 19）；(b) miss 分配自适应且重叠良好；
  (c) 每 pass 提交与同步开销 < 1 ms（**已测 0.065-0.084 ms，M1-4b**）；(d) q8_0 K + q4_0 V + 16K 窗口下 21.7% 缓存能塞进 8 GiB
  （第 5.5 节，v0.5 已定；默认档需过 G-QUAL）。**
- 其中 (d) 已由 U-3/U-10 解决：q8_0 K + q4_0 V + 16K 窗口 + 21.7% 缓存正好落在 7176 MiB；默认档必须过 G-QUAL，
  不过则降 q8_0/q8_0（缓存 21.4%），再不过回退 f16/f16（20.6%）。当前软件下 20% 档是 108-118（`RESULTS.md` 第 11 节），低于 130；
  R1b 实测 CPU 0.118 是 131，到 0.090 是 146。因此 130 的达成取决于 **CPU 专家核（M3-1）**，
  不是 R1c。**k=4 的保真已由 M1-3e 在 2x128 token 上验证；k=5 不是验收配置（R9）。**
- 因此 **TG 130 的可达性目前是"有条件"，不是"已确认"**：需要 M1-3b（受限词表 E）、M1-4b（周期）、
  M1-6（KV 预算）三项，再回用户处评审。
- (e) **文本类型**：U-5 已决，code 纳入 130。code 的命中率只有 66.0%，需 CPU 专家核 <=0.059
  （目标 0.055）+ H2D 10.8；当前 0.118 只到 82。M3-1a 是硬前提。

## 8. 测试与验收

### 8.1 正确性

- **参考对齐**：同一 prompt、同一 seed、greedy，输出 token 序列与 `llama-cli`（同模型）逐 token 一致。
- **logits 对齐**：完整词表 logits 与参考实现的 KL 散度 ≤ 1e-4（只在 k=1 路径上检查，推测路径上只检查接受的 token）。
- **重组校验**：重组文件的每个专家块与原 GGUF 的字节 SHA-256 一致。
- **接受回滚**：构造 k 个 token 中第 i 个不匹配的用例，检查 KV 与 DeltaNet 状态与串行解码一致。

### 8.2 性能

- 统一工况：10K prompt（`prompt10k.txt`，并增加一份非重复文本），ctx 256K，greedy，生成 128 token。
- 每个数字必须带口径：日期、提交号、电源态、显存预算、缓存大小、k、草稿词表大小。
- 报告：PP、TG、E（平均接受数）、接受率 p（分位置）、命中率、**H2D 字节/token 与 CPU 算的专家数/token**、
  miss 分配比例、显存峰值（每进程独占，`GPU Process Memory`）、内存峰值。
- **roofline 按指令类别报**（2026-10-25，取值见 1.3 与 DECISIONS 68）：每条腿同时报"硬地板"与
  "0.85 x 该腿 roofline"。int8 腿用 **15.8 TOPS（0.85 x = 13.4）**，FP32 腿用 **7.9 TFLOPS（0.85 x = 6.7）**，
  TG 用带宽 roofline（实测 148，0.85 x = 126 低于硬地板，故 TG 只报 130 与它比）。
  跨类别不可比，不许用一个 TFLOPS 数比较两条腿。
- **同一任务第 3 次尝试前必须写失败假设**；归因到硬件之前，先确认内核没有结构性问题
  （RESULTS 第 51-55 节的教训：六次微优化都建立在"dense 上限 3.5"这个错误读数上）。

### 8.3 回归门禁

- 每个里程碑必须跑通第 8.1 节的正确性测试。
- 改动内核后跑 Vulkan 的 `test-backend-ops` 相应用例（`MUL_MAT`、`MUL_MAT_ID`、`FLASH_ATTN_EXT`），与 CPU 结果一致。

### 11.3 术语

- **稠密（dense）**：每个 token 都会全量读取的权重（attention/DeltaNet/输出头/共享专家）。
- **U_k**：连续 k 个 token 在一层中的唯一专家数。
- **E**：一个 pass 中平均接受的 token 数（含 bonus）。
- **p**：草稿每个位置的接受率（几何模型）。
- **MTP**：模型自带的多 token 预测层（`nextn_predict_layers`）。
