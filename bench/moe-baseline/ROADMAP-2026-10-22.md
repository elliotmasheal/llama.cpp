# PP/TG 优化指南（2026-10-22 总览）

> 分支 `trim-vulkan-cpu-qwen35moe`。本文是后续优化的索引与判决依据，不是新实验记录。
> 所有数字都标注来源文件；标注「估算」的必须先实测再当结论用。
> 口径提醒：本文里 `session` 指 2026-10-21/22 那批测量，机器处于「平衡」电源方案，
> 比 AGENTS.md 记录的基线低约 25%（`expert-tiering/PP-BASELINE.md`，映射系数约 x1.33）。
> 跨 session 的数字不可直接比较。

## 1. 判决摘要

| 目标 | 物理边界 | 判决 | 依据 |
|---|---|---|---|
| PP1000 | ub2048 时 eval 需 <= 2.05 s；活跃参数约 2.2B，需约 4.4 TFLOP/s 有效算力。实测 dense 8.6 TF、id GEMM 渐近 6.04 TF | **可达**，需把 GPU compute 砍 35-40% | 第 4 节 |
| TG200 | 5 ms/token x 224 GB/s = 1.12 GB 预算；实际每 token 需从显存读 dense 1.31 GiB + 命中专家约 0.37 GiB = 1.81 GB | **本机不可达**。全驻留 + 100% 带宽效率的绝对上限是 8.1 ms = 123 t/s | 第 3 节 |
| TG 工程目标 | 上传与握手全部消除后地板约 13-20 ms/token | **50-75 t/s（当前的 2-3 倍）** | 第 5 节 |

TG200 只能通过「每次前向平均产出 2-4 个 token」的投机解码拿到 effective rate，
不能靠提高单步前向效率拿到。这一结论与 stash 里旧版 AGENTS.md 的独立推算一致。

## 2. 度量地基（做 A/B 之前先修）

1. **电源方案当前是「平衡」**（`powercfg /getactivescheme` = `381b4222-...`）。
   `expert-tiering/PP-BASELINE.md` 记录 pp512 332-335 vs AGENTS 的 383-405、tg 21.6 vs 26.4，
   并要求只能同 session 对比。**任何 A/B 之前先切到高性能并重标基线**，否则收益测不准。
2. **热漂移**：连续跑 pp2048 会让同一命令后几次掉到约 310 t/s；间隔约 40 s 或用 r=3 看方差
   （`expert-tiering/PP-COMPUTE-PROFILE.md` 开头）。
3. **外部进程**：GPU 上有别的 `llama-server` 时整批 TG 数据作废
   （`moe-baseline/TG-DECODE-BREAKDOWN.md` 开头）。
4. **`GGML_VK_PERF_LOGGER=1` 会把 decode 拖慢 2.6 倍**（tg32 26.8 -> 10.4），
   它给出的绝对时间和「带宽效率」都不可信；decode 的 kernel 时间只能用
   `test-backend-ops perf` 的隔离微基准（`moe-baseline/T2-GEMV-CEILING.md` 第 1-2 节）。
   prefill 上它也只汇总到约 77 ms 的碎片，与 3.5 s/ubatch 不符（`moe-baseline/PP-UB-BOUNDS.md` 第 1 节）。
5. **未结异常**：`expert-tiering/anom-*.err`（2026-10-22 10:15-10:45）显示 eval 1 的 h2d 是
   6134 ms/91 copies，eval 2 只有 2454 ms；同样 144 MiB 的整层拷贝早期 132 ms、后期 28-45 ms
   （约 1.1 vs 5 GB/s）。**没有结论文档**。跑基线时要么丢弃首个 eval，要么先查清这个。

## 3. 屋顶线：TG 的边界怎么算出来的

每 decode token 的字节（`moe-baseline/T2-GEMV-CEILING.md` 第 2 节、`TG-DECODE-BREAKDOWN.md` 第 2 节）：

- dense 权重 1.31 GiB，全部常驻显存（`L8` 的 memory logger：权重 1303 MiB）。
  其中 output 投影 417 MB（q6_K，248320 x 2048）占 32%。
  实测该 kernel 216-217 GB/s，即 dense GEMV 已经在 DRAM 地板的约 97%。
- 活跃专家 8 x 40 = 320 个三元组，每个 1.945 MiB -> 全 miss 时 622 MiB/token。
  实测命中率 60.9%，上传 206 MiB/token，命中部分从 bank 读约 0.37 GiB。

因此：

| 情形 | 每 token 下限 | TG |
|---|---:|---:|
| 显存读全部权重（1.81 GB @ 224 GB/s） | 8.1 ms | 123 t/s（`BASELINE.md` 独立算出 111） |
| 当前实测构成：GPU math 12 ms + 上传等价 15.5 ms + 握手 10.1 ms | 37.6 ms | 26.6 t/s |
| 上传与计算完全重叠（SDMA 与 gfx 是不同引擎） | 约 15-20 ms | 50-65 t/s |

**TG200 需要 1.12 GB/token 的预算，而模型至少要 1.81 GB。** 缺口只能来自：
(a) 更小的权重足迹（降精度，见第 6 节）；(b) 一次前向出多个 token（投机解码）；(c) 更高带宽的硬件。
不要试图用调度或 kernel 优化填这个缺口。

PP 侧的边界：pp512 是**链路受限**（10.4 GiB/eval，14.3 GB/s 上限 -> 约 0.78 s，实测 1.26 s/eval）；
pp2048 ub2048 是**compute 受限**（eval 3.9 s，GPU busy 3.88 s，跳过上传拷贝的 NOOP 探针同样 516 t/s）。
所以「PP 被上传限制」只对 ub<=512 成立，ub2048 下预取已经把传输移出关键路径。

## 4. PP 路线：逐项砍 GPU 时间

pp2048 ub2048 的 kernel 分解（`expert-tiering/PP-COMPUTE-PROFILE.md`，session 口径，eval 3.9 s）：

| op | ms/eval | 占比 | 实测效率 | 目标 | 可省 |
|---|---:|---:|---|---|---:|
| **CONCAT**（30 层 GDN） | **751** | 19% | **2.7 GB/s** | 显存速度，50-100 ms | **-0.65 s** |
| MUL_MAT dense | 955 | 25% | q4_K 6.3-6.6 TF；**q6_K 仅 3.6 TF** | q6_K 到 6.0 TF | -0.30 s |
| MUL_MAT_ID | 899 | 23% | **in-situ 3.5 TF**（微基准 batch2048 是 5.11，渐近 6.04） | 5.0 TF | -0.27 s |
| FLASH_ATTN_EXT | 359 | 9% | 36 ms/层 x 10 层 | -30% | -0.11 s |
| elementwise / GDN | 423 | 11% | gate+up 两次 dispatch，silu*mul 未融合 | 融合 | -0.09 s |

合计 3.9 -> **2.48 s**，pp2048 = 826（session）约 **1100（AGENTS 电源态）**。

### 4.1 CONCAT 是最高 ROI（优先做）

`src/models/delta-net-base.cpp:469`：

    conv_input = ggml_concat(conv_states[3, 8192, n_seqs], qkv_mixed^T[2048, 8192], dim 0)

`qkv_mixed` 是 channel 连续（ne0=8192），transpose 后 dim0 变成 time，
通用 `concat.comp` 按目标内存序走，于是同一 channel 的 2048 个 time 值以 32 KiB 步长被读：
每个 4 B 元素拉一个 32 B sector，**8 倍放大**，67 MB/层跑到 2.7 GB/s、25 ms/层。
transpose 节点本身是 view，不花钱，成本全落在 CONCAT。

两条修法（`PP-COMPUTE-PROFILE.md` 已给出）：

1. **32x32 shared-memory 分块转置 + concat 的新 kernel**：读侧和写侧都连续，一趟 streaming。
   预期 751 -> 50-100 ms/eval。数值完全等价，**不需要 KLD/PPL 门**，只要算子回归。
2. **从图里删掉这个 concat**：short conv 是线性的，`out[t] = sum_j w[j] * qkv[t-3+j]`，
   只有 `out[0..2]` 混入 state；`ssm_conv.comp` 已经按 `i2 + i0 + i1*nb01/4` 读，
   主体可以直接吃 `qkv_mixed` 的 strided view，3 行边界用 elementwise 补。
   这是删代码不是加代码，更可上游化。**先花半天验证 view 的 stride 假设**，
   注意 conv 沿 time 读仍然是 32 KiB 步长，要确认 ssm_conv 的访问模式不会把同样的放大搬进 kernel；
   如果会，退回方案 1。

### 4.2 id GEMM 的 in-situ 差距来自 padding，不是 BN

ub2048 时 256 专家、coverage 0.734，被选中的专家平均 87 token -> BN=64 的第二个 tile
只有约 23/64 行有效，约 32% 的权重行被重读而无效。
`P6-BN32-CORRECTION.md` 已证明**缩小 BN 是错的方向**（一致的 BN=32 使 5.11 -> 4.89，
因为权重行被多流一遍）。正确方向是变长 tile / 跨专家合并 tile，
或减少 `max_tiles` 的过发射（`ggml-vulkan.cpp` 约 6153-6172，空 tile 只付 dispatch+return，
但 128/256 专家时 overshoot 不小）。

`P8-ID-GEMM-GATE.md` 的判决要记住：**id GEMM 只占 10k prefill wall 的 18.4%**，
做到 dense 平价也只有 474 vs 448.6（+5.7%），低于 485 的门。
所以不要为 id GEMM 做结构性重写；把它当第三优先级。

### 4.3 q6_K dense 的 1.8 倍差距

同一份 profile 里 q4_K dense 6.3-6.6 TF、q6_K 只有 3.6 TF。
模型有一组 layout 是 q6_K-down（`llama-moe-cache.cpp` 按 layout 分 group 就是为此）。
先定位是 MMQ 的 q6_K dequant 路径还是 tile 选择问题，这是 955 ms 里最肥的一块。

### 4.4 FLASH_ATTN_EXT 的已知慢路径

- prefill `n_kv > n_q` 时单次调用 666 ms = 13 GFLOPS（q=512, kv=1024, d=256），
  而 kv=q=512 时约 3 ms；`-fa off` 让 PP2048 ub512 从 44.08 到 163.82（3.7x）
  （`moe-baseline/PROFILE-2026-10-18.md` 2.2）。
- decode 的 `row_split` 被 `(n_rows<4 || hsk<=64) ? 1 : 4` 强制成 1，长上下文 TG 估计 +20-60%
  （`moe-baseline/PROGRESS.md` D1）。
- 调参入口集中在 `get_fa_tuning_params_scalar`（`ggml-vulkan.cpp:1200-1275`），
  含一个 AMD-only 的 `limit_occupancy_shmem`（注释写「Values are guessed, tested on RDNA2」）。
- **门禁未结**：`FLASH_ATTN_EXT -b Vulkan1` 5332 例那次跑到一半中止（`expert-tiering/GATES.md` Gate 4）。
  动 FA 之前先把它跑完。

## 5. TG 路线：三项已验证机制的组合

当前 37.6-40.5 ms/token 里 GPU math 只占约 12 ms 且已贴 DRAM 地板，
**全部空间在上传（15.5 ms）与握手（10.1 ms）**。

### 5.1 换掉 ggml_backend_sched，走 MoE executor（收益最大）

Gate 1 已 PASS（`expert-tiering/GATES.md`、`gates/gate1_boundary_result.txt`）：
每层边界 0.115-0.206 ms，而调度器是 0.64 ms/split。
40 层 x 0.44 ms = **-17.6 ms/token**，单这一条就能把 26 推到 45+。
代码在 `src/llama-moe-exec.{h,cpp}`（untracked，且不在 `src/CMakeLists.txt` 里）。

Gate 2 也已 PASS：两队列重叠 105.5 ms vs 串行 192.8-195.4 ms，**99.3% 被隐藏**
（注意其中 compute 臂 370-380 GB/s 被 Infinity Cache 抬高，不是带宽数字）。

**但 M2 的结论必须一起读**（`expert-tiering/STAGE2-DESIGN.md` 1.5）：
executor 变体 G 在每层 5.2 MiB 上传下是 0.772 ms/层 -> 约 43 ms/token = **23 t/s，比基线 26 更差**。
原因是层内重叠窗口只有约 0.385 ms，上传字节本身在关键路径上。
**所以 executor 必须和「消除上传」或「上传换到 CPU 计算」一起做，单独做是负收益。**

### 5.2 miss 交给 CPU 并发算，不上传

`expert-tiering/m2-hybrid-probe.txt`：CPU/GPU 并发 0.639 ms vs 串行 0.905 ms，**80.4% 被隐藏**
（需要常驻线程）。CPU 侧每 token 243 MiB miss，实测 20.3 GB/s（34 GB/s 上限的 60%）、
63 GFLOPS @ t=5（`moe-baseline/HYBRID-PLAN.md` 第 1 节）-> 12.6 ms；
GPU 侧 8.1 ms。并发后地板约 13 ms -> **75 t/s**，且 PCIe 权重上传归零。

**两个必须正视的反面证据**：

- 图内 `--moe-hybrid` 实测 TG **6.1 t/s**（vs 基线 15.9），splits 42 -> 122，
  cpy_sync 72.5-102.9 ms/token（`moe-baseline/HYBRID-STATUS.md`）。
  根因是每个 CPU split 都要 device sync，两个分支从不重叠 —— 是**实现**问题不是物理问题。
  前提是绕开 `ggml_backend_sched`，即 5.1。
- `GGML_OP_MUL_MAT_ID_MASK` **只有 CPU 实现**（`ggml/include/ggml.h:605`、`ggml/src/ggml.c:3447-3463`、
  `ggml/src/ggml-cpu/ggml-cpu.c:1647-1673`；Vulkan 侧 `ggml_backend_vk_device_supports_op`
  落到 `default: return false`）。所以图内 hybrid 会把 GPU 分支也拽到 CPU。
  **补一个 Vulkan MUL_MAT_ID_MASK 是「GPU 算命中 / CPU 算 miss」真正并行的前置条件。**
- **CPU 多线程扩展性存疑**：stash 里的旧版 AGENTS.md 记录，纯 CPU 隔离下 t=1 时 fork 与官方相等
  （4.21 vs 4.49 t/s），但 t=6 时官方 18.16 vs fork 8.54，**fork 的 batch=1 多线程扩展只有 2.0x，
  官方约 4.0x**（`bench/lfm25/COMPARE-OFFICIAL.md` 第 6 节）。
  如果这条在本树仍然成立，5.2 里「16 线程把 CPU 侧压到 7.5 ms」的假设要先实测再采信。
  候选原因：未合入的上游窗口（`ggml-cpu` 的 silu/expf 向量化、非连续 SUM、MoE down scale）与 Clang vs GCC。

### 5.3 上传路径的三个免费修正（`bench/h2d-bw/H2D-CEILING.md` 已量化，全部未实现）

1. **ids 的 D2H 回读改到 fam2 transfer-only 队列族**：
   同队列族合计 13.7 GB/s，分队列 **23.28 GB/s**（第 4 节表）。
   本机队列族：fam0 flags=0xf（gfx/cmp/xfer, 8 条）、fam1 0xe（cmp/xfer, 4 条）、
   fam2 0xc（**xfer-only, 1 条**）。现在 decode 每层的 ids 回读在直接吃专家上传的带宽。
2. **小 chunk 的在途深度 K=1 -> 8/32**：4 MiB 10.19 -> 13.46，1.5 MiB **7.01 -> 11.42**（第 2 节表）。
   decode 每 token 约 113 个小 fill，正好踩在最差档位。这与 `L9` 记录的
   「每次 host-weight copy 前全设备 drain」是同一件事的两面。
3. **源改 pinned `Vulkan_Host` buft 跳过 staging memcpy**：10.8-11.2 -> **14.2 GB/s**（第 5 节）。
   buft 已存在（`ggml-vulkan.cpp:13284-13346`，名字 `GGML_VK_NAME "_Host"`）。
   **注意**：`ggml_vk_host_get` 的 import 路径依赖 `VK_EXT_external_memory_host`，
   本机 AMD 上 `ggml_vk_host_buffer_import_usable()` 返回 false，强行启用会 0xC0000005 崩
   （`moe-baseline/PARADIGM-HOST-DIRECT-AND-UBATCH.md`）。
   只能用后端自己分配的 host buft，**不能 import 模型的 mmap/resident 内存**。
   预取实现已经用上这条（slot map 放 pinned host buffer 使 tg32 20.08 -> 22.54）。

### 5.4 H2D 是硬墙，不要再投入

`bench/h2d-bw/H2D-CEILING.md`：单向 H2D 上限 **14.2-14.3 GB/s**，
SDMA 与 GPU 内核拷贝、3 种队列族、chunk 16 KiB 到 512 MiB、在途深度 K=1..64、WC/cached、
是否保持映射，**全部落在同一个 14.1-14.3 平台**；同方向多队列不叠加（2 腿 13.60、3 腿 14.09）。
Windows 报的 `CurrentLinkSpeed/Width = 4/16` 是驱动虚拟化的能力位，不是协商结果；
14.3 GB/s 是 15.75 GB/s 载荷上限（Gen3 x16 或 Gen4 x8）的 91%。
D2D 74.6 GB/s（约 149 GB/s 显存读写）。**唯一真实余量是全双工**（见 5.3 第 1 条）。

## 6. 范式级选项（需要用户确认才动）

### 6.1 混合精度专家分层：用同样 6 GiB 换更高的命中字节数

decode 的硬约束是「6 GiB bank 只能驻留 10240 个专家三元组里的 3380 个（33%），LRU 命中 60.9%」。
把冷专家降精度可以在同一预算里提高覆盖率，例如 25% 热专家保 Q4_K + 75% 冷专家走 IQ2/IQ3，
覆盖率可到约 48%，命中率估计 75-85%，上传 206 -> 约 100 MiB/token（估算，需实测）。

**全驻留不可行**：19.4 GiB 专家压进 6 GiB 需要约 1.4 bpw（IQ1_S 级），质量不可接受。
所以这条路的形态是「热高精度 + 冷低精度」的两层，不是整体降精度。

**结构代价（这是它需要确认的原因）**：GGUF 里 `ffn_gate_up_exps` / `ffn_down_exps`
是单个 3D 张量、单一量化类型，**同一张量内混合精度当前不可表示**。
必须拆成 `.hot` / `.cold` 两个张量 -> 转换器、loader、graph、bank 布局都要改。

**前置条件**：`tools/expert-repack/` 已有专家重排工具与 KLD/PPL 门，
但 `expert-tiering/ADAPTIVE-REPACK.md` 记录**纯排列的 KLD 是 0.00920 而不是 0**（PPL 1.8638 -> 1.8958，+1.7%）。
排列在数学上必须严格等价，这是个 bug（疑在文件排列 x loader/`REPACK=1` 的交互，
probe 的 256-slot bank staging 也有问题）。**修好它是这条路线的前提**，
否则任何降精度的质量判断都不可信。

### 6.2 gate/up 合并 + SwiGLU 融合进 epilogue

`src/llama-graph.cpp` 约 2361-2374：gate 与 up 分两次 MUL_MAT_ID，共享 src1 与 ids，
导致重复的 Q8_1 量化、路由与 barrier。`gate_up_exps` 分支已存在（约 2340），
但 Qwen3.6 的 GGUF 是分开存放的。业界常规做法（SGLang、TensorRT-LLM grouped GEMM）
可把每 MoE 层的算子数从约 16 降到约 5。**改张量布局，需要确认。**

### 6.3 expert-major grouped GEMM 重写

BK=4、BN 64/128、shmem 双缓冲、scatter 直接写回。新 kernel，
**须先写设计草案并征求确认**。注意 4.2 的 P8 判决：id GEMM 只占 18.4%，
这条路即使成功，PP 收益也小于 4.1 的 CONCAT。

## 8. 代码级待办（来自 stash 里的 MoE Vulkan 审计，本树尚未复核行号）

- **F2（高，与投机解码相关）** mat-vec id 路径按 token 逐次分派（`ggml-vulkan.cpp` 约 7932、8032-8049）：
  `ids->ne[1] <= 8` 时每层每个 MoE 算子分派 nei1 次，每次重读专家权重，无跨 token 复用。
  实测 83 GB/s vs 同字节 dense 路径 295 GB/s（约 3.5x kernel 级差距），
  且不是 workgroup 数受限（rows/WG 2/4/8 分别 56.9/59.3/57.5/57.8 us）。
  修法：token 索引放进 `gl_WorkGroupID.z`；`nei1 >= 2` 时改走 mmq row-map 路径。
  验证步有 k+1 个 token 时收益最大。
- **F3（中）** 路由重复计算（约 7637、7724-7735）：gate/up/down 三个 MUL_MAT_ID 各跑一次
  `count_experts`，而该 shader 以 `{1,1,1}` 单 workgroup 串行扫全部 id 两遍。估算占 PP 0.5-1%。
  参考 vLLM `moe_align_block_size`：一层算一次，三个算子共用。
- **F4（中）** top-k 归约为 7 次独立 `ggml_add`（`llama-graph.cpp` 约 2521-2527）。
  `multi_add` 融合仅在 `shaderRoundingModeRTEFloat16` 为真且未设 `GGML_VK_DISABLE_MULTI_ADD` 时启用
  （约 4559-4561）；**RX 6700S 上是否生效待确认**。TG 每 token 约 270 个小 kernel 与此相符。
- **F5（中，结构）** gate 与 up 分两次 MUL_MAT_ID（见 6.2）。
- **F6（低，约束）** 预取环只有 2 槽、提前量 1 层（`llama-moe-cache.cpp` 约 1168，`pos % 2`）。
  每层约 498 MiB，8 GiB 显存放不下更多槽；ub 增大后上传占比下降，优先级低。
- **GEMV 的向量化缺口**：`mul_mat_vec_q4_k.comp` 的 `calc_superblock` 每线程做**标量 32-bit 加载**
  （`data_a_packed32[ib0+i].qs[q_offset/4]` 与 `.qs[+16]`，外加三次独立 `scales[]` 加载），
  16 线程处理一个 256 元素 superblock，没有 vec4/128-bit 权重加载；
  MMVQ 路径反而更好（`repack4` 组 `i32vec4`、`dotPacked4x8EXT`、`cache_b_qs`、K_PER_ITER=16）。
  但 `T2` 已证明 dense GEMV 在 DRAM 地板的 97%，**这里没有 2.7 ms 可回收**，不要再投人。
- **死代码**：`src/llama-moe-exec.{h,cpp}` untracked 且不在 `src/CMakeLists.txt`（见 5.1）。
