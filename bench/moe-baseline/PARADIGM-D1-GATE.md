## 2. 确定性计数（有效）

| 量 | 值 |
|---|---:|
| 上传字节 / token | 206 MiB（216 MB）-> **15.5 ms** @13.9 GB/s |
| 命中率 | 60.9%（每 token 约 113/240 次 partial 层 miss） |
| 每层上传 | 206 MiB / 30 partial 层 = **6.9 MiB = 0.50 ms** |
| 每层 MoE 计算 | 30.2% x 21.7 ms / 40 层 = **~0.16 ms** |

关键比例：**每层上传(0.50 ms) 是每层可重叠计算(0.16 ms) 的 3 倍**。

## 3. D1 能重叠多少：机制分析

依赖链（task-26 已确认）：ids(L) 依赖 MoE(L-1) 输出 -> 上传(L) -> MoE(L)。
所以 layer L 的上传只能被 **layer L 自己的计算**（0.16 ms）覆盖：
- 绝对上限：0.16 ms/层 x 30 = **4.8 ms/token**（37.6 -> 32.8 ms -> **TG 30.5**，且假设重叠零成本）。

再加提交模型的**粗粒度等待**：`ggml_vk_get_compute_ctx` 会等待"最新传输信号量值"，因此任何在
compute 提交之前排队的 deferred 上传都会阻塞那个 compute；三种放置都拿不到收益：
1. gate 前上传（现状）：串行；
2. gate 提交后排队 -> up 的 compute 等待它（假依赖）：净收益 ~0；
3. up 提交后排队 -> 同一个 transfer ctx，会在 down split 的 drain 里**先提交 transfer 再提交 compute**，
   于是 up 和 down 都等它：净收益 ~0。
要拿到那 4.8 ms，必须给 deferred 批次**单独的 timeline semaphore** 并在"真正的消费者"compute 上显式
等待它（其余 compute 不等）——这是 ggml-vulkan 的提交层改造，L9/L10 的经验说明这类顺序假设很容易
引入竞态，且今天没有干净窗口可验证。

## 4. token 时间与 TG 上界

| 场景 | token ms | TG |
|---|---:|---:|
| 现状（干净窗口实测） | 37.6 | 26.6 |
| D1 理想（4.8 ms 重叠 + 握手减 3 ms） | 29.8 | 33.5（且需要后端改造） |
| D1 当前提交模型下的现实 ceiling | 32.8-33.8 | **29.5-30.5** |
| 理论极限（上传全隐藏 + 零握手） | 23.9 | 41.8（不可达） |

握手项说明：37.6-12-15.5=10.1 ms 并不是全可省的——它包含每层"等 routing split 完成"的必要 GPU 等待；
真正可省的 submit/observe 延迟上限约 0.1 ms/层 = 3 ms。task-23 已实测单独去掉 drain 是 **-2.5%**
（25.62/25.75 vs 26.36/26.23, r3），因此不能把 10.1 ms 当作可回收预算。

## 5. 判定与建议

- **D1（ring + targeted wait，不改后端）ceiling ~29.5-30.5 t/s，达不到 33**；确切 blocker 是
  (a) 每层上传 0.50 ms > 每层可重叠计算 0.16 ms（3x），(b) 单传输信号量的粗粒度等待把任意 deferred
  上传强加给下一个 compute 提交，使重叠退化为串行。
- 要继续追 33+，正确路径是 **后端提交层改造**（第二传输 timeline semaphore + deferred 标记 + 消费者
  显式 wait），估算 TG 36-39，工作量 1-2 session，风险中高，必须在干净窗口验证。建议作为下一个任务，
  先做"双信号量 + 空转微基准"验证等待语义，再改 MoE 上传路径。
- 若不想动后端：这台 8 GiB 机器的 decode 天花板就是 26.6 t/s（GPU math 12 ms + 上传 15.5 ms +
  必要握手，三者都已被各自的上限钉住）。

## 6. 本轮没有改动代码的原因

按任务约定"若 33 无法安全达到则报告 measured ceiling 与确切 blocker"：基于确定性计数与已实测的
干净窗口数据，D1 不满足验收；同时机器被污染无法做任何时间验证，写一条无法验证的重叠路径只会增加
竞态风险。树保持 `5aeab4cae`，worktree/build 完整；下次干净窗口可直接开工第 5 节的后端改造任务。
