### 2.2 PP2048（多 ubatch 病态）

`-p 2048` 在 ub=512 下是 4 个 ubatch。`copy`（几乎全是 cpy_sync 等待）逐 ubatch 为
2.38 / 3.00 / 3.07 / 3.07 s（合计 11.5 s），eval 总时长 12.26 s：

| ub | fa on（t8） | **fa off（t5）** | 倍数 |
|---|---:|---:|---:|
| 512 | 44.08 | **163.82** | 3.7x |
| 1024 | 33.82 | **77.67** | 2.3x |
| 2048 | 52.93 | **92.80** | 1.75x |

算子级证据（PP2048 ub512，`GGML_VK_PERF_LOGGER=1`）：MUL_MAT_ID 47% / **FLASH_ATTN_EXT 37%** /
稠密 MUL_MAT 11%。单个 FA 调用（q=512, kv=1024, d=256, 2 KV heads, mask）耗时 **~666 ms = 13 GFLOPS**，
而 PP512 内（kv=q=512）单个 FA 仅 ~3 ms。即 **Vulkan FA 在 n_kv > n_q 的 prefill 形态下掉进慢路径**。
`-fa off` 用 matmul 路径绕开，是 PP2048 目前唯一的大杠杆；`ub=1024 + fa off`（77.7）不如 `ub=512 + fa off`（163.8）。
另注意：`fa on` 的多 ubatch 数字不稳定（t8 下 ub1024 单次测到 76.4，复测 33.8），`fa off` 稳定。

旁证：打开 `GGML_VK_PERF_LOGGER=1` 会把 PP2048 ub512 从 45.7 推到 86.8 t/s（per-split 强制
submit+fence），说明多 ubatch 下提交批处理还存在一处 ~2x 的停顿；单独试
`GGML_VK_MAX_NODES_PER_SUBMIT=1`（45.87）与 `GGML_VK_SERIALIZE_SUBMISSIONS=1`（44.66）都复现不了，
机理待查（见杠杆 4）。

### 2.3 TG32（每 token 53.6-56.4 ms）

canonical（`-t 8 -fa on`）：`copy=14.7-15.6ms (cpy_sync 13.3-14.3) cpu=24.6-27.0ms gpu_submit=10.0-11.9ms`
最优（`-t 5 -fa off`，53.6 ms/token）：`copy=14.4ms (cpy_sync 13.5) cpu=21.7ms gpu_submit=10.1ms`

| 成分 | 每 token | 占 token | 边界/说明 |
|---|---:|---:|---|
| CPU MoE（27 层 x 8 experts） | 21.7 ms | **40%** | 440.6 MB/token -> **20.3 GB/s**，约为 CPU 带宽上限 34 GB/s 的 60%；1.36 GFLOP -> 63 GFLOPS |
| GPU 计算（藏在 D2H 同步等待里） | 13.5 ms | 25% | 见算子表 |
| gpu_submit（host 命令录制） | 10.1 ms | 19% | 56 splits，约 0.18 ms/split |
| 拷贝本体（D2H 0.27 + H2D 0.5） | 0.8 ms | 1.5% | Phase A 已把 fallback 清零（fb=0, async=29, asyn_get=54） |
| 其它（构图/采样/输出回读/同步尾巴） | ~7.4 ms | 14% | 未单独插桩 |

TG 的 GPU 算子占比（`GGML_VK_PERF_LOGGER=1`，注意 logger 会把 TG 拉慢到 115 ms/token，只取占比）：
MUL_MAT_VEC（稠密 GEMV，含 attention 投影/共享专家/lm_head）59%，MUL_MAT_ID_MUL 10%，
MUL_MAT_ID_VEC 6%，FLASH_ATTN 5%，RMS_NORM_MUL 3.5%，TOPK_MOE 3.3%。

静态配置下 TG 的关键事实：`hw=0`，即 **decode 路径没有专家上传**（14 层 MoE 在 GPU 常驻、27 层在 CPU 算），
CPU MoE 是唯一的大头，也是 40% 的 token 预算。

## 3. 缓存路径 vs 静态放置（新载入模式）

`llama-bench` 不支持 `--moe-cache-mib`，该组用相同 harness 的 `llama-cli` 测（514 token prompt，
`-n 32 -c 2048 --temp 0 -st -t 5 -fa off`，取 `[ Prompt: X | Generation: Y ]`，单位 t/s；
同 harness 下 `-ncmoe 27` 静态的 TG 18.25 与 llama-bench tg32 19.2 相当，方法可比）：

| 配置 | Prompt | Generation | 说明 |
|---|---:|---:|---|
| `-ncmoe 27`（静态，最优） | 337.0 / 340.0 | 18.4 / 18.1 | 交叉两次 |
| `-ncmoe 41 --moe-cache-mib 6144` | 285.7 / 286.1 | **23.1 / 23.2** | **TG +27%**，PP -15% |
| `-ncmoe 41 --moe-cache-mib 4096` | 287.6 | 22.7 | |
| `-ncmoe 41 --moe-cache-mib 4096 --moe-hybrid` | 297.7 | 11.9 | 带 masked CPU-miss 的 hybrid 反而慢 2x |
| `-ncmoe 27 --moe-cache-mib 1024` | 311.3 | 13.9 | VRAM 被 14 层常驻 + cache 挤爆 |
| `-ncmoe 27 --moe-cache-mib 2048` | 59.1 | 12.3 | 严重 VRAM 抖动 |
| `-ncmoe 30 --moe-cache-mib 4096` | 54.0 | 13.2 | 同上 |
| `-ncmoe 34 --moe-cache-mib 6144` | 279.0 | 16.5 | |

缓存命中率（`-v`，ncmoe 41 + c6144，decode）：`llama_moe_cache: ubatch <= 8: hits = 817,
misses = 1978, hit rate = 29.23%, uploaded = 3600.33 MiB`；加载期日志：
`impl: 20 layers, q6_K: 1690 slots (33.0%)`（cache 只覆盖 20/41 层，值得核查）。

结论（明确回答任务问题）：在 decode 上缓存路径**可以**赢静态放置（18.3 -> 23.2，+27%），
但在 prefill 上输 15%（上传层数 41 vs 27 的 1.44x 放大 + cache 每 split 的额外 ids/同步开销）。
合理形态是 **prefill 用静态放置、decode 用缓存**（cache 已按 `ubatch <= 8` 分流，prefill 侧开销才是要修的）。

## 5. Top-3 杠杆（按实测收益排序）

### L1. 专家驻留缓存（decode）：TG +27%，已实测
- 证据：`-ncmoe 41 --moe-cache-mib 6144`：TG 23.1-23.2 vs 静态 18.1-18.4（交叉两次）；
  4096 MiB 时 22.7。命中率仅 29%（cache 仅覆盖 20/41 层），提升命中率还有空间。
- 机理：把 decode 的 27 层 CPU MoE（21.7 ms/token = 40%）换成"GPU 算 + 少量 miss 上传"
  （440 MB x miss 率 / 12 GB/s）。
- 代价：prefill -15%（层数 41 vs 27 + 每 split 额外开销）。应在 prefill 走静态放置、decode 走缓存。
- 这是"hide uploads / 缓存路径"能否赢静态放置的答案：**decode 能赢，prefill 不能**。

### L2. CPU MoE 吞吐（静态配置的 40% token 预算）：理论最多省 ~8-9 ms/token
- 证据：440.6 MB/token、21.7 ms -> 20.3 GB/s，只有 CPU 带宽上限（34 GB/s）的 60%；
  1.36 GFLOP -> 63 GFLOPS（5 线程）。`-t 5` 已拿到 +9%，剩余靠 kernel：q4_K/q6_K GEMV 的
  repack/预取/非临时访存、按 expert 行重排。若到 34 GB/s：21.7 -> 13 ms，TG 19.2 -> ~25 t/s。
- 风险：不一定纯带宽受限（8 expert 随机行、线程间同步），需先做单层微基准。

### L3. Vulkan FA prefill 慢路径（n_kv > n_q）：PP2048 3.3-3.7x
- 证据：PP2048 ub512 44.08 (`fa on`) -> 163.82 (`fa off`)；单 FA 调用 666 ms = 13 GFLOPS，
  而同 shape 内 kv=q 时仅 ~3 ms。受影响形态：多 ubatch prefill / 多轮对话（KV 已长）。
- 修法方向（不是本任务范围）：为 head_dim 256 + 2 KV heads + mask 的 prefill 形态选对
  FA pipeline（或 n_kv > n_q 时退回 matmul attention）；修好后 PP2048 有望从 45.7 到 150+，
  对 server 首 token 延迟意义更大。

### L4（备选，未进前三）. gpu_submit 10.1 ms/token = 19%
- 56 splits x ~0.18 ms 的 host 端录制（fusion 搜索 + descriptor/命令缓冲）。若能合并相近 split
  或缓存 split 的录制结果，最多省 ~5 ms/token（+10% TG）。需要单独 task 验证可行性。
- 另：PP2048 ub512 在 VK perf logger 下 45.7 -> 86.8，说明多 ubatch 提交路径还有一处 ~2x 停顿，
  `GGML_VK_MAX_NODES_PER_SUBMIT` / `GGML_VK_SERIALIZE_SUBMISSIONS` 均无法复现，值得单独查。

## 6. 三个数字

## 8. 注意事项

- 本机 +-3% 漂移；PP2048 的 `-fa on` 多 ubatch 配置复测可差 2x（`-fa off` 稳定）。
- 缓存路径数字来自 llama-cli（llama-bench 缺该参数），与 llama-bench 的 tg32 在静态配置上
  只差 ~2-5%，可用于相对比较，但精度不如 llama-bench。
- 内存：resident 载入后私有内存 21.4 GiB、working set 12.9 GiB；`LLAMA_FAULT_DIAG=1` 稳态
  decode 页错误仅 +547（PP512 第二轮），确认已无 mmap 抖动。
