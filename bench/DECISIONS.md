# DECISIONS - 判决、已证伪、开关、未结项

与 `RESULTS.md` 冲突处以 `RESULTS.md` 的数字为准；本文件只回答"这意味着什么、还能不能做"。
本文件只记录 qwen36 运行时（design）的判决。新判决按编号追加，不改写已生效的条目。

## 1. 可达性判决（2026-10-24，基于 M0 实测）

| 问题 | 边界 | 判决 |
|---|---|---|
| 单流 TG 130 | 稠密每 token 2.17 GB，217 GB/s -> 10 ms -> 单步 <= 100 tok/s | **单步不可达**，必须把一次前向摊到 k 个 token |
| 完整词表 MTP 能否达标 | 修正投影 102-127（`RESULTS.md` 第 4 节） | **不达标**，只作基线 |
| 受限词表能否达标 | 草稿步约 0.15 ms，只需 E >= 2.1（默认深度）或 2.3（n-max 4） | **有条件可达**，取决于 M1-3 |
| PP 1000 | 6 GFLOP/token -> 需 6 TFLOPS 有效；RDNA2 FP32 峰值约 7.9 TFLOPS，实际 30-50% | **FP32 不可达**，M2 必须走 int8 点积 |
| 显存预算 | 不含 KV 已 7850 MiB，而可用约 7176 MiB | **不成立**，专家缓存要降到 2.5-3.0 GiB（design 5.5） |
| 256K KV | KV 预算待 full-attention 层数确认 | **未定**，出数前不得承诺 256K 驻设备 |
| 静态 top-N 专家驻留 | 25% 覆盖只 46.1% 命中，LRU 97.9% | **已证伪**，必须动态 LRU/SLRU |
| 每 pass 提交与同步开销 | 未测；投影要求 < 1 ms/pass | **未验证**（M1-4b） |
| miss 全部走 H2D（design 4.7 的模型） | 实测 miss 18-23%；25-30% 缓存下 H2D 需 24.7-31.0 ms/pass | **不达标**，TG 90-113 |
| miss 全部走 CPU | 30% 缓存、k=4：miss CPU 20.2 ms，周期 20.7 ms | **刚过线**，余量极小 |
| miss 由 H2D 与 CPU 分担（用户 2026-10-24 选择 N8） | 各一半时两条腿各 12-16 ms，与 GPU 20-24 ms 同量级 | **采纳为主路径**；投影 132-148（`RESULTS.md` 第 8 节），必须实测 |
| k 与 E 必须成对使用 | E=2.84 对应约 2.9 草稿/周期、验证宽度约 4 token | **已定**：拿 k=8 的 U_8 配 k=3 的 E 会高估 TG 约 40% |
| 显存读带宽 217 GB/s | 大缓冲区实测 154.9-156.5 GB/s（128 MiB 到 2 GiB，两种 kernel 形状） | **已证伪**；真实上限约 156 GB/s，单步稠密地板从 100 降到 72 tok/s |
| 用 14 MiB 工作集测显存带宽 | 该尺寸落在 32 MB Infinity Cache 内，同一探针给出 285-370 GB/s（超物理） | **已证伪**，历史 217 GB/s 即此法所得 |

三个前提 (a) 局部性跨文本、(b) 受限词表 E、(c) 每 pass 开销 < 1 ms 任一不成立，TG 会落到 110-125，
必须回用户处决定是否下调目标（design 6.5 与第 9 节）。

## 2. 已证伪 / 不要重做

| 方向 | 依据 |
|---|---|
| 单步前向冲 130（加 kernel、调调度、调线程） | 稠密地板 100 tok/s，`RESULTS.md` 第 5 节 |
| 完整词表草稿作为达标路径 | 修正投影 102-127，`RESULTS.md` 第 4 节 |
| 静态 top-N / 整层驻留作为专家缓存策略 | 25% 只 46.1%，`RESULTS.md` 第 2 节 |
| 把 63.8% 当单草稿接受率 | 默认深度约 3，按位置算会高估 E（design 2.4） |
| 只报总 TG、不单列草稿输出头代价 | 会藏掉 2.3 ms/步（design 2.6） |
| 把 `cb_eval` 的 post-compute 回调返回 `false` 当作"读完就结束" | 调度器会 `break` 出当前 split（`ggml-backend.cpp:2118`），前向残缺；这是 M1-1 的根因，`RESULTS.md` 第 7 节 |
| 用 `-ngl 0` 或关 `op_offload` 来做"纯 CPU"trace | 关掉后全图合到 1 个 split，遇到第一个被追踪节点就 `break`，只剩 layer 0；开 op_offload 时 61 个 split 才把缺口摊成"个别层缺失"的假象 |
| 按 design 6.2 的 "miss 约 2%" 估算 H2D 代价 | 实测 miss 率 18-23%（25-30% 缓存），`RESULTS.md` 第 7 节；H2D 因此是主项不是可忽略项 |
| 引用修复前的命中率（97.9%）与 U_8（23.3） | 那份 trace 的前向残缺，已作废，`RESULTS.md` 第 2 节标注 |

## 3. 复用判定（运行时对现有 fork 资产）

| 资产 | 复用 | 说明 |
|---|---|---|
| `llama_moe_cache` 的调度与预取 | 否 | design 3.3：依赖旧图，静态驻留不如动态 LRU |
| `llama_context` 图路径作为 decode 主路径 | 否 | design 3.3：每 token 约 4000 节点，MoE 节点在 decode 有缺口 |
| `common/fit.cpp` 的预算式 | 借鉴，不直接复用 | design 5.5 要按 k=8 与专家缓存重算 |
| 量化格式与反量化块定义（`ggml-common.h`） | 是 | design 3.3 |
| Vulkan `mul_mat_vec` / `mul_mat_id` 内核 | 复用但需改造 | 要改成批量 k 版本 |
| GGUF 解析、Vulkan 设备初始化、tokenizer | 是 | design 3.3 |

## 5. 未结项（M1 决策门，按阻塞顺序）

1. ~~**N1，M1-1**：10 个 full-attention 层与 layer 39 在解码阶段没有 `ffn_moe_*` 回调。~~
   **已闭环（2026-10-24）**：根因是 `cb_eval` 的 post-compute 回调返回 `false` 会让调度器跳过当前 split
   余下的节点（`ggml-backend.cpp:2118`）。修复后 40 层 x 128 token 全部有记录，r=2 逐字节一致。
   见 `RESULTS.md` 第 7 节。
2. **N2，M1-2b**：局部性只在两份技术文本上测过（唯一词比例约 0.4，解码 token 唯一值 89/92 of 128）。
   对话、代码、多语言未测。
3. **N3，M1-3b**：受限词表的 E 未测。它决定 TG 130 是否可达；已测的完整词表投影只有 102-125。
4. **N4，M1-4b**：Vulkan 原型的周期时间（含提交与同步）未测，每 pass 开销 < 1 ms 是纯假设。
   这是 design 2.6 全部投影的分母。
5. **N5，M1-5**：~~带宽是同机历史读数，未复测~~ **已闭环（2026-10-24）**。H2D 14.17/14.18 与 CPU 4T
   40.8/39.2 在 5% 内；显存读 **156.5 GB/s 而不是 217**（-28%）。见 `RESULTS.md` 第 8 节。
6. **N6，design 5.5**：显存预算不成立（不含 KV 7850 MiB 对可用 7176 MiB），专家缓存与计算缓冲的
   最终大小未定稿；KV 一行还是 TBD，需要先确认 full-attention 层数。
7. **N7，design 第 10 节开放问题 3**：是在 `ggml`/`llama.cpp` 之外另建运行时（design 按此写），
   还是在现有 fork 内改造。选后者要重写 design 3.3，并重估"不复用图路径"的理由。
   它是 M2 开工前的用户决策，不阻塞 M1。
8. **N8，miss 率与 design 6.2 冲突（阻塞 M1-GATE）**：design 6.2 按 miss 约 2% 估算，实测 18-23%。
   **用户已于 2026-10-24 决定：miss 由 H2D 与 CPU 分担**（第 1 节已采纳为主路径）。
   剩余动作：design 4.7（"CPU 不参与 decode 专家计算"）与 6.2 需按此改写，且专家缓存需约 25-30%
   （4.70-5.64 GiB，与 N6 的预算冲突）。design 由用户改，agent 只读。
9. **N9，CPU 单专家代价需要优化**：miss CPU 用 0.108 ms/专家（4 线程，历史读数）。按 40 GB/s 与
   1.93 MiB/专家，理论上限约 0.048 ms；现读数有约 2 倍差距。M1-5 的 CPU 读（39.2-40.8 GB/s）说明
   带宽不是瓶颈，差距应在 expert 计算核里。
10. ~~**N10，显存读带宽 156 GB/s 与 design 1.3 / 6 节的 217 冲突**~~ **已闭环（2026-10-24）**：
   用户授权后 design 升到 v0.2，按 156 GB/s 改写 1.3 / 2.2 / 2.6 / 3.1 / 4.x / 5.5 / 6.x / 7 / 9 / 10 节；
   单步稠密地板记为 72 tok/s，周期模型改为三条腿（GPU / H2D / CPU）。
11. **N11，N8 的处置方式待实测**：用户已选定"miss 由 H2D + CPU 分担"，但 H2D 与 CPU 读共用主机内存
    带宽，两者并发时的聚合带宽未测（现有 `h2d-bw` 的 8 线程 memcpy 干扰臂只给 14.86 GB/s 合计，
    明显低于各自单跑之和）。各半分担的 136-148 投影建立在这个未知量上。**这是 M1-7 的唯一目的。**

处置规则：任一项在第 3 次尝试后仍无进展，按 `AGENTS.md` 第 7 节升级给用户，不得自行下调里程碑阈值。
