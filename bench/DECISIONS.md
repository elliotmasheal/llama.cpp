# DECISIONS - 判决、已证伪、开关、未结项

与 `RESULTS.md` 冲突处以 `RESULTS.md` 的数字为准；本文件只回答"这意味着什么、还能不能做"。
本文件只记录 qwen36 运行时（design）的判决。新判决按编号追加，不改写已生效的条目。

## 1. 可达性判决（2026-10-24，基于 M0 实测）

| 问题 | 边界 | 判决 |
|---|---|---|
| 单流 TG 130 | 稠密每 token 2.17 GB，217 GB/s -> 10 ms -> 单步 <= 100 tok/s | **单步不可达**，必须把一次前向摊到 k 个 token |
| 完整词表 MTP 能否达标 | 修正投影 102-127（`RESULTS.md` 第 4 节） | **不达标**，只作基线 |
| 受限词表能否达标 | E 门槛不是常数：E >= TG_min x 周期（RESULTS 第 9 节周期下 k=4 为 2.73、k=5 为 3.16；R1 后 2.3-2.4） | **有条件可达**，取决于 M1-3b；旧值 2.1/2.3/2.85 都是不同周期的快照，作废 |
| PP 1000 | 6 GFLOP/token -> 需 6 TFLOPS 有效；RDNA2 FP32 峰值约 7.9 TFLOPS，实际 30-50% | **FP32 不可达**，M2 必须走 int8 点积 |
| 显存预算 | dense 2079 + 25% 缓存 4798 + 计算 700 + 草稿 100 = 7677 MiB，可用 7176 MiB，且未计 KV | **不成立**，25% 缓存与 8 GiB 互斥（`RESULTS.md` 第 10 节） |
| 256K KV | M1-6：10 个 full-attn 主层 + 1 个 nextn，20-22 KiB/token，256K = 5120-5632 MiB | **不成立**（f16），占可用 7176 的 71-78%，超预算 1335 MiB |
| KV 处置 | **U-3（用户 2026-10-24）：q4_0 KV + 16384 token 常驻窗口**，窗口外放主机（256K 共 1584 MiB） | **采纳**；16K 窗口占 99 MiB，剩 4198 MiB = 21.9% 专家缓存；q4 必须过 G-QUAL，不过则回退 f16 + 降 ctx |
| 静态 top-N 专家驻留 | 25% 覆盖只 46.1% 命中，LRU 97.9% | **已证伪**，必须动态 LRU/SLRU |
| 每 pass 提交与同步开销 | 未测；投影要求 < 1 ms/pass | **未验证**（M1-4b） |
| miss 全部走 H2D（design 4.7 的模型） | 实测 miss 18-23%；25-30% 缓存下 H2D 需 24.7-31.0 ms/pass | **不达标**，TG 90-113 |
| miss 全部走 CPU | 30% 缓存、k=4：miss CPU 20.2 ms，周期 20.7 ms | **刚过线**，余量极小 |
| miss 由 H2D 与 CPU 分担（用户 2026-10-24 选择 N8） | 实测 H2D 争用时 8.9-11.2 GB/s、CPU 0.137 ms/专家；自适应分配后 miss 腿 15.1-23.7 ms | **采纳为主路径**，投影 TG 132-143（`RESULTS.md` 第 9 节） |
| k 与 E 必须成对使用 | E=2.84 对应约 2.9 草稿/周期、验证宽度约 4 token | **已定**：拿 k=8 的 U_8 配 k=3 的 E 会高估 TG 约 40% |
| 显存读带宽 217 GB/s | 大缓冲区实测 154.9-156.5 GB/s（128 MiB 到 2 GiB，两种 kernel 形状） | **已证伪**；真实上限约 156 GB/s，单步稠密地板从 100 降到 72 tok/s |
| 用 14 MiB 工作集测显存带宽 | 该尺寸落在 32 MB Infinity Cache 内，同一探针给出 285-370 GB/s（超物理） | **已证伪**，历史 217 GB/s 即此法所得 |

三个前提 (a) 局部性跨文本、(b) 受限词表 E、(c) 每 pass 开销 < 1 ms 任一不成立，TG 会落到 110-125，
必须回用户处决定是否下调目标（design 6.5 与第 9 节）。

## 2. 已证伪 / 不要重做

| 方向 | 依据 |
|---|---|
| 单步前向冲 130（加 kernel、调调度、调线程） | 稠密地板 100 tok/s，`RESULTS.md` 第 5 节 |
| 完整词表草稿作为达标路径 | 修正投影 102-127，`RESULTS.md` 第 4 节 |
| 静态 top-N / 整层驻留作为专家缓存策略 | 25% 只 46.1%，`RESULTS.md` 第 2 节 |
| 把 63.8% 当单草稿接受率 | 默认深度约 3，按位置算会高估 E（design 2.4） |
| 只报总 TG、不单列草稿输出头代价 | 会藏掉 2.3 ms/步（design 2.6） |
| 把 `cb_eval` 的 post-compute 回调返回 `false` 当作"读完就结束" | 调度器会 `break` 出当前 split（`ggml-backend.cpp:2118`），前向残缺；这是 M1-1 的根因，`RESULTS.md` 第 7 节 |
| 用 `-ngl 0` 或关 `op_offload` 来做"纯 CPU"trace | 关掉后全图合到 1 个 split，遇到第一个被追踪节点就 `break`，只剩 layer 0；开 op_offload 时 61 个 split 才把缺口摊成"个别层缺失"的假象 |
| 按 design 6.2 的 "miss 约 2%" 估算 H2D 代价 | 实测 miss 率 18-23%（25-30% 缓存），`RESULTS.md` 第 7 节；H2D 因此是主项不是可忽略项 |
| 引用修复前的命中率（97.9%）与 U_8（23.3） | 那份 trace 的前向残缺，已作废，`RESULTS.md` 第 2 节标注 |

## 5. 未结项（M1 决策门，按阻塞顺序）

1. ~~**N1，M1-1**：10 个 full-attention 层与 layer 39 在解码阶段没有 `ffn_moe_*` 回调。~~
   **已闭环（2026-10-24）**：根因是 `cb_eval` 的 post-compute 回调返回 `false` 会让调度器跳过当前 split
   余下的节点（`ggml-backend.cpp:2118`）。修复后 40 层 x 128 token 全部有记录，r=2 逐字节一致。
   见 `RESULTS.md` 第 7 节。
2. **N2，M1-2b**：局部性只在两份技术文本上测过（唯一词比例约 0.4，解码 token 唯一值 89/92 of 128）。
   对话、代码、多语言未测。
3. ~~**N3，M1-3b**：受限词表的 E 未测。~~ **已测（2026-10-24，RESULTS 第 19 节）**：
   16K 词表 k=4 E=2.850、k=5 E=3.055；按 CPU 0.118 的 E_min（2.90 / 3.23）都不过，
   按 0.090 的 E_min（2.72 / 2.88）都过。词表代价只有 k=5 的 5.8%。**门仍不过**，原因见 N14。
4. **N4，M1-4b**：Vulkan 原型的周期时间（含提交与同步）未测，每 pass 开销 < 1 ms 是纯假设。
   这是 design 2.6 全部投影的分母。
5. **N5，M1-5**：~~带宽是同机历史读数，未复测~~ **已闭环（2026-10-24）**。H2D 14.17/14.18 与 CPU 4T
   40.8/39.2 在 5% 内；显存读 **156.5 GB/s 而不是 217**（-28%）。见 `RESULTS.md` 第 8 节。
6. ~~**N6，design 5.5**~~ **已闭环（2026-10-24，U-3）**：f16 下 256K KV = 5120-5632 MiB，与 8 GiB
   互斥；用户选 q4_0 KV + 16384 token 常驻窗口，窗口外页面放主机。16K 窗口占 99 MiB，
   剩 4198 MiB = 21.9% 专家缓存（`RESULTS.md` 第 10 节）。q4 必须过 G-QUAL（KLD <= 1e-4），
   长上下文 decode 速度不计入 TG 目标。
7. ~~**N7，design 第 10 节开放问题 3**~~ **已闭环（2026-10-24 用户决定）**：独立运行时，fork 只作
   参考（正确性基准、接受率口径、硬件探针）。内核从 fork 拷进 `runtime/kernels`，不链接
   `ggml-vulkan`；M2-4 / M3-1 的写路径已改为 `runtime/kernels/**`。design 3.3 按此生效。
8. **N8，miss 率与 design 6.2 冲突（阻塞 M1-GATE）**：design 6.2 按 miss 约 2% 估算，实测 18-23%。
   **用户已于 2026-10-24 决定：miss 由 H2D 与 CPU 分担**（第 1 节已采纳为主路径）。
   剩余动作：design 4.7（"CPU 不参与 decode 专家计算"）与 6.2 需按此改写，且专家缓存需约 25-30%
   （4.70-5.64 GiB，与 N6 的预算冲突）。design 由用户改，agent 只读。
9. **N9，CPU 单专家代价需要优化**：miss CPU 用 0.108 ms/专家（4 线程，历史读数）。按 40 GB/s 与
   1.93 MiB/专家，理论上限约 0.048 ms；现读数有约 2 倍差距。M1-5 的 CPU 读（39.2-40.8 GB/s）说明
   带宽不是瓶颈，差距应在 expert 计算核里。
10. ~~**N10，显存读带宽 156 GB/s 与 design 1.3 / 6 节的 217 冲突**~~ **已闭环（2026-10-24）**：
   用户授权后 design 升到 v0.2，按 156 GB/s 改写 1.3 / 2.2 / 2.6 / 3.1 / 4.x / 5.5 / 6.x / 7 / 9 / 10 节；
   单步稠密地板记为 72 tok/s，周期模型改为三条腿（GPU / H2D / CPU）。
11. ~~**N11，N8 的处置方式待实测**~~ **已闭环（M1-7）**：H2D 在 CPU 读负载下 8.9-11.2 GB/s
    （单跑 14.17，-27%），聚合 33.5-41.0 GB/s（单跑之和的 74-83%）。两条腿分担成立，但分配必须
    自适应。用实测量重算的 TG 为 132-143（`RESULTS.md` 第 9 节），比算术投影略低、余量更紧。
12. **N9 已复测**：每专家 0.123-0.137 ms（4 线程），比历史 0.108 慢；与带宽上限 0.048 差 2.6-2.9 倍。
    这不是当前模型的前提（投影已用 0.137），但它是唯一还有 2 倍以上余量的项，M3 内值得优化。
    R0 提醒：0.048 只是带宽口径，反量化算力可能先撞墙；R1 必须同时报 GB/s 与 GFLOPS。

13. **N12（R1a）：显存读 156.5 不是软件差。** read8 8 链、组数 512-4096、1-2 GiB 缓冲、16 GiB 持续
    读都停在 156.1-156.8；规格 224 不可达，156.5 恰好是 128-bit x 10 Gbps（160 GB/s）的 97.8%。
    **用户 2026-10-24 决定：平衡电源为唯一基准，不做性能方案 A/B，U-4 关闭。**
    156.5 作为本机显存上限；换机器时按 `bench/env/hw-<id>.json` 的新 profile 重算，不沿用。

14. **N13（M1-2b）：命中率随文本类型变化，code 最差。** 21.9% 缓存下 chat 81.6%、multi 87.3%、
    code 66.0%；对应 TG 143 / 136 / 82-97（CPU 0.118-0.090）。M1-2b 的 <=5 pp 判据对 code 不通过。
    **U-5 已决（用户 2026-10-24）：code 纳入 TG 130。** 由此推出 CPU 专家核硬指标 **0.059 ms/专家**
    （约 107 GFLOPS，目标 0.055），H2D 争取 12.5；当前 0.118 只能到 82。M3-1a 是达标前提。
15. **N14（M1-3b）：k=5 验证路径与 greedy 分叉，阻塞 M1-GATE。** 16K 与完整词表两个 k=5 臂
    彼此前缀一致，但与纯 greedy 在第 26 个生成 token（0 基索引 25）分叉（`dump` / `snippet`）；k=4 路径完全一致。
    分叉来自 5 宽验证批的数值路径，不是 M1-3c 的词表掩码（掩码臂与无掩码臂同样分叉）。
    k=5 的 r=2 停止位也不同（242 / 253）。任务 M1-3d 负责定位；在此之前 k=5 不能作为验收配置，
    design 3.1 / 6.3 的 k=5 主路径需要重估。

处置规则：任一项在第 3 次尝试后仍无进展，按 `AGENTS.md` 第 7 节升级给用户，不得自行下调里程碑阈值。

## 7. M1-3b 判决：受限词表接受率与 k=5 正确性（2026-10-24）

| 问题 | 证据 | 判决 |
|---|---|---|
| 16K 受限词表是否毁掉 E | k=4：2.850（完整 2.829）；k=5：3.055（完整 3.243） | **不是主因**。k=4 代价在噪声内，k=5 损失 5.8%（0.19 token/周期） |

## 11. N15：CPU 腿的"每专家 0.115 ms"可能只对 1 个 token 成立（2026-10-24）

- R1b 的 0.115-0.118 ms/专家是**单 token** 口径（8 个不同专家，每专家一次 GEMV）。
- k 宽验证批里，一个未命中专家要为**路由到它的 1..k 个 token** 各算一遍；权重只读一次，
  但计算与累加随 token 数增长。design 6.2 的 "miss x 0.137 ms" 把每专家当成单 token，偏乐观。
- 本轮的专用核单 token 0.082-0.091 ms，其中大头是 1.77 MiB 权重读（约 0.045 ms @39 GB/s）；
  按此推断 t=5 时每专家可能到 0.11-0.13 ms，CPU 腿比 design 6.2 高约 10-30%。
- 影响：E_min 与 TG 的 miss 腿都要按 t 的口径重算；若 t=5 明显高于 0.115，k=5 的投影还要再收。
- 处置：新任务 **M3-1b**（t=1..5 的摊销曲线，同一权重重读一次），未测之前不把 0.115 当 k=5 的结论。

## 12. N15 收口：多 token 摊销曲线（2026-10-24）

| t | 8T ms/专家 | 备注 |
|---:|---:|---|
| 1 | 0.079-0.120（另一轮 0.082） | 权重读主导 |
| 2 | 0.106 | |
| 4 | 0.160 | |
| 5 | 0.199 | 最坏情况 |

- k=5 的一个 miss 专家平均服务 40/23.5 = **1.70** 个 token（k=4 为 1.61），期望代价约 **0.10 ms**（8T），
  与 design 6.2 的 0.115-0.137 同档，略偏乐观；最坏 t=5 是均值的 2 倍。
- 因此：**CPU 腿按多重度分布算，不按 t=k 全量算**。若 M3-1/M3-2a 对每个 miss 专家都跑 k 个 token，
  CPU 腿会翻倍（320 miss x 0.20 = 64 ms），E_min 与 TG 132-143 的投影全部作废。
- code 的 0.059 仍未达到（t=1 最好 0.079），M3-1a 保持 partial；后续要再快 1.5x 才能覆盖 code。

不是 E、不是显存、不是保真。按契约不自行下调阈值，交用户选：

- **A（推荐）条件通过**：进入 M2（prefill）先做；code 130 与 M3-6 以 M3-1a 的 0.059 为硬门，

- **B（U-2）下调 code 的 TG**：例如 code 目标 110（对应 CPU 约 0.08），设计与验收口径都要改。

code 的 TG 130 与 M3-6 以 M3-1a 达到 0.059 为硬门，不达则走 U-2；M2（prefill）先开工。

旧代码已回退，无法复跑证实，按"最可能根因 + 已封堵 + 有回归命令"记录。

- 4198 MiB 的缓存预算**按层切分**（每层分到多少槽），切分策略由 M3-0 用路由 trace 的层内 miss
  加权决定；仍然只有**一个**缓存预算器（红线 4），不新开第二个预算或调度器。
- 相对"全局按最大 2.195 MiB"：槽数多约 15%（38 层每槽省 0.39 MiB），代价是槽不再跨层互换，
  SLRU 要按层维护。
- 需要用户改 design 的地方（agent 不改）：5.3 第 304 行"每个槽 1.84 MiB"、5.1 的 `ExpertSlot`
  注释、以及 111 行"每个专家约 1.84 MiB（摊平）"这一平均值的口径说明。

`state.json` 的 escalation E-1 已关闭，M3-0 的标题改为"按层槽尺寸"。

## 36. M2-5 第二步判决：int8 GEMM 接进运行时，但 prefill 必须整层单次提交（2026-10-25）

| 项 | 结果 |
|---|---|
| GEMM 正确性 | gate 对 CPU 双精度参考 **rel_L1 1.599e-7**（PASS，阈值 1e-4） |
| 算力 | **1.51-1.55 TFLOPS**（每专家 M=64），同一内核 M=2048 是 6.08-6.20（第 28 节） |
| 每块 | 0.335-0.338 ms（8 槽，含 read 0.12 / upload 0.03 / compute 0.18） |
| 覆盖 | gate+up 跑；**down 跳过**（Q5_K/Q6_K，`down_skipped` 计数） |

**判决**：adopt（GEMM 进运行时，正确性过），但 M2-5 仍 partial。理由：算力只有内核上限的 1/4，
且 down 的 1/3 矩阵没跑，PP 还不能判。

**根因（两个，都已定位到可测的量）**

1. **占用率**：每专家 M=64 只有 16 个 workgroup（2048 线程），28 CU 填不满；6.1 TFLOPS 是 512 个
   workgroup 的形状。
2. **每专家一次 submit+fence**：0.176 ms 里约 0.065 ms 是固定提交开销（第 35 节测过）。

**下一步（按收益排序，下一轮只做第一条）**

1. **整层单次提交**：把 256 个专家的 dispatch 录进一个命令缓冲，上传完成后一次提交。
   这同时解决占用率（GPU 能持续吃满）与提交开销，等价于 design 4.6 的每 pass 单次提交。
   验收：prefill 每块 0.335 -> 目标 <= 0.15 ms，TFLOPS >= 3。
2. **Q5_K / Q6_K 的 GEMM 变体**：补上 down（多数层 Q5_K、层 34/38 Q6_K）与层 39 的 gate/up。
   量化类型按层混合这件事已写进 design 2.1（RESULTS 39）。
3. **把 gate/up 的 Q8_1 激活量化也搬上 GPU**：现在输入平面的 Q8_1 是宿主侧生成的固定图案，
   真实路径要从 hidden state 量化，属于 M2-5 收尾。

**新增开关/接口**

| 名字 | 作用 | 默认 |
|---|---|---|
| `--prefill-compute probe|moe` | compute 腿选带宽读核还是 int8 GEMM | `moe` |
| `--moe-check <prefix>` | gate GEMM 对 CPU 参考的逐元素校验 | 不跑 |
| `--moe-layer/--moe-expert/--moe-rows` | 校验的取样点与行数 | 0/0/64 |
| `qrt_q4k_*` / `qrt_moe_*` | GEMM 管线与专家合成（`kernels` 模块，design 5.1 已登记） | - |

## 37. M2-5 第三步判决：三型 GEMM 全部落地，下一步是整层单次提交（2026-10-25）

| 项 | 结果 |
|---|---|
| Q4_K / Q5_K / Q6_K | 三个内核都在运行时里，按矩阵字节数自动判定类型 |
| 正确性 | 三型全部 rel_L1 <= 2.5e-7（阈值 1e-4），见 RESULTS 40 |
| 算力 | 1.90-2.16 TFLOPS（三个矩阵全跑）；仍是内核上限（6.1）的 1/3 |
| 覆盖 | gate+up+down 全跑，`down_skipped=0` |

**判决**：adopt。`runtime/kernels/q4k_gemm.*` 更名 `gemm.*`（不再是单一 Q4_K），
新增 `qrt_gemm_block_bytes/matrix_bytes/type_of` 三个纯函数与 `qrt_quant` 枚举。

**为什么 Q6_K 按字节寻址**：210 字节的块让行起点不是 4 的倍数，用 `uint w[]` 逐字读需要
两个 word 加 funnel shift；这是 Q6_K 只占少数层（34/38/39）却仍值得单独一个内核的原因。

**未结项**

1. **整层单次提交**（下一轮）：256 个专家的 dispatch 录进一个命令缓冲，目标每块 <=0.15 ms、

2. **MoE 输出累加**：现在每个专家把结果写进同一块 `o_out`（值不使用），真实路径要按路由权重
   累加到 token 上；这是收尾项，等整层提交做完再定实现。
3. 输入激活的 Q8_1 量化仍在宿主侧生成固定图案（第 39 节未结项 3）。

## 38. M2-5 第四步判决：整层单次提交采纳，下一步是层间双缓冲（2026-10-25）

| 项 | 结果 |
|---|---|
| 算力 | 2.02 -> **3.69-3.71 TFLOPS**（1.84x），每块 0.351 -> 0.272 ms |
| 每层提交次数 | 256 -> **1**（每层一个命令缓冲，512 个 compute barrier） |
| 显存 | 层缓冲 464-476 MiB + 各专家 hidden 平面 9 MiB + 输出切片 4 MiB |
| 新增开关 | `--prefill-mode layer|perexpert`（默认 layer） |

**设计取舍（都记下来，免得以后重踩）**

1. **每专家自己的 hidden 平面**（`hb_qs`/`hb_ds` 按专家切片）是必要的：整层在一个命令缓冲里，
   若共用一块平面，后一个专家的 swiglu 会覆盖前一个专家还没被 down 读走的数据。
2. **每个专家 2 个 compute barrier**（gate+up -> swiglu -> down）。整层 512 个 barrier 的代价
   远小于 256 次 submit+fence（实测总时间还降了 23%）。
3. **专家输出仍写 8 个轮转切片**：按路由权重累加到 token 上还没实现（未结项），
   值不使用，切片只是避免同一地址并发写。
4. **层缓冲按该层实际字节**开（不是 256 x 最大专家），层 39 会更大，符合 U-8。

**未结项**

1. **层间双缓冲**（下一轮，收益最大）：现在 read+upload（41 ms/层）与 compute（28 ms/层）串行，
   双缓冲后每层 max(41, 28) = 41 ms，推算 734 -> 1250 tok/s。代价是第二块层缓冲 464-476 MiB，
   合计约 1 GiB，落在 design 5.5 的 compute 桶 700-1100 MiB 上沿。
2. **MoE 输出累加**（路由权重 + 按 token 归约）：真实数值路径的最后一块。
3. 输入激活的 Q8_1 量化仍在宿主侧（固定图案）。

## 39. M2-5 第五步判决：层间双缓冲采纳；显存复用 decode 缓存区（2026-10-25）

| 项 | 结果 |
|---|---|
| 每块 | 0.272 -> **0.190-0.193 ms**（1.42x） |
| 专家腿推算 | **1226 tok/s**（40 层，三矩阵全含，不含注意力/稠密） |
| 显存 | 层缓冲 x2 = 952 MiB（层 39 更大时按实际字节） |
| 新增开关 | `--prefill-pipeline 0|1`（默认 1）,`qrt_gemm_rings/begin(ring)/submit_nowait/wait` |

**U-9 已决（用户 2026-10-25）：两块层缓冲复用 decode 的专家缓存区**。理由：prefill 阶段不用
decode 的 SLRU 缓存（那是逐 token 的结构），把 4198 MiB 缓存区在 prefill 期间当层缓冲用，
**不新增预算桶、不改 design 5.5 的桶划分**；decode 启动时再按原计划把缓存建起来。
这条要写进 design 5.5 的"复用"说明（已加）。

**为什么不是"再加槽"**：16/24/32 槽实测更慢（GETIT 205/211/223 ms），因为提交的 CPU 时间随槽数线性涨，
而 DMA 速率不变。8 槽已经能在一次 read 的时间窗内把 DMA 排满。

**未结项（按剩余收益排序）**

1. **H2D 分块合并**：现在每次 DMA 1.8 MiB，探针显示 16 MiB 块 pipe-8 是 13.76 GB/s、64 MiB 是 14.05，
   而 1.5 MiB 是 11.59。把相邻专家拼进 8-16 MiB 的 staging 块再传，预计每层 41 -> 36-38 ms
   （推算 ~1300-1380 tok/s）。
2. **多线程读取**：read 34.7 ms 是单线程 memcpy 13.7 GB/s；2-3 线程可望到 20-25 GB/s。
   只有当 H2D 也一起提上去才有意义（两条腿现在几乎等高）。
3. **MoE 输出累加**（路由权重 + 按 token 归约）与**输入 Q8_1 量化上 GPU**：数值路径收尾。
4. **注意力与稠密**（M2-6 / M2-2 的形状）：整模型 PP 还差这两块，本节的 1226 只是专家腿。

## 40. M2-5 第六步判决：分块合并采纳；多线程读取回退为默认关闭（2026-10-25）

| 项 | 结果 |
|---|---|
| 分块合并（16 MiB） | 每块 0.191 -> **0.179 ms**（1.07x），提交 CPU 23.5 -> 7.2 ms |
| 多线程读取 2/3/4/6 | **无收益**（read 恒定 ~141 ms），`--prefill-readers` 默认保持 1 |
| 专家腿推算 | 1226 -> **1330 tok/s** |
| PCIe 地板 | 18.5 GiB/chunk at 14.17 GB/s = **1.31 s -> 1560 tok/s**，本路线只剩 17% |

**判决**：分块合并 adopt（默认 16 MiB）；多线程读取保留开关但默认 1，等诊断清楚再启用。

**新发现的瓶颈结构**：read（13.6 GB/s）与 H2D（13.4 GB/s）**速率相同**，而且加读线程完全无效。
在 coherent staging 内存上，CPU 写与 DMA 读很可能是同一条有效带宽的两端。
若真如此，则"读取 35 ms + H2D 35 ms 重叠成 35 ms"已经是这条内存路径的极限，
而不是两条独立的腿各 35 ms。要先做解耦实验才能定论（未结项 1）。

**未结项（按收益排序）**

1. **解耦读取与 H2D**：读进普通堆缓冲再 memcpy 到 staging，或双份 staging 交替；
   若拷贝能到 25 GB/s，H2D 就成了唯一的腿（33.6 ms/层 -> 推算 1450 tok/s）。
2. **层优先跨 chunk（结构性，需用户批准）**：design 4.5 说"每层的专家只读一次"，
   而现在每个 chunk 都重读一遍（10K prompt = 5 次）。改成"一次 prompt 只进一轮层"，专家流量
   92.5 GiB -> 18.5 GiB，且每专家 token 数 64 -> 320，算力与占用率一起上去。
   算术上专家腿从 1.54 s 降到 max(1.37 s PCIe, 5.6 s 算力@3.7 TFLOPS) = 5.6 s -> **1830 tok/s**；
   算力若因占用率上去到 6.1 TFLOPS 则是 3.4 s -> 3000 tok/s。
3. MoE 输出累加、输入 Q8_1 量化上 GPU（数值路径收尾）。

## 41. M2-5 第七步判决：层优先跨 chunk 采纳，专家腿 3436 tok/s（2026-10-25）

| 项 | 结果 |
|---|---|
| 10K prompt 的专家腿 | **2976-2980 ms -> 3436-3441 tok/s**（chunk 优先约 1190） |
| 专家搬运 | 92.5 GiB -> **18.5 GiB/prompt** |
| 算力 | 3.7 -> **7.09-7.10 TFLOPS**（每专家 token 64 -> 320，网格 16 -> 80 workgroup） |
| 与目标 | design 的 0.85 x roofline = 7.06 TFLOPS，专家腿已达到；但整体 PP 还要加注意力与稠密 |

**为什么这个改动是设计要求的、而不是投机**：design 4.5 原文"每层的专家只读一次"，
而 chunk 优先的实现每层读 5 次（10K prompt）。这一步把实现拉回设计，同时把"占用率"这条
潜在收益一起吃掉——两者是同一个改动的两个结果，所以收益是 2.9 倍而不是 17%。

**代价与约束（都已满足）**

1. 激活要按"层 x 整 prompt token"排布：每专家 320 token 的 Q8_1 平面 = 320x2048 = 640 KiB/专家，
   256 个专家 = 160 MiB（在 hb 平面里，已算进 alloc）。
2. 每层计算时间变长（28 -> 约 32 ms/层 @7.1 TFLOPS for 320 token... 见 RESULTS 44），
   上传被完全藏住：upload 只有 50 ms/1317 次拷贝。
3. KV/注意力仍按 chunk 走（M2-6 的形状），不冲突：本节的循环顺序只改"层内怎么切 token"。

**未结项**

1. **注意力与稠密**：整模型 PP 缺这两块（M2-6 之后）。
2. **read 与 compute 各占一半**：read 1572 ms（13.0 GB/s）与 compute 1330 ms 现在几乎等高，
   要再快得两条腿一起动；第 43 节的"解耦读取与 H2D"仍没做。
3. MoE 输出累加、输入 Q8_1 量化上 GPU（数值路径收尾）。

## 42. M2-6 切分与第一步判决：稠密投影是 PP 的最大一条腿（2026-10-25）

**判决**：M2-6 保持 doing，切成四块，因为形状账（RESULTS 45）证明它不是"一个注意力内核"能收口的：

| 子任务 | 内容 | 依据 |
|---|---|---|
| **M2-6b** | Q8_0 x Q8_1 GEMM（稠密投影） | 30.9 TFLOP，50%，且现有 int8 GEMM 只覆盖 Q4_K/Q5_K/Q6_K |
| **M2-6c** | DeltaNet：conv1d(4) + L2 norm + 递推 + gated RMS norm | 30 层，串行，1.6 MFLOP/token 但时延敏感 |
| **M2-6d** | full-attn：per-head RMS norm + IMRoPE + flash 因果 + sigmoid 门 | 11 层，9.45 TFLOP |
| M2-6a | KV q4_0 + 16K 窗口（已有） | 依赖 M2-6d 的 KV 形状 |

**为什么先切不做**：原任务 done_when 是"k=1 prefill 与参考一致"，那需要四条腿全部落地；
而形状账显示其中 50% 的算力压在**一个还没写的 Q8_0 内核**上。按"不留半成品"的约定，
本轮只交付可复核的形状账（`bench/tools/attn_account.py`，纯形状乘积、无实测），把内核工作登记成子任务。

**这一步暴露的三个事实**

1. **稠密投影（30.9 TFLOP）比路由专家（21.1 TFLOP）还大**。之前所有 PP 讨论都只盯着专家腿，
   这是口径上的漏洞，已写进 design 4.5。
2. 稠密权重是 **q8_0**（8.5 bpw），现有 GEMM 的三种 K-quant 变体一个都吃不了；
   这一块不写，PP 就只能永远按"假设 6 TFLOPS"估。
3. 按 6 TFLOPS 的稠密速率，PP 只有 **1055 tok/s**，对 1000 的余量 5%。要站稳 1000，
   稠密腿实测必须 >= 6 TFLOPS；如果只有 5，就是 970 tok/s，不达标。**这是 PP 的真实风险点。**

**下一步**：M2-6b（Q8_0 GEMM）——它是唯一一个"不做就算不出 PP"的内核。做完它，
稠密腿就能像专家腿那样有实测速率，PP 口径才算真正闭合。

## 43. M2-6b 判决：Q8_0 内核正确但太慢，PP 的绑定腿换成了稠密投影（2026-10-25）

| 项 | 结果 |
|---|---|
| 正确性 | rel_L1 **1.297e-7**（阈值 1e-5），PASS |
| 速率 | M=1024/2048 是 2.12-2.17 TFLOPS；**M=10240（真实形状）只有 1.10** |
| 对 PP | 稠密按实测速率算，PP 从 1055（假设 6 TFLOPS）掉到 **258-474 tok/s** |
| 结论 | **PP 1000 的绑定腿已经从专家腿换成稠密 GEMM**，差距 4-6 倍 |

**判决**：M2-6b partial。内核进运行时、可校验、可按任意 M 计时，但效率不达标，
不能拿去算 PP。`--dense-gemm-check` 作为它的回归入口保留（正确性 + 速率一条命令）。

**为什么这不是"设计问题"而是"内核工程"**：形状是标准的（N=8192、K=2048、M=10240），
比专家 GEMM 更规整；差的是数据布局（34 字节非对齐块 + 行距 40 KiB 的输出）与 tiling。
M2-4 在 Q4_K 上把 3.66 -> 6.08 靠的就是"激活分平面"，同一招在这里还没用上。

**未结项**

1. **权重平面预打散**（下一轮的第一条）：加载时把 34 字节块拆成 qs/ds 两平面，内核用对齐 `uvec4`。
2. 输出布局与 K 分块（见 RESULTS 46）。
3. Δ 之后才是 DeltaNet（M2-6c）与 full-attn（M2-6d）：在稠密 GEMM 达标前，
   它们即使完美，PP 也上不去——因为它们同样依赖稠密投影的吞吐。

## 44. M2-6b 第二步判决：平面重排 +23%，但离 PP 还差一个 LDS 分块（2026-10-25）

| 项 | 结果 |
|---|---|
| 预打散成对齐平面 | M=2048/4096 **2.64-2.68 TFLOPS**（原 2.17，+23%） |
| 真实形状 M=10240 | 1.18-2.11（不稳定），仍是大 M 更差 |
| 否决项 | group_m 轮转（权重 L2 复用）反而更慢，已回退并记录 |
| PP 推算 | 2.65 TFLOPS 时 **563 tok/s**；要 1000 需约 6 TFLOPS |

**判决**：M2-6b 继续 partial。平面重排 adopt（正确性不变、+23%、内存 +6%），
但当务之急不是继续微调，而是两件事：

1. **调度层（便宜）**：层内把稠密投影切成 <=4096 token 的子批，避开大 M 的退化。
   预期把稠密腿从 1.6-2.1 的抖动区拉回稳定的 2.65。
2. **内核层（贵但必须）**：给 GEMM 加 LDS 分块（权重/激活先搬共享内存再复用）。
   这是 pp 1000 的唯一出路：2.65 x 2.3 = 6.1 TFLOPS。

**为什么不再试小改动**：本轮已经排除了"权重重复读"（加宽 token tile 无效）和"L2 复用顺序"
（轮转更慢），剩下的差距只能靠提高每次读的复用次数，也就是共享内存分块。按 AGENTS 第 8 节，
这属于"同一任务第 3 次尝试前先写排查计划"，计划已写进本节。

**未结项**

1. LDS 分块 GEMM（M2-6b 下一条，独立可验证：同一 `--dense-gemm-check` 看 TFLOPS）。
2. 层内稠密子批调度（顺手可做，等内核定型后一起量）。
3. DeltaNet（M2-6c）与 full-attn（M2-6d）仍待做；它们同样受稠密 GEMM 吞吐制约。

## 45. M2-6b 第三步判决：瓶颈是 q8_0 的位宽，不是 tile 也不是 L2（2026-10-25，更正第 45 节第一版）

**更正**：第 45 节的第一版据一张 6 组 tile 的表格断定"LDS 分块是唯一出路"，那张表是无效的
（切换 CMake 变量时 ninja 复用了旧的 `.spv`）。已验证的对照见 RESULTS 48：

| 对照 | 结果 |
|---|---|
| rows 2 -> 8（激活加载喂 2 行 -> 8 行） | 3.44 -> **3.52**（+2%），激活重复读不是瓶颈 |
| 工作集 30 MB（超 L2） -> 1.1 MB（落 L2） | 2.64 -> **3.50**（+33%），L2 只影响 1/3 |
| q8_0 vs Q4_K（同为 int8 点积内核） | **3.5 vs 7.1**，即每字节 MAC 数减半 |

**判决**：稠密腿 3.5 TFLOPS 已经接近 q8_0 的位宽上限（int8 ALU 8.67 / 2 = 4.3，达 81%）。
**LDS 分块被撤销为"未验证的假设"**，不再作为既定下一步——它最多补 L2 那 33%，
而且省下的重复读已被 L2 吸收。

**修正后的 PP**：稠密 11.5 s + 专家 2.98 s = 14.5 s -> **706 tok/s**（第 45 节写的 1055 是假设 6 TFLOPS 得来的，作废）。

**三条路（都需要用户决策，见 RESULTS 48 D）**

1. 保位宽：PP 约 706 是这条路线下的上限附近；要 1000 必须动稠密 FLOPs 或位宽。
2. 算法：DeltaNet 的 qkv+z 合并（一次 12288 宽投影代替两次），省 5-8% 稠密 FLOPs，不变量化。
3. 位宽：稠密权重再量化到 4-bit —— **改变数值，违反 design 1.2，必须用户批准并先过 KLD 门**。

**未结项**

1. 稠密 GEMM 与位宽上限之间还有约 20%（3.5 vs 4.3），是否值得继续挖需要 profiler（本机无 RGP）。
2. M2-6c/6d 仍未做；它们受同一条稠密腿约束。

## 46. M2-6b 第五步判决：LDS 分块无效，稠密腿的瓶颈在量化位宽（2026-10-25）

| 尝试 | 结果 |
|---|---|
| q8_0 预打散成对齐平面 | 2.17 -> 2.65（**+23%，唯一有效**） |
| group_m 轮转 | 更慢（1.62 -> 1.14） |
| tile 形状（rows 2/4/8、tokens 8/16、wg 128/256） | 2.60-2.66，无效 |
| **LDS 分块（4x8 寄存器块 + 激活面板进共享内存）** | **2.64 / 3.50，与旧版持平** |

**判决**：M2-6b 的内核路线走完了。稠密 q8_0 GEMM 在本机是 2.6-3.5 TFLOPS，
已达"q8_0 每字节 MAC 数减半"前提下的 81%（上限约 4.3）。代码保留 LDS 版本
（等价且结构更清晰），旧版在 git 历史里可回退。

**PP 的结论（需要用户拍板）**：按实测，稠密 30.91 TFLOP / 3.5 = 8.8 s、注意力 9.45 / 7 = 1.35 s、
专家 2.98 s -> **约 780 tok/s**；即使注意力再快也只是 800 上下。**PP 1000 在"q8_0 稠密 +
int8 点积"路线上不可达**，要过线必须改变稠密的数值方案（4-bit 重存，用户已否决）或
减少稠密 FLOPs（qkv+z 合并只值 5-8%）。

**未结项（留给用户决策）**

1. 接受 **~780 tok/s** 并把 design 的 PP 目标按 U-2 改成实测可达值（需要用户改 design）。
2. 重新考虑稠密的数值方案（4-bit 或其他），这需要先有 KLD 门（M2-7 + X-1）来量化质量损失。
3. 把稠密投影放到 CPU 上跑的方案不值得（CPU 约 0.1 TFLOPS 量级，稠密 30.9 TFLOP 要 300 s）。

## 47. X-1 判决：质量门工具成形，参考基线落盘，rt 侧只差 qrt 的 logits 出口（2026-10-25）

**改了什么**：`bench/tools/quality/`（路径 `bench/tools/quality/**`）：

| 文件 | 作用 |
|---|---|
| `logitio.py` | 两套转储的流式读写：fork `--save-all-logits`（u16 量化 log-prob）与 rt fp32 |
| `metrics.py` | PPL / mean KLD / same top-1 / 首次分叉 + margin / `verify_dump` 结构自检 |
| `qgate.py` | `ppl` / `compare` / `verify` / `convert` / `selftest` 子命令，退出码 0/3/2 |
| `selftest.py` | 9 项合成自测（不需模型） |
| `reference.ps1` | `llama-perplexity` 封装，一条命令产参考转储 |

**判决**
1. **采纳**：一条命令出 `PPL | mean KLD | same top p | PASS/FAIL`，满足 X-1 的 done_when。
   自测 9/9；真跑区分度成立（同配置 KLD 0 / PASS；`-fa on/off` KLD 1.47e-2 / FAIL）。
2. **口径判决**：KLD 与 PPL 都在"保留词表"上重新归一（fork 的 16 nat 地板会给尖峰行凭空加

   **这条口径对 M2-7 强制生效**，不许用 fork 打印值直接当门禁读数。
3. **采纳**：判决规则 = token 流一致 + `mean KLD <= 1e-4` + top-1 分叉只允许出现在 margin `< 0.05`
   的位置（U-7 的直接落地）。分叉率与分叉处 margin 作为必报列。
4. **未结项（不影响 M2-7 起步）**：rt 转储要等 qrt 有 logits 输出；工具侧不再改，
   格式见 `bench/tools/quality/README.md` 第 3 节。
5. **证伪**：`-t` 不是这个模型的扰动源（5 vs 8 线程转储逐字节相同）。想在参考侧造"近似但不相同"的
   对照，只能换数值路径（如 `-fa on/off`），不能换线程数。

**与已有条目的关系**：第 16 节 M1 评审里"`k=1` 路径另测 logits KLD"与本节共用同一套工具；
第 45 节"要动数值方案就得先有质量门"的产品级结论，现在有了可执行的判据。
`bench/README.md` 第 2 节"正确性判据与速度分开报"里的 KLD 一栏从此有脚本，不再是手工步骤。

**开关**：无新增运行时开关。`reference.ps1` 的 `-Ctx/-Batch/-Chunks/-Threads/-Fa/-Ncmoe/-Extra`
只影响参考侧转储，不进入 qrt。

## 48. M2-6c 第一步判决：DeltaNet 递推核正确且状态可比特，但速度只用掉预算的 1.09x（2026-10-25）

**改了什么**：`runtime/attn_deltanet.{h,cpp}`（内核驱动 + 双精度 CPU 参考）、
`runtime/attn_deltanet_check.cpp`（`qrt --deltanet-check`）、`runtime/kernels/deltanet_recur.comp`；
`qrt_main.cpp`/`qrt_config.cpp`/`CMakeLists.txt` 接线；`vk_dev.{h,cpp}` 增加
`subgroup_size` 与 `has_subgroup_arithmetic`（`--vk-info` 里可看）。

**判决**
1. **采纳**递推实现：GPU 对 CPU 双精度参考 `rel_L1 = 2.3e-07`（门限 1e-4），状态
   `2.5e-07`；状态保存/恢复与串行解码对批量**逐位相同**，所以 M3 的串行解码可以复用同一内核，
   不需要第二套实现。
2. **口径**：token 循环放在 shader 内（每 workgroup 一个 v-head 的列组，状态常驻寄存器），
   这是"批量 == 串行"能够逐位成立的唯一原因；一旦改成 token 并行的 chunked 形式，
   这个等价性就要重新验证（允许 fp 级差异，但要按 X-1 的 U-7 口径报分叉）。
3. **partial 的原因（性能）**：4.75-4.83 us/token，30 层 10K = **1.46-1.48 s**，而第 45 节给整条
   attention 腿的预算只有 1.35 s，单 DeltaNet 就 1.09x 超了；折算 655 GFLOPS，只有绑定腿的 9%。
   理想 0.32 s。**下一步先做 token 并行（chunked/WY 或一头一 workgroup 全 128 列），
   再谈 conv1d/投影/gated norm 的接线**，否则接完也过不了 PP。
4. **证伪**：不能按 32 写死 lane 组。本机 subgroup 是 64，写死 32 时 `rel_L1 = 1.036` 且**不报错**，
   只是全错。subgroup size 现在从设备属性读、作为 specialization constant 传入，且与 `head_dim`
   不整除时直接拒绝。**这条对其他内核同样适用**（ggml 那边靠 `USE_SUBGROUP_*` 编译开关规避）。

**遗留（进 M2-6c 第二步）**：conv1d(4)+silu、L2 norm、`ssm_alpha`/`ssm_beta`/`ssm_dt` 投影、
gated RMS norm + `ssm_out`，以及整层对 CPU 参考的端到端比对。并行化提速单独立项，
因为它是"能不能到 PP 目标"的分水岭。

## 49. M2-6b 第六步判决：稠密 GEMM 是"指令/发射"受限，不是权重带宽受限；下一步换内层形状，不动数值方案（2026-10-25）

用户 2026-10-25 的指令：稠密是最大的一块（30.9 TFLOP、11.5 s of 16 s），先解决它。
M2-6b 重新打开。第 43-46 节把四个微优化都试过了，本节只回答一个问题：**墙在哪**。

**已证伪**
1. **权重带宽不是墙**。折算有效权重速率 39-59 GB/s，只有读上限 156.5 的 25-38%；
   把 `TOKENS` 8 -> 16 让权重流量**减半**，速率从 3.35-3.43 变到 3.37 TFLOPS（没变）。
2. **tile 形状不是墙**（第 48 节已扫过 rows 2/4/8 x tokens 8/16/32），**LDS 分块也不是**（第 50 节）。
   这两条的失败原因现在有了共同解释：它们都在改数据流，而瓶颈在算术发射。

**仍未定**
- **(H2) dot4 发射率**：若 `sudot4` 在本机是 2-4 拍/条，上限就是 7-14 TFLOPS，实测 3.37 是它的 24-48%。
- **(H3) 内层形状**：现在是 4 行 x 8 token/ lane、每行 8 条独立 `uint` 加载；专家核是
  2 行 x 8 token 且权重按 superblock 一次 `uvec4` 读。同一个 dot4 在专家核上有 **6.08-6.20 TFLOPS**，
  是稠密的 1.8x。**这条差异是当前最大的已知可回收量。**

**计划（下一步，单变量，按代价排序）**
1. **D-1（本轮之后立刻做）**：把稠密核的内层形状对齐专家核 —— 权重一次 `uvec4` 读 16 字节（而不是
   8 条 uint）、行块按 2 行/lane 组织、K 面板加深到 256。目标：先看 3.35 -> 是否到 5。
   若到 5，done_when 就满足；到 6 就与专家核同档。
2. **D-2（若 D-1 不足）**：直接测 dot4 的发射率（一个只做 dot4、不读内存的微核，r=5），
   把 H2 变成数字。这条决定 5 TFLOPS 是不是硬上限：如果 dot4 只有 3.5 TMAC/s，上限 7 TFLOPS，
   5 仍可达；如果只有 1.75 TMAC/s，则必须换数值方案（那就回到用户手里，不许自行动）。
3. **D-3（D-1 有收益后再叠加）**：权重按"块主序"重排，把 128 行 x 128 元素的块存成连续区，
   让一个 wave 读连续的 4 KiB。这条只改加载布局，不改数值。

**目标数字**：`N=8192 / K=2048 / M=10240 >= 5 TFLOPS`（M2-6b 的 done_when）。
按 5 TFLOPS 反算，稠密腿从 11.5 s 降到 **6.2 s**，PP 从约 620 提到 **约 780-800 tok/s**；
若到 6.2（专家核同档），稠密 5.0 s，PP 约 **850 tok/s**。**PP 1000 仍然要动数值方案，那不是本任务。**

## 50. M2-6b 第七步（D-1）判决：内层形状无效，下一招是块主序权重重排（D-3），仍是纯布局改动（2026-10-25）

**改了什么**：`runtime/kernels/gemm_q8k.comp` 换成专家核的内层形状：2 行 x 8 token/lane
（16 个累加器，原来 32 个）、权重一次 `uvec4` 读 16 字节（原来每行 8 条 `uint`）、
K 面板 128 -> 256（barrier 与激活暂存各摊薄一半）、每面板的 8 个 f16 delta 一次 `uvec4` 读齐。
正确性不变（`rel_l1 = 1.297e-07`）。

**判决**
1. **D-1 无效**：3.35-3.43 -> 3.38 TFLOPS。保留新版（寄存器更少、指令更省），但它不是解。
2. **D-2（dot4 发射率）暂时不必做**：专家核跑 6.08-6.20，说明这条指令通路的可用上限至少 6，
   5 TFLOPS 的门槛不是被指令调幅挡住的。真要做也是为了给 D-3 之后的新天花板定位。
3. **采纳新画像**：稠密核受"散列读延迟"限制，不是带宽也不是发射率。三条读数的组合
   （流式 3.38 / L2 常驻 4.34 / 专家核 6.2）只有延迟+局部性这一种解释能同时对上。
4. **下一步单变量 D-3**：加载期把权重按 **块主序** 重排 —— `[行块 128][k 面板 128]` 的
   16 KiB 连续块，wave 内 32 条 lane 读连续 4 KiB 而不是 32 个散点。预期：把 3.38 推到
   4.3-6 之间（对照 L2 常驻的 4.34 与专家核的 6.2）。**不改数值方案、不改量化格式**。
   若 D-3 后仍 < 5 TFLOPS，那时才需要用户就数值方案拍板（第 46 节的结论在 D-3 之后才成立）。

**纪律**：这是 M2-6b 的第 7 步、第 6 个失败/半失败的假设。已按第 8 节要求把失败假设与排查计划
写在这里；D-3 是最后一次"纯布局"尝试，再无效就走 D-2 的数值上限测量，不再继续盲试。

## 51. M2-6b 判决：块主序重排达标，3.38 -> 12.89 TFLOPS，稠密线关闭（2026-10-25）

   需要用户确认是否改成按 int8 指令率折算。agent 不改 design。

### 53.1 v 段第 3 次尝试失败后的失败假设与排查计划（2026-10-25）

**现象**：q/k 逐元素 5e-06 对上；v 段 `rel_L1 = 47.7`。第 3 次检测（把 v 平面逐通道对"用同一份
输入算出的 CPU conv"比对）给出 `v_worst_diff = 2.59`：GPU 2.597 对 CPU 约 0.003——**CPU 侧的四点
卷积比 GPU 小三个数量级**，而两边的公式与索引写法完全一致。

**失败假设（按可能性排序，每条一个检测就能判定）**

1. **两侧读到的权重不是同一份数据**（设备缓冲与主机副本在某段之后不同）。检测：把
   `cw[4096..4223]` 与核内读同一区间的结果各打印 8 个数。
2. **`stb.st`（conv 历史状态）绑定到了错的 buffer**：prep 的 binding 2 若落到别的缓冲，三个历史
   tap 全错；而 q/k 因为做了 L2 归一化，"全错的方向"会被照成单位向量——**归一化掩盖幅度错误**。
   这正好解释"q/k 对、v 不对"，也是唯一能同时对上两边现象的假设。检测：把状态清零再跑，
   q/k 若仍然对上就说明状态根本没进内核。
3. **v 平面下载读错 buffer**：确认 `b->v` 与 prep 写入的 `dn->bufs.v` 是同一个句柄。

**计划**：下一轮按 1 -> 2 -> 3 各做一个检测（每次一次编译一次运行），不再盲改代码。
在 v 归零之前，M2-6c 的 prep 环节保持 `PARTIAL(v-open)`，不计入退出码。

## 54. 规约改动：尝试额度 3 -> 5，但加上"不许盲试"的四条硬约束（用户 2026-10-25）

用户要求放大尝试额度，并明确"要吸取教训而不是盲目尝试"。`AGENTS.md` 第 8 节已改，落地为四条：

1. **额度**：同一任务第 5 次尝试前写失败假设 + 排查计划（原 3 次）。
2. **每次尝试必须写明它证伪什么、产出什么证据**：没有可证伪命题的改动不算一次尝试，不许占用额度。
3. **同一族假设不许连试两次**：同一个变量的同方向微调（例如"再换个 tile 形状""再把面板加深"）
   试过一次就必须换族；连续两次拿不到新读数即判为无效尝试。
4. **归因硬件前先排除内核结构性问题**：`RESULTS` 第 51-55 节就是反例——六次微优化全部建立在
   "稠密上限 3.5 TFLOPS"这个错误读数上，真正的原因是权重读请求散列；块主序重排一次就到 12.89。

**本仓库已经付过学费的三条教训，写在这里供每次尝试前对照**
- **归一化会掩盖错误**：q/k 做了 L2 归一化，幅度错三个数量级仍能"对上"（DECISIONS 53.1）。
  凡是归一化之前的中间量，必须留一个不做归一化的对照。
- **在旧实现上量出来的"上限"不是硬件上限**：先把数据流/访存模式弄清楚，再谈天花板。
- **共用资源（pipeline layout、push 常量范围、描述符集）出错时的症状是静默崩溃或无输出**：
  这类基础设施问题要先排除，否则会把时间花在算法上（本轮 0xC0000005 就是 push 范围 20 B vs 32 B）。

**没有变的**：失败必留"复现命令 + 已排除项 + 下一步判据"三样；8 类必须停下来问用户的事项照旧。

## 55. M2-6c 第二步判决：prep 三段达标，两个基础设施缺陷入账（2026-10-25）

**采纳**：`conv1d(4) + silu + q/k/v 拆分 + 每头 L2 norm` 对双精度参考 rel_L1 <= 6.4e-08
（门限 1e-4），含非零 conv 历史；0.26 ms/256 token。

**两个缺陷（已在代码里修掉，且都写成常驻约束）**
1. **push 常量结构必须与 host 逐字段一致**。shader 多一个 `vbase` → 36 B vs 32 B →
   shader 把 `l2_eps` 的位当偏移，写越界，**且不报错**。约束：共用 layout 的模块，
   struct 字段数/顺序在两边注释里点名"必须一致"，并用常量模式的检测兜住。
2. **shader 的拷贝不能挂在 exe 的 POST_BUILD 上**。只改 shader 时 exe 不重链接，拷贝不触发，
   跑的是旧 SPIR-V。现在 `qrt_spv_copy ALL` 独立 target，依赖全部 spv。**这条对后续所有内核都适用**，
   也是"改了没效果"类问题的第一嫌疑人。

**方法论**：本轮按第 54 节的规约，每次检测都先写"证伪什么"。真正定位靠的是**零数据依赖的常量模式**
（权重=1、输入=1、状态=0）：它把"数据错"和"通路错"分开，一步排除了权重、状态、索引三类嫌疑。
这条检测保留在 `--deltanet-check` 里作为常驻回归。

## 56. M2-6c 判决：gate 正确性达标、形状待优化（2026-10-25）

**采纳**：`deltanet_gate.comp` 与双精度参考一致（decay 1.36e-08、beta 1.24e-07），

**顺带记录**：本轮把 gate 的权重（alpha/beta/dt/a）纳入 `qrt_dn_weights`，并新增
`qrt_dn_weights_host()` 供双精度参考读取；`qrt_dn_bufs` 增加 `norm`（RMS norm 输出，gate 的输入）。
