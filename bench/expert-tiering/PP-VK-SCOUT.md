# PP expert-layer prefetch on the Vulkan transfer queue - code scout

Date 2026-10-21. Read-only audit of ggml-backend.cpp, ggml-vulkan.*, llama-context.cpp, llama-moe-cache.cpp. Target RX 6700S, backend Vulkan1, single device. No code changed. Lines are this checkout (E:\fastLlama).

## Q1. Scheduler copy callback timing

- Callback invoked in `ggml_backend_sched_copy_input` at `ggml-backend.cpp:1936-1942`: `sched->callback_copy(split_backend, input, input_cpy, &split->graph, ...)`; contract `ggml-backend.h:325-332` ("called after all non-weight inputs ... copied"). Host weights are the pass-1 copies, `ggml-backend.cpp:2017-2058`.
- Splits are submitted immediately, not batched until the end: loop `ggml-backend.cpp:1999-2120`, each iteration copies then calls `ggml_backend_graph_compute_async(split_backend, &split->graph)` at `2074`; `llama-context.cpp:2845` drives the whole graph with one async call, so every split is queued in that single pass.
- When the callback for split L runs, compute L-1 was submitted at line 2074 of the previous iteration. In this config it has also completed on host: before the callback, `1934` calls `ggml_backend_sched_wait_backend`, and `1906-1913` does `if (events != NULL) event_wait(); else ggml_backend_synchronize(backend);`. Events exist only when `n_copies > 1` (`2157`), i.e. pipeline parallel, which requires `n_devices > 1` (`llama-context.cpp:584-590`); on one GPU `sched_new(..., false)` (`llama-context.cpp:830`) leaves `events == NULL` (`ggml-backend.cpp:2190-2194`). So the scheduler host-drains the GPU before every host-weight copy (this is the drain in L8 section 3; the racy skip probe reached 797 t/s).
- Second drain per MoE layer: ids readback at `llama-context.cpp:2913-2915` (`get_async` + `ggml_backend_synchronize`). Whole-layer prefetch needs no ids, so both drains can be removed on that path.

## Q2. Vulkan async upload path

- Trace: `ggml_backend_vk_set_tensor_async` (`ggml-vulkan.cpp:13451-13454`) -> `ggml_backend_vk_set_tensor_2d_async_impl` (`13390-13448`) -> `ggml_vk_buffer_write_2d_async` (`ggml-vulkan-buffers.cpp:516-582`).
- (a) Submission: the set path only records; nothing is submitted there. `ggml_vk_submit_transfer_ctx` (`ggml-vulkan.cpp:5931-5972`) ends the ctx, runs deferred host memcpys (`5942-5944`), bumps+signals `transfer_semaphore` (`5946-5947`) and calls `ggml_vk_submit(cpy_ctx, {})` (`5949`). All call sites: `13603` (synchronize), `14452` (start of graph_compute), `15315` (event_record). A callback batch is therefore submitted at the next graph_compute, just before compute of the same split, and drained at the next synchronize.
- (b) Pinned source: `ggml_vk_host_get(dst->device, src, ...)` (`buffers.cpp:519-521`, impl `368-397`). For a tracked host allocation it records one `copyBuffer` with per-row slices and returns true (`523-543`); the staging branch at `546-581` is skipped. `Vulkan_Host` buffers come from `ggml_vk_host_malloc_on_device` (`305-340`), which creates a host-visible VkBuffer as the "pinned" allocation and sets `entry.views[device->idx] = buf` (`335`), so no external-pointer import is needed (AMD import is disabled at `ggml-vulkan.cpp:4035-4038`, but only the multi-device path `buffers.cpp:380-392` uses it). Host experts really live there: `bench/expert-tiering/ab-on.log.err:242` "overridden to Vulkan_Host".
- (b) Size limit: none on the direct path; a 466 MiB layer is one copyBuffer. If the source is not a tracked allocation, write_2d_async returns false and `set_tensor_2d_async_impl` allocates `ctx->sync_staging` for the full size then calls `ggml_vk_synchronize(ctx)` (`13419-13448`, sync at `13447`). `ggml_vk_ensure_sync_staging_buffer` (`buffers.cpp:409-417`) creates a host-visible+coherent+cached VkBuffer of the requested size and keeps it: a second 466 MiB VRAM buffer plus a full device wait. Avoid this path; other users of the staging buffer are `buffers.cpp:488,553,675`, `ggml-vulkan.cpp:13492`.
- (c) Destination offset: `dst_offset = vk_tensor_offset(tensor) + tensor->view_offs + offset;` and `vk_buffer buf = buf_ctx->dev_buffer` (`ggml-vulkan.cpp:13413-13415`), so views and sub-ranges work. All set_tensor_async calls issued before the next submit append to the same transfer ctx (`13407-13408`); copyBuffer takes a multi-slice `std::vector<vk::BufferCopy>` (`buffers.cpp:525-538`), so 3 tensors = 3 copy commands plus barriers (`540`) in ONE command buffer and ONE queue submit (transient one-time-submit pool, `types.h:1019-1027`, `ggml-vulkan.cpp:5809-5818`).

## Q3. Semaphore / fence primitives

- `struct vk_semaphore { vk::Semaphore s; uint64_t value; }` (`ggml-vulkan-types.h:1068-1071`), created as timeline semaphores: transfer pair `ggml-vulkan.cpp:5532-5539` (value 0), events `16263-16266`, gc semaphores `1095-1105`.
- `transfer_semaphore` (`types.h:1257`, `last_submitted` `1258`): +1 per submitted transfer batch and signaled (`5946-5947`); waited by compute in `ggml_vk_get_compute_ctx` when `last_submitted < value` (`5881-5885`, which also advances it), and by the empty compute submission in `ggml_vk_synchronize` before the fence (`13634-13647`).
- `transfer_semaphore_deferred` (`types.h:1261-1264`): same mechanism (`5963-5966`), waited only when `wait_deferred_pending` is set (`5886-5893`); the flag is set by `ggml_backend_vk_wait_deferred` (`13466-13469`) from the pre-split hook (`llama-context.cpp:787-792`, hook at `ggml-backend.cpp:2067-2069`); used only by `LLAMA_MOE_DEFER_UPLOAD` (`llama-moe-cache.cpp:1132-1146`).
- `ctx->fence` (`types.h:1230`, created `5528`): single binary fence per backend context, submitted only in serialize mode/synchronize/perf logger (`ggml-vulkan.cpp:12986,13622,13646,13649,14877`). `ggml_vk_wait_for_fence` (`339-378`) waits `almost_ready_fence` first, then spins `getFenceStatus` and resets: a full-device drain, not a per-work signal.
- `ggml_vk_submit` (`902-977`): one SubmitInfo per queued submission with TimelineSemaphoreSubmitInfo wait/signal lists, waits always use `ctx->p->q->stage_flags` (`944`), one `q->handle->submit(...)` (`974`), then `ctx->seqs.clear()` (`976`).
- Host wait for transfer only: absent. The only host timeline wait is `ggml_backend_vk_device_event_synchronize` (`16302-16305`): `vk::SemaphoreWaitInfo swi{...}; device.waitSemaphores(swi, UINT64_MAX);` plus command-buffer recycle by `use_counter` (`16314-16322`). Copy this pattern.
- Compute-completion timeline/counter: none. `vk_event::tl_semaphore` (`types.h:1079`) increments per `event_record` (`15337-15341`) but exists only when the scheduler has events, i.e. `n_copies == 4` (pipeline parallel), impossible on one device. There is nothing to snapshot today.
- Only compute<-transfer sync: `5881-5885` (plus the same semaphore in `13634-13647`). `event_wait` is the opposite direction, transfer<-compute (`15359-15362`).

## Q4. Minimal patch sketch (design only)

1. `ggml-vulkan-types.h`, `ggml_backend_vk_context` after `1254-1266`: add `vk_semaphore compute_semaphore{};` `vk_semaphore prefetch_semaphore{};` `vk_context_ref prefetch_ctx;` `bool wait_prefetch_pending {};` `uint64_t prefetch_wait_value {};` plus recycle fields like `vk_event` (`1079-1081`): `vk_command_buffer * prefetch_cmd_buffer; uint64_t prefetch_cmd_buffer_use_counter;`. For a llama-visible API mirror `ggml-backend-impl.h:158-161` + `ggml-backend.h:98-101` (deferred copies); a Vulkan-only helper called from llama code is smaller.
2. `ggml_vk_init` `5510-5542`: create both timeline semaphores with the code at `5533-5535`, guarded by `async_use_transfer_queue`; destroy in `ggml_vk_cleanup` `13088-13094`.
3. `ggml_vk_submit` `902-974`, single choke point before the SubmitInfo loop: if this ctx belongs to the compute queue and async transfers are on, `ctx->compute_semaphore.value++; ctx->seqs.back().back().signal_semaphores.push_back(compute_semaphore);`. This covers every compute submit site: `12986,12988,12991` (per-batch compute_forward), `13622,13626` (synchronize), `14877` (perf logger), `15341` (event_record), `12339` (prealloc flush), debug `ggml-vulkan-debug.cpp:183,387,663`. Detect with `ctx->p->q.get() == ctx->device->compute_queue.get()` (do not use `transfer_only`, which is false on the aliased queue too).
4. New functions, impl `ggml-vulkan.cpp`, decls `ggml-vulkan-common.h:69-95`: `uint64_t prefetch_begin(ctx)` returns `compute_semaphore.value` (host snapshot, no wait), creates `prefetch_ctx` on `transfer_cmd_pool` like `ggml_vk_get_transfer_ctx` (`5903-5915`), begins it, then pushes `{compute_semaphore.s, snapshot}` into `prefetch_ctx->seqs.back().back().wait_semaphores`; `prefetch_tensor(...)` = `ggml_vk_buffer_write_2d_async(prefetch_ctx, ...)` (`buffers.cpp:516`) per tensor into the ring; `uint64_t prefetch_commit(ctx)` ends the ctx, `prefetch_semaphore.value++`, appends the signal, `ggml_vk_submit(prefetch_ctx, {})`, resets the ref, returns the value, and must NOT touch `submit_pending` or `transfer_semaphore`; `prefetch_wait(ctx, value)` = host `waitSemaphores` (`16302-16305`) plus cmd-buffer recycle (`16314-16322`); `prefetch_wait_compute(ctx)` arms `wait_prefetch_pending` + value for the next compute ctx.
5. `ggml_vk_get_compute_ctx` `5879-5893`: third block mirroring `wait_deferred_pending` that pushes `{prefetch_semaphore.s, prefetch_wait_value}` into `result->s->wait_semaphores`. This supplies the memory dependency at wait stage `{eComputeShader|eTransfer}` (`4823`, propagated at `944`); a host wait alone orders execution, not visibility.
6. `ggml_vk_synchronize` `13631-13660`: host-wait the latest `prefetch_semaphore.value` before the fence submit (or add it to the wait list at `13640-13646`) so the fence and teardown cover prefetch; this must precede `ggml_vk_graph_cleanup` resetting the transfer pool (`13022-13025`).
7. `ggml-backend.cpp`: skip the drain at `1934` for callback-handled host weights. Smallest change: call `callback_copy` before `wait_backend` and return on true; safe because the ring slot replaces the gallocr dst (old reason for the drain is dst reuse across splits, comment `2004-2005`). `callback_split_pre` (`2067-2069`) is the place to arm the consumer wait (already used for deferred copies).
8. `src/llama-context.cpp` `sched_copy_experts` `2885-2983` / `llama-moe-cache.cpp`: return true early for ring-backed host weight tensors, skip the per-expert grouping (`2937-2974`) and the ids drain (`2913-2915`), issue prefetch L+1 in the first callback of layer L, and set the ring view as the split input.

Pitfalls:
- Do not reuse `transfer_semaphore`: `get_compute_ctx` would make compute L wait for upload L+1 (`5881-5885`).
- `submit_pending` drives `ggml_vk_synchronize` (`13631-13654`) and the idle heuristic (`13570-13573`); setting it from prefetch turns every per-split synchronize into a full transfer drain.
- `GGML_VK_SERIALIZE_SUBMISSIONS` (`4952`) fences and host-waits every compute batch (`12985-12986`, `14518-14532`), killing overlap; gate the feature off in that mode.
- Command pool reuse: the transfer pool is reset only inside `ggml_vk_graph_cleanup` after a full sync (`13012-13025`); buffers are allocated when all are `in_use` (`1114-1124`, `5798-5807`). Without the `use_counter` recycle each prefetch leaks a command buffer and the transient pool grows without bound.
- Descriptor sets: copyBuffer touches none; the hazard exists only if prefetch falls back to the compute queue (`async_use_transfer_queue == false`, `single_queue`, `4936-4939`), so reject that configuration.
- Semaphore values are monotonic and never reset (the transfer one is shared with the existing async path); never wait on a value above the last signal, and give the new counters their own 0-based semaphores.
- 2-deep ring: slot (L+1)%2 was last read by compute L-1, so the prefetch must wait on the compute-counter snapshot taken in the callback of L (after L-1 was submitted); do not snapshot after queueing compute L. Same-slot ordering between prefetches is guaranteed by the transfer queue itself.
- Ring cost 2 x 466 MiB = 932 MiB VRAM, which must come out of the MoE bank (`--moe-cache-mib 6144` is the measured max, L8 section 2) or resident layers. Upload is 466 MiB / 13.9 GB/s = 33.5 ms per layer vs 61 ms compute per layer, so a full-layer prefetch fits under compute and removes the used-expert compaction (about 75% of a layer for ub2048).

## Q5. Env knobs and queue selection

- `allow_graphics_queue` is only the env `GGML_VK_ALLOW_GRAPHICS_QUEUE`, `ggml-vulkan.cpp:4336-4337`: `const bool allow_graphics_queue = (getenv("GGML_VK_ALLOW_GRAPHICS_QUEUE") != nullptr);` `const vk::QueueFlagBits graphics_flag = allow_graphics_queue ? (vk::QueueFlagBits)0 : vk::QueueFlagBits::eGraphics;`. It makes the compute search avoid graphics families (`4338`) and the transfer search avoid compute|graphics (`4339`); it does not disable the graphics queue globally.
- `prefers_transfer_queue` (`4924-4929`): AMD && architecture != GCN && !uma && !allow_graphics_queue; `async_use_transfer_queue = prefers_transfer_queue || getenv("GGML_VK_ASYNC_USE_TRANSFER_QUEUE") != nullptr;` (`4935`). The env only forces it on; there is no off switch. `single_queue` (`4342`) aliases the queues and forces it off (`4936-4939`).
- This machine: `bench/expert-tiering/GATES.md:9` (vkgate info probe, same GPU/driver) reports compute family=1 (non-graphics), transfer family=2 (TRANSFER only, count 2), timeline semaphores available; therefore `single_queue == false`, `prefers_transfer_queue == true`, and `async_use_transfer_queue` is TRUE by default on Vulkan1.
- `GGML_VK_DEFERRED_COPIES` (`13404`): presence gate for set_tensor_async_deferred; the batch is submitted on the transfer queue but signals `transfer_semaphore_deferred` (`5963-5966`) and is waited only when `wait_deferred_pending` (`5886-5893`). Existing precedent for "submit transfer early, let a later split wait", but it still needs the ids drain and only defers one tensor.
- `GGML_VK_SERIALIZE_SUBMISSIONS` (`4952`): presence gate, forces fence waits per submit; incompatible with overlap.

## Q6. Compute submission waits and ordering hazard

- `ggml_vk_get_compute_ctx` runs on every graph node (`12416`) and at graph start (`14479,14491`), from `get_tensor_async` (`13483`), `cpy_tensor_async` (`13551`), `event_record` (`15317`), `event_wait` (`15353`) and the prealloc flush (`14558`); each call appends pending transfer waits (`5881-5885`) to the currently open submission (no duplicate once `last_submitted` has advanced).
- Transfer submitted after ctx creation but before its submission: the new value is not in that open submission's wait list, so that compute may run before the copy finishes. Existing code stays ordered by call order: graph_compute submits the transfer ctx first (`14452`), and event_record does too (`15315` before `15317`). Any prefetch path must keep this rule.
- Transfer submitted after the compute ctx was submitted: the next `get_compute_ctx` sees `last_submitted < value` and appends the wait, so a following submission catches it; with `n_copies == 1` there is no second compute ctx within a split, so there is no catch-up there.
- No implicit cross-queue ordering: without a semaphore wait (or a host wait plus a barrier) compute can read stale ring data. The scheduler's `overlaps_unsynced` logic (`ggml-vulkan.cpp:12424-12477`) only sees graph-node tensors, not transfer-queue writes, so it cannot protect the ring.

## Recommended design (smallest sequence)

Add 5 Vulkan helpers and 1 scheduler rule:
1. `prefetch_begin(backend) -> uint64_t compute_snapshot` (host read of the new compute timeline; no wait).
2. `prefetch_tensor(backend, ring_view, host_ptr, size)` (direct copyBuffer from Vulkan_Host; no staging, no size limit).
3. `prefetch_commit(backend) -> uint64_t prefetch_value` (submit now, signal the prefetch timeline).
4. `prefetch_wait(backend, prefetch_value)` (host wait on the prefetch timeline only).
5. `prefetch_wait_compute(backend, prefetch_value)` (device wait armed for the next get_compute_ctx).
6. Sched rule: call callback_copy before the drain at `ggml-backend.cpp:1934`, skip the drain when it returns true.

Ring: 2 slots x 466 MiB in Vulkan1 device buffers (not Vulkan_Host), 3 tensor views per slot (gate/up/down).

Host call sequence (slot of layer L = R[L % 2]):
1. Graph start: `prefetch_begin` (snapshot C0); copy layer 0 into R[0]; `prefetch_commit` -> V0; `prefetch_wait_compute(V0)`.
2. Copy callback of layer L (first invocation, dst name `blk.L.ffn_*_exps.weight`): (a) `prefetch_wait(V_L)`, which blocks only until upload L completed (upload L was issued during layer L-1 and overlapped compute L-1); (b) `C = prefetch_begin()`, whose counter includes all compute up to L-1 (submitted in the previous split); (c) copy the 3 tensors of layer L+1 into R[(L+1)%2] and `V_{L+1} = prefetch_commit()`; the batch waits on C, so it cannot overwrite the slot before compute L-1 finished reading it, and it starts when L-1 retires, overlapping compute L; (d) return true so the scheduler skips its own copy and the drain.
3. Pre-split hook of layer L (`ggml-backend.cpp:2067-2069`): `prefetch_wait_compute(V_L)`; the next `get_compute_ctx` attaches the wait, then compute L reads R[L % 2].
4. Repeat step 2 for every layer; at the last MoE layer skip 2c but still arm the consumer wait.
5. Graph synchronize/teardown: host-wait the latest prefetch value before the fence in `ggml_vk_synchronize`, then let graph_cleanup reset the pool; never reset while a prefetch is in flight.
6. Warmup: prefetch layers 0 and 1 synchronously (or accept the first two layers as non-overlapped).

Basis: overlap is already proven on this GPU (99.3% hidden, GATES.md Gate 2); the missing pieces are exactly the compute timeline counter and the removal of the pre-copy drain. Do not combine with `GGML_VK_SERIALIZE_SUBMISSIONS`.
