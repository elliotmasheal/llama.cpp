# 自适应重排：统计开关 + 重排命令（设计，2026-10-21）

目标：runtime 在正常使用中持续记录**按人、按负载**的专家使用权重（带时间衰减），用户随时执行一条命令即可
基于这些权重重排模型文件，越用越贴合自己的使用习惯。不依赖单一 bench 语料，也不需要用户手工挑选画像集。

## 1. 统计开关（已实现，M0 扩展）

| 环境变量 | 作用 | 默认 |
|---|---|---|
| `LLAMA_MOE_STATS=<path>` | 打开统计；路径为二进制统计文件 | 关闭 |
| `LLAMA_MOE_STATS_DECAY=<f>` | 每 token 的衰减系数，`0.999` 约 693 token 半衰期 | 0.999 |

实现位置：`src/llama-moe-cache.cpp`，在每次 MoE cache 查找回读 ids 后调用 `observe_ids()`。

语义：
- 每到一个新 token（层号回绕）先把全部权重乘以 decay，再给本层选中的专家 +1.0。
- 权重与 token 数按 `[n_layer][n_expert]`（本机 41 x 256）存成 f32 数组，文件头 `MOES`/version/n_layer/n_expert。
- 每 512 token 自动落盘一次，进程退出再落一次；只有真正记录过 token 的上下文才写盘
  （模型加载期的探测上下文不会清空已有统计）。
- Windows 上先删除旧文件再改名（`rename` 不覆盖）。

实测（Qwen3.6，`-ncmoe 41 --moe-cache-mib 6144`，两次会话共约 48 生成 token）：

```
layers: 41, experts: 256, total weight: 10722.6 -> 17782.3（第二次会话累积）
layer 10: gini=0.802 top8=0.330 top32=0.690
layer 20: gini=0.841 top8=0.431 top32=0.760
layer 35: gini=0.814 top8=0.336 top32=0.729
```

注意：样本很小，这些数字只证明设施工作；是否“显著偏斜且跨会话稳定”要看真实长期使用后的统计，
且不同用户/任务会得到不同排列——这正是这个开关存在的意义。

限制：
- 只统计**有 cache 查找**的层（整层驻留层不产生 ids 回读），prefill 不计入；这是 decode 使用画像，正合放置/重排的用途。
- 多 slot / 并发生成时，层号回绕判 token 边界可能误判，衰减会略微多算；对相对排序影响很小，后续可按 slot 分别计数。
- 统计文件不含任何文本内容，只有专家编号与权重。

## 2. 重排命令（已实现，2026-10-21）

实现：`tools/expert-repack/expert_repack.py`（Python，与 `convert_hf_to_gguf.py` 同类工具）。

```powershell
python tools\expert-repack\expert_repack.py ^
  --model F:\LLM\llm\Ornith-1.5-35B-Q4_K_M.gguf ^
  --stats bench\expert-tiering\stats\qwen36.bin ^
  --out F:\LLM\quants\Ornith-35B-Q4KM-repack-test.gguf --verify --sha256
```

做的事（纯排列，不改量化类型、不改数值精度）：
1. 读统计文件，按每层权重降序得到排列 `perm[il][j]`（并列按专家号升序，保证确定性）。
2. 专家张量：把 `ffn_gate_exps/up_exps/down_exps` 的第 j 个专家切片从原位置 `perm[j]` 搬来；
   量化块按专家连续存放，属于字节级移动，不涉及解码/重编码。
3. router：`ffn_gate_inp`（[n_embd, n_expert] F32）按同一排列重排列，保证 router 的 argmax 仍指向同一个逻辑专家。
4. 写出新 GGUF（流式读写，不整模型载入内存）。头部/KV/tensor-info 段逐字节复制，因此张量偏移全部保持不变；
   排列单独写到 `<out>.perm.json`（含统计文件 SHA256、源/产物 SHA256、逐层排列）。
5. 产物写 `F:\LLM\quants\` 独立目录，记录命令与 SHA256（AGENTS 要求，不覆盖原模型）。

### 实测（2026-10-21，Qwen3.6，30 层非恒等排列）

| 检查 | 结果 |
|---|---|
| 结构验证 | 头部逐字节一致；164 个按专家张量全部匹配排列（`--verify`） |
| 恒等排列对照 | 全零统计 -> 产物与原文件 **SHA256 完全一致**（写文件路径无损） |
| 可加载性 | 重排文件可正常加载生成（tg 19.0 vs 原 18.7 t/s，同量级） |
| KLD（README，c=64，1 chunk） | **0.01516 ± 0.00438**，top-1 一致率 **93.55%**；原模型自比 = 0.00000 / 100% |
| PPL（README，c=128，3 chunks） | 原模型 1.8638；重排 1.8958（**+1.7%**） |
| 选中专家集合（轨迹对比） | 329 条记录中 **109 条**至少 1 个专家不同（每次差 1-2 个） |

### 重要结论：纯排列不是数值等价的

排列改变了 8 项加权求和的累加顺序，产生约 1e-7 的相对扰动；但在 router 的近平局处这会翻转少数专家选择，
再逐层放大：约 1/3 的层记录出现 1-2 个专家差异，最终 KLD 0.015、PPL +1.7%。
这不是映射错误（文件级逐字节核对通过，恒等排列 SHA256 相同），而是**浮点累加顺序的真实影响**。

两个可选对策（下一轮实现，需你选）：
1. **恢复精确**：在 GGUF KV 里记录排列；runtime 在 MoE 加权求和前把 ids 映射回逻辑编号并按其排序累加，
   使累加顺序与原模型一致（预期 KLD ~0，代价是每层一次很小 host 映射，可用 host 侧 id 重排实现）。
2. **接受漂移**：把上述 KLD/PPL 作为质量门数据，阈值由你确认；排列带来的收益（上传段数、热前缀）与这点漂移权衡。

### 2026-10-21 定位进展：router 轴已排除

用户要求 KLD=0（逻辑顺序累加）。在执行器自测里加入「固定输入，打印 router 全部 256 个 logits」的探针，
分别在原模型与重排文件上运行（同一 x），并核对映射：

```
max |R[j] - O[perm[j]]| = 0.000000    （R=重排模型 logits，O=原模型，perm=逐层排列）
max |R[j] - O[inv[j]]|  = 2.983605
max |R[j] - O[j]|       = 3.797114
```

即 **runtime 看到的 router logits 与 `old[perm[j]]` 逐位相等**：router 的专家轴方向与排列方向都正确，
「轴搞反」的假设被排除。原始 logits 文件是 uint16 的 log-softmax（`nv=248324`，每 chunk 后一半 31 个位置），
之前按 float 数组直接比较得到的「首 token 巨大差异」是解析错误，不再作为证据。

下一步（待完成）：用固定 slot 序列直接比较两模型的单层 MoE 输出，确认专家张量也逐位一致；
若一致，则确认差异只来自加权求和的顺序，再实现你要求的「逻辑顺序累加」。

### 2026-10-21 最新 KLD 与路径二分（仍未归零）

统一参数（README，`-c 64 --chunks 2`，同 session、同构建）重测：

| 路径 | KLD | top-1 一致率 |
|---|---:|---:|
| cache 上传路径（`-ncmoe 41 --moe-cache-mib 6144`） | 0.00920 ± 0.00265 | 95.16% |
| 纯 CPU 专家路径（`-ncmoe 41`，无 cache，绕过上传） | **0.00920**（与上者完全一致） | 95.16% |

结论：差异**不在 cache 上传路径**——两条路径给出完全相同的 KLD，说明运行时对重排文件的专家张量解释在两条路径上一致地偏离。
剩余唯一未隔离的环节：文件层排列本身与运行时 mmap/加载/repack 的交互（含 CPU REPACK=1 的量化重排）。

下一步隔离方案（下次继续）：
1. 用 PoC（`pocs/moe-exec`，直接从 GGUF 读张量、走 ggml 图）对同一层、同一 ids 计算两文件的 MoE 输出，
   原文件 slot e 对重排文件 slot j（new[j]=old[e]）应逐位相等；这一步只在 ggml 层、不经过 llama runtime；
2. 若 PoC 层相等而 runtime 层不等 → 在 `llama-model-loader`/`llama-model` 的加载路径定位差异
   （重点：`REPACK=1`、mmap/resident 载入、tensor->data 替换）；
3. 若 PoC 层也不等 → repack 工具仍有映射错误（尽管 `--verify` 通过），需要按 ggml 实际 nb 布局重新核对。

探针开关（仅调试用，默认关闭）：`LLAMA_MOE_EXEC_SELFTEST=1 LLAMA_MOE_EXEC_PROBE=1`，
可选 `LLAMA_MOE_EXEC_IDS=0,1,2,...` 指定固定 slot 序列；日志行 `PROBE ...` / `PROBEOUT ...`。
（repack 侧 PROBEOUT 曾返回全 0，需先修探针的 256 槽 bank staging，再做单层对比。）

### 2026-10-21 路线调整（用户确认）

- **M2 改为 PP 方向**：整层专家预取 + 传输/计算重叠，提高 prefill（pp2048 目标 780+）；
  TG 方向的执行器已证否，保留为 env 门控工具。
- **冷专家降比特降级为最后保底**，不作为主要手段；优先完成重排 KLD=0 + 热前缀（连续上传段），再做 PP 重叠。



为什么可能更快（要逐项实测，不预设结论）：
- 热专家连续后，未命中上传变成**少数连续段**而不是散拷贝，DMA 段数下降；
- 可以引入“热前缀”布局：slot i == expert i（i < hot_count），去掉 slot-map 间接寻址与 host 重映射；
- 若某层选中的专家全在热前缀内，该层不需要任何上传；
- 统计与重排是**逐人**的：bench 语料上“静态命中≈覆盖”不适用于个人负载，样本中 top32 已覆盖 68%-81% 的权重。

约束与质量门：
- 纯排列不改量化类型，但如上所述不是位等价；在选出对策 1 之前，产物只能作为实验文件，不作为默认模型。
- 重排结果与统计文件绑定；换用户/换负载要重新累积、重新重排。旧排列可通过 `.perm.json` 回滚到原模型。
- 不做“冷专家降比特”（最后手段，需单独确认）。


## 3. 与越用越快的关系

```
正常使用（统计开启）
   -> 统计文件持续累积（衰减记忆 + 新数据加权）
   -> 用户执行 llama-expert-repack
   -> 新 GGUF（按自己的热度排列 + 热前缀）
   -> runtime 用新文件：上传段数/间接寻址/未命中字节下降
   -> 继续使用，继续累积（现在统计基于新排列的 ids，逻辑一致）
```

统计按**逻辑专家**记录；重排后模型内部编号变了，但 router 与专家一起重排，因此 ids 仍指向同一逻辑专家，
统计文件可以继续复用（KV 里记录排列，工具据此把新 ids 映射回旧编号再累计，避免累积错位——实现时处理）。

## 4. 为什么不能只用 bench 轨迹

- 现有全部数字（静态命中≈覆盖、LRU 48%@33%）来自 bench 语料；
- 不同人/不同任务的专家激活集合不同，画像必须来自本机真实使用；
- 因此统计做成默认即可长期打开的开关，而不是一次性采样。
